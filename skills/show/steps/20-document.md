# 문서 구조를 짜는 법

**로드 시점 - 보고 무게의 Step 2(구조) 에서 항목을 절로 묶을 때, 그리고 Step 3 에서 문장과 그림을 쓸 때.** 빠른 보기는 이 문서를 열지 않는다. 페이지 모양 전반은 [pages](../catalogs/pages.md) 에 있다. 템플릿을 채우고 화면, 인쇄, 결정, 전달을 확인하는 일은 [60-output](60-output.md) 에 있다.

고정 목차는 없다. 목차를 채우는 대신 **항목 목록에서 구조를 끌어낸다.** 항목이
없으면 절도 없고, 항목이 몰린 곳에 절이 선다.

## 세 층의 뼈대

어떤 질문에 답하든 이 세 층은 있다.

```
1층  한 장으로 끝나는 요약     세어진 판정, 이 문서가 답하는 질문
2층  항목을 묶은 본문 절들     묶는 기준은 아래 셋 중 하나
3층  받는 사람이 다른 부록     작업자용 절, 검증 방법, 원문 인용
```

1층은 **받는 사람이 여기서 멈춰도 되도록** 쓴다. 2층부터는 궁금한 사람만 내려간다.
3층은 없으면 안 만든다.

## 2층을 무엇으로 묶을 것인가

### 화면별 묶음

한 화면에 여러 항목이 몰려 있을 때. 개선 보고의 기본이다. 절 하나가 화면 하나이고,
그 안에서 항목을 항으로 세운다.

```
2. 시스템 목록 화면   R-3, A-6
   2.1 집계 표시  A-6
   2.2 식별자 컬럼  R-3
3. 시스템 수정 화면   R-1
```

읽는 사람이 화면을 아는 경우에 잘 맞는다. 화면 이름만 봐도 어디 얘기인지 안다.

### 판정별 묶음

판정이 갈릴 때. 명세 대조의 기본이다. **정할 것이 앞** 에 오고 잘된 것은 뒤로 간다.
받는 사람이 회의에서 다룰 것만 먼저 볼 수 있다.

```
2. 판단이 필요한 것   G-1 ~ G-3
3. 결함              G-4
4. 기획대로 된 것     한 장에 표로 요약
```

**잘된 것을 항목마다 펼치지 않는다.** 35개가 기획대로 됐다면 그것은 표 한 장이고,
어긋난 3개가 문서의 본문이다. 순서를 뒤집으면 받는 사람이 정할 것에 닿기 전에 지친다.

### 항목별 묶음

항목 하나하나가 독립된 결정일 때. 의사결정문의 기본이다. 절 하나가 항목 하나이고,
각 절이 같은 모양을 반복한다.

```
2. 안내 화면에 위치 지도가 없습니다
   기획서 원문 / 지금 화면 / 선택지 / 우리가 지어낼 수 없어 받아야 하는 것
3. 알림 발송 시점이 기획서에도 미정입니다
   ...
```

각 절의 내부 모양을 고정하면 두 번째 절부터는 읽는 속도가 붙는다. **선택지는
고르게 만들어 준다.** "어떻게 할까요" 로 끝내면 상대가 처음부터 생각해야 한다.
선택지는 `<ve-ask>` 로 두면 받는 사람이 고른 결과를 그대로 묶어 회신한다([60-output 결정 받기](60-output.md#결정-받기)).

### 원인별 묶음

점검 보고처럼 발견이 수십 개이고 화면 여러 곳에 흩어질 때. 영역별로 늘어놓으면 같은
원인이 영역마다 반복돼 읽는 사람이 패턴을 직접 찾아야 한다. **같은 원인끼리 묶고, 묶음은
무거운 순서로** 세운다. 묶음 머리에 "왜 한 묶음인가" 한 줄을 둔다(공통 컴포넌트가 없어서,
API 가 그 값을 안 보내서). 원인을 고치면 묶음 전체가 고쳐진다는 것이 그 한 줄에서 읽힌다.

```
1. 화면이 저장된 값 대신 짐작한 값을 그린다   1-1 사진 셋, 1-2 사진 둘, 1-3 코드 근거
2. 빈 값을 판정 문장으로 바꾼다               2-1 사진 둘, 2-2 표 하나
...
잘 지킨 곳                                   고칠 때 기준이 될 화면
```

### 축이 섞일 때 절 나누기

명세 대조를 하다 보면 "기획에 없는데 이미 있는 것" 이 나온다. 성격이 다르므로
같은 절에 넣지 않는다. 판정 어휘를 따로 두고 절도 따로 세운다.

## 판정 어휘

문서 전체에서 **한 벌로 통일한다.** 항목마다 다른 말로 적으면 세어지지 않고,
세어지지 않으면 1층 요약을 쓸 수 없다.

명세 대조라면 이 정도가 쓸 만하다.

```
구현됨        기획대로 화면에 있다
다르게 구현됨  있지만 기획과 모양이나 조건이 다르다
없음          화면에 없다
기획 미정      기획서 자체가 정하지 않고 남겼다
판단 필요      우리가 정할 수 없고 받는 사람이 정해야 한다
결함          기획과 무관하게 잘못 동작한다
```

`없음` 과 `판단 필요` 를 가르는 기준은 **누가 정하느냐** 다. 만들면 되는 것은
`없음` 이고, 무엇을 만들지부터 정해야 하는 것은 `판단 필요` 다.

`결함` 은 따로 세운다. 나머지는 상의할 것이지만 결함은 고칠 것이라 성격이 다르고,
섞어 두면 "이것도 논의 대상인가" 로 읽힌다.

점검 보고라면 판정은 무게다. `심각 / 중요 / 참고` 셋이면 충분하다. 심각은 사용자가
틀린 사실을 믿게 되는 것, 중요는 헷갈리거나 한 번 더 찾게 되는 것이다. 그리고 **화면으로
보였는가를 따로 단다.** 코드로는 확인했지만 데이터에 사례가 없어 찍지 못한 항목은 제목에
"(코드 근거)"를 붙이고 사진 자리에 못 찍은 이유를 적는다. 섞어 두면 찍은 것의 무게까지
의심받는다.

개선 보고라면 판정 대신 `조치` 한 줄이면 된다. 무엇이 문제였고 무엇을 했는지가
한 항목 안에 들어간다.

## 참조 코드

항목마다 코드를 붙이고 본문 절에서 그 코드를 참조한다. 목록에서 코드를 짚어
해당 절로 바로 갈 수 있다.

- `R-1`, `R-2` ... 요청받아 한 일
- `A-1`, `A-2` ... 하다가 발견해 함께 고친 것
- `G-1`, `G-2` ... 명세와 어긋난 것
- 점검의 발견은 묶음 번호를 따른다 `1-1`, `1-2` ... (원인이 같은 것끼리)

접두어를 나누는 이유는 받는 사람의 관심이 다르기 때문이다. 요청한 것은 "됐나" 가,
발견한 것은 "왜 건드렸나" 가, 어긋난 것은 "어떻게 할 건가" 가 궁금하다.

A 항목은 구분(동작, 표시, 수치, 권한)으로 묶으면 성격이 한눈에 보인다.

절 부제와 항 제목에 해당 코드를 강조색으로 단다.

```html
<h2><span class="n">3.</span>시스템 목록 화면</h2>
<div class="sub"><span class="rc">R-3</span>, <span class="rc">A-6</span> 표시 항목 및 집계 개선</div>
<h3><span class="n">3-1</span>집계 표시 <span class="rc">A-6</span></h3>
```

**본문에 절이 있는데 목록에 대응 항목이 없다면 목록이 빠진 것이다.** 코드를
붙이다 보면 이런 누락이 드러난다. 발견하면 목록을 채운다.

## 1층 요약을 쓰는 법

두 가지가 들어간다.

- **세어진 판정** - "35개 구현, 3개 판단 필요, 1개 결함". 이 한 줄이 문서를 대신한다
- **이 문서가 답하는 질문** - 무엇을 대조했고 무엇을 기준으로 삼았는지

**어디부터 읽으라고 안내하지 않는다.** 정할 것을 앞에 두는 것으로 이미 순서를 말했고,
거기에 "2절만 보셔도 됩니다"를 덧붙이면 문서가 자기 사용법을 설명하기 시작한다.
받는 사람은 목차를 읽을 줄 안다.

숫자를 크게 세우는 KPI 카드가 잘 맞는다. 다만 **의사결정용 문서는 톤을 낮춘다.**
큰 타이포와 면색 카드는 성과 공유에는 맞지만, 무엇을 정해야 하는지가 화면보다
앞서야 하는 문서에서는 방해가 된다. 구체 토큰은 `kit/show.css` 의 ledger 레지스터가 정본이다.

## 항 번호

`가. 나. 다.` 대신 `1.1`, `1.2` 를 쓴다. 모든 절이 "가." 로 시작하면 지금 어느
절 안에 있는지 제목만 봐서는 알 수 없다. 절 번호가 앞에 붙으면 위치가 자명하다.

시각적으로도 두 단계를 갈라 놓는다. 템플릿은 절 제목에 굵은 윗줄을, 항 제목에 카드 머리를
주어 크기 차이 없이도 층이 보이게 해 두었다. 그 모양을 보고서마다 바꾸지 않는다.

## 표를 쓸 자리와 쓰지 말 자리

**쓸 자리** - 두 값을 대조할 때, 그리고 판정이 같은 항목을 한 장으로 접을 때.
"기획대로 된 35개" 는 표가 정답이다.

**쓰지 말 자리** - 항목을 펼쳐 설명할 때. 셀 안에서 문장이 접히면 지저분해지고
세로 공간을 많이 먹는다. 대신 라벨을 왼쪽에 세우는 항목 목록을 쓴다.

```html
<div class="items">
  <div class="item">
    <div class="key"><div class="code">R-1</div><div class="name">기간별 추이 그래프</div></div>
    <div class="val">
      <div>두 종류의 측정값이 서로 다른 저장소에 있어 한 화면에 겹쳐 볼 수 없었습니다...</div>
      <div class="act"><b>조치</b>추이 그래프를 신설하고 두 값을 함께 읽는 조회 기능을 추가하였습니다.</div>
    </div>
  </div>
</div>

<div class="grp">
  <div class="gh">동작</div>
  <div class="glist">
    <div class="row"><div class="code">A-1</div><div>조회 기간을 직접 지정한 뒤...</div></div>
    <div class="row"><div class="code">A-2</div><div>분석 화면 진입 시...</div></div>
  </div>
</div>
```

그룹 라벨을 소제목 줄로 뽑으면 그룹마다 한 줄씩 더 먹는다. 옆에 붙이면
계층은 그대로 보이면서 세로가 줄어든다. 좁은 화면에서는 템플릿이 라벨을 위로 올린다.

## 그림 배치

비교하는 두 장은 한 카드 안에 `.pair` 로 나란히 둔다. 좁은 화면에서는 템플릿이 위아래로
쌓는다. 전후 비교면 각 그림 머리에 라벨을 색으로 구분해 단다.

```html
<div class="pair">
  <figure><div class="lab b">개선 전</div><img src="images/list-before.png" alt="개선 전 목록"><figcaption>목록 화면 - 1 식별자 열</figcaption></figure>
  <figure><div class="lab a">개선 후</div><img src="images/list-after.png" alt="개선 후 목록"><figcaption>목록 화면 - 1 식별자 열</figcaption></figure>
</div>
```

**세로로 긴 이미지는 `<figure class="tall">` 로 높이를 묶는다.** 묶지 않으면 카드 하나가
화면 몇 장을 먹는다. 인쇄에서는 템플릿이 묶음을 풀어 전체가 나온다.

캡션에는 화면 자리와 표시 번호가 가리키는 것을 적고, 본문에서 그 번호로 가리킨다.

**비교 대상이 없는 그림도 캡션은 단다.** 명세 대조에서 "지금은 이렇습니다" 한 장만
싣는 경우가 많은데, 캡션이 없으면 그것이 문제 화면인지 정상 화면인지 알 수 없다.

## 화면의 자리와 깊이

그림 한 장은 자기가 어디서 왔는지 말해 주지 않는다. 받는 사람은 화면 이름을 읽고
자기 머릿속 구조와 맞춰 보는데, 그 대조를 문서가 대신해 주지 않으면 그림마다 한 번씩
멈춘다. **화면을 실을 때는 그 화면의 자리와 깊이를 함께 적는다.**

세 가지를 말하면 된다.

- **어느 자리인가** - 경로로 적는다. `홈 탭`, `내 정보 탭 > 알림 설정`
- **몇 걸음인가** - 탭은 0걸음, 탭 안에서 스크롤하면 만나는 것도 0걸음, 눌러서 들어가면
  1걸음이다. 걸음 수가 다르면 "안 보인다"는 말의 뜻이 달라진다
- **어떻게 들어가는가** - 1걸음 이상이면 무엇을 눌러 오는지 한 줄. "목록의 카드를 누르면 열립니다"

### 화면이 넷을 넘을 때의 지도

절마다 경로를 적어도 전체 모양은 안 보인다. 본문 첫머리에 **한 장짜리 지도**를 두고
그 뒤에 상세를 편다. 왼쪽에서 오른쪽이 깊이이고 위아래는 같은 깊이의 다른 기능이다.

```
진입          탭                      눌러서 들어가는 곳
로그인  ->   홈        ->   상세
             검색      ->   상세
             내 정보   ->   알림 설정
             안내      ->   자주 묻는 질문
```

**돌아가는 길은 그리지 않는다.** 들어온 길의 역이라 화살표가 양쪽에 붙으면 어느 쪽이
흐름인지 읽히지 않는다. 탭끼리 오가는 선도 마찬가지다 - 넷이 서로 다 닿아 아무것도
말해 주지 않는다.

화면 흐름 지도 자체가 문서의 목적이면 이 스킬의 일이 아니다. 여기서 말하는 지도는
증거를 놓을 자리를 잡아 주는 한 장이다.

### 한 화면을 조각내 실을 때

긴 화면을 블록별로 잘라 여러 장으로 실으면 **그것이 한 화면이라는 사실이 사라진다.**
절 제목에 화면 이름을 한 번 세우고 그림은 그 아래에 모으되, 캡션에 순서를 적어 위에서
아래로 이어진다는 것을 말한다. `그림 3-7. 프로필(화면 위쪽)`처럼 쓴다.

## 무엇을 보여줄지 고르기

목록 화면에서 컬럼명 하나 바뀐 것을 보여주면 "이게 다야?" 소리를 듣는다.
같은 변경이라도 **그 값을 실제로 다루는 화면** 을 보여주면 무게가 다르다.

비교 대상이 아예 없던 것은 비교가 성립하지 않는다. 신규 기능 절로 따로 묶고
지금 화면만 싣되, 무엇이 없었는지를 문장으로 적는다.

명세 대조에서 `구현됨` 인 항목은 **대부분 그림이 필요 없다.** 표에 한 줄이면
된다. 그림은 어긋난 것과 정해야 할 것에만 쓴다.

## 문장

- 본문 완결 문장은 정중체(~입니다)로 쓴다.
- 키보드로 칠 수 있는 문자만 쓴다. 원문자, 특수 불릿, 화살표는 쓰지 않는다.
- 변경 이력을 문서에 적지 않는다. 받는 사람은 이전 문서를 본 적이 없다.
- **틀렸던 것을 문서 안에서 정정하지 않는다.** 만드는 중에 판정을 뒤집었으면
  문서에는 맞는 것만 남기고, 뒤집었다는 사실은 문서를 건네면서 말로 전한다.
- 고칠수록 분량이 늘기만 하면 잘못하고 있는 것이다. 새 절을 만들었으면 그
  내용을 담고 있던 기존 서술을 걷어낸다.
