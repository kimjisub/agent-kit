# 비교축별 준비

**로드 시점 - Step 0 에서 축을 고른 뒤, Step 3(찍기) 를 시작하기 전에. 고른 축의 절만 읽는다.**

| 부모(SKILL.md 절차) | 이 문서 |
|---|---|
| 1 항목과 판정 | 점검축은 §점검축 1~2 가 항목을 만든다. 나머지는 부모 그대로 |
| 3 찍기 | 축마다 준비(코드 되돌리기, 데이터 바꾸기, 문서 읽기, 사례 찾기) |

문서가 답하는 질문이 정해지면 무엇을 준비해야 하는지가 정해진다. 축마다 준비의
성격이 다르다. 시간축은 **코드를 되돌리는** 일이고, 상태축은 **데이터를 바꾸는**
일이며, 기준축은 **문서를 읽는** 일이다. 섞어 쓰는 경우가 흔하니 해당하는 절만
골라 읽는다.

---

## 시간축 - 이전 코드 <-> 지금 코드

"무엇이 바뀌었나" 에 답할 때 선다. 개선 후 화면만 있는 문서는 "좋아졌습니다"
라는 주장이고, 개선 전 화면이 옆에 있으면 그것은 증거가 된다.

### 1. 기준 커밋 고르기

이번 작업이 시작되기 직전 커밋을 찾는다.

```bash
git log --oneline -30
```

여러 세션이 같은 저장소를 다루면 내 작업과 남의 작업이 섞여 있다. `git log
--author` 나 파일 경로로 걸러 **내가 손댄 것이 시작되기 직전** 을 잡는다.

### 2. worktree 로 체크아웃

현재 작업 트리를 건드리지 않는다. 브랜치를 옮기면 사용자가 보던 화면이 바뀌고
다른 세션의 작업과 충돌한다.

```bash
git worktree add /tmp/before-stack <이전커밋해시> --detach
```

끝난 뒤 `git worktree remove /tmp/before-stack` 으로 정리하되, **문서를 다 만들
때까지는 남겨 둔다.** 이미지를 다시 찍어야 하는 일이 자주 생긴다.

### 3. 저장소와 포트를 분리

같은 DB를 쓰면 한쪽에서 돌린 마이그레이션이 다른 쪽을 깨뜨린다. 컨테이너 이름,
볼륨, 포트를 전부 다르게 준다.

```bash
# 예시 - 실제 값은 프로젝트 구성을 보고 정한다
# 지금 코드: DB 15433, 화면 3200
# 이전 코드: DB 15434, 화면 3210
```

docker compose 를 쓴다면 `-p` 로 프로젝트 이름을 나누는 것이 가장 간단하다.

### 4. 양쪽에 같은 데이터

시드 스크립트를 한 벌 만들어 접속 정보만 바꿔 두 번 돌린다. 몇 건을 넣었는지
세어 두고 문서의 검증 방법 절에 적으면 "같은 조건에서 찍었다" 는 근거가 된다.

## 상태축 - 조건 A <-> 조건 B

"마감 전과 후가 어떻게 다른가", "이 플래그를 켜면 뭐가 보이나", "권한별로 뭐가
다른가" 에 답할 때 선다. 코드는 하나이고 **데이터와 설정만 바꾼다.**

### 1. 상태를 가르는 값 찾기

화면이 갈리는 원인은 대개 셋 중 하나다. 코드에서 실제로 읽는 값을 찾는다.

- **플래그** - 기능 on/off 를 담은 설정이나 컬럼
- **시각** - 마감일, 행사일처럼 지금 시각과 견주는 값
- **주체의 상태** - 신청 여부, 선발 결과, 권한, 소속

셋이 섞여 한 화면을 만든다. 하나만 바꿔 놓고 "이 단계 화면" 이라고 찍으면 틀린다.

### 2. 상태 조합 적기와 만들기

단계마다 세 값을 표로 적어 두고, 그 조합을 실제로 DB와 설정에 넣는다.

```
단계 1 신청 접수중   applicationsOpen=true   now < 마감    status=submitted
단계 2 신청 마감     applicationsOpen=false  now > 마감    status=submitted
단계 3 선발 발표     resultsOpen=true        now > 마감    status=accepted
```

시각을 바꿀 때는 시스템 시계를 건드리지 말고 **데이터의 날짜를 옮긴다.** 시계를
바꾸면 인증 토큰과 로그가 함께 어긋난다.

### 3. 되돌릴 값 기록

상태축 캡처는 개발 DB를 실제로 바꾼다. 무엇을 어떤 값에서 어떤 값으로 바꿨는지
적어 두고, 캡처가 끝나면 되돌린다. 운영 DB는 어떤 경우에도 대상이 아니다.

## 기준축 - 명세 <-> 지금 화면

"기획대로 되었나, 남은 건 뭔가" 에 답할 때 선다. 준비의 대부분이 **읽는 일** 이고,
캡처는 그 결과를 뒷받침하는 자리에 온다.

### 1. 명세를 한 줄씩 항목으로

문단째로 "됐다/안 됐다" 를 판정하면 그 안에 섞인 미구현이 묻힌다. 한 문장이 요구
하나가 되도록 쪼개고 번호를 붙인다. 원문 표현을 그대로 옮겨 적어 두면 나중에
문서에 인용할 때 다시 찾지 않아도 된다.

명세가 여러 벌이면 **어느 것이 최신인지 먼저 정한다.** 같은 주제에 날짜가 다른
문서가 있으면 늦은 것이 이긴다. 어느 것을 기준으로 삼았는지 문서에 적는다.

### 2. 항목별 화면 확인과 판정

코드 검색만으로 판정하지 않는다. 문자열이 코드에 있어도 화면에 안 뜰 수 있고,
없는 것처럼 보여도 조건이 맞으면 뜬다. **판정은 화면에서 내린다.**

판정을 내리기 전에 확인할 것:

- 로그인했는가. 그 항목을 볼 자격이 있는 계정인가
- 그 항목이 뜨는 조건(플래그, 단계, 데이터)이 맞춰져 있는가
- 화면 아래쪽에 있어 스크롤 밖으로 나간 것은 아닌가

이 셋을 건너뛰면 있는 기능을 없다고 적게 된다. 실제로 나오는 실수다.

### 3. 명세에 없는데 있는 것

대조는 양방향이다. 기획서에 없지만 구현된 것은 "왜 넣었나" 를 물을 자리이고,
기획서 자체가 미정으로 남긴 것은 "이번에 정하자" 를 물을 자리다. 판정 어휘에
`기획 미정` 을 두면 이것이 구현 누락과 섞이지 않는다.

## 점검축 - 원칙 <-> 지금 제품

"우리 원칙대로 돼 있나", "이 화면들 전체를 훑어 문제를 찾아 줘"에 답할 때 선다. 기준축과
닮았지만 기준이 명세 조항이 아니라 **원칙이나 체크리스트**이고, 대상이 화면 몇 개가 아니라
제품 전체라 준비의 대부분이 코드를 훑는 일이다. 사진은 그 발견 가운데 화면으로 보일 수
있는 것을 골라 증명하는 자리에 온다.

### 1. 원칙을 판정 기준 표로

원칙 문서를 읽고 "이렇게 어긋나면 문제다"를 한 줄씩 적는다. 이 표가 서브에이전트 브리프와
보고서 맨 앞 기준 표에 그대로 들어간다. 원칙이 다른 스킬에 있으면 그 문서의 측정 기준을 옮겨
적고 출처를 단다.

### 2. 영역별 동시 훑기

제품이 크면 한 번에 못 읽는다. 저장 단위(스키마)와 화면 묶음이 같이 가는 영역 다섯에서 일곱으로
나누고, 영역마다 서브에이전트를 하나씩 띄운다. 브리프에 넣을 것:

- 판정 기준 표 전문, 읽기 전용이라는 것
- 그 영역의 스키마 파일, 화면 파일, 설계 문서 절
- 산출 모양 고정: `심각도 | 원칙 번호 | 파일:줄 | 무엇이 문제인지 | 사용자가 겪는 장면 | 처방`, 최대 개수, 잘된 점 두세 개

돌아온 발견은 영역별이 아니라 **원인별로 다시 묶는다**(→ [document §원인별 묶음](../steps/20-document.md#원인별-묶음)).
가장 무거운 서넛은 코드를 직접 열어 다시 확인한다. 서브에이전트의 발견은 그대로 믿으면 틀린 것이 섞인다.

### 3. 화면으로 보일 사례 찾기

발견마다 그 조건에 맞는 레코드가 지금 데이터에 있는지 읽기 쿼리로 센다. 있으면 그 레코드의
화면을 찍고, 저장된 값을 함께 적어 둔다(→ [capture §증거로 남기는 화면 값](../steps/30-capture.md#증거로-남기는-화면-값)).
없으면 "(코드 근거)" 항목이 된다. 사례를 만들려고 데이터를 바꾸지 않는다.

같은 사실이 화면 여러 곳에서 다르게 보이는 발견이면 **그 화면들을 모두 같은 레코드로 찍어**
나란히 둔다. 한 진행 건이 목록에서는 "통과", 상세에서는 "건너뜀"인 것이 사진 두 장으로 끝난다.

## 환경축 - 운영 <-> QA, 화면 폭

같은 코드가 환경에 따라 다르게 보이는지를 볼 때 선다. 대개 다른 축에 곁들여 쓴다.

- **환경 대조** - 배포 상태가 다를 수 있다. 무엇이 어느 커밋인지 먼저 확인한다.
  "고쳤는데 안 보인다" 의 대부분은 배포가 안 걸린 것이다
- **화면 폭** - 같은 화면을 여러 폭으로 찍는다. 문서에는 문제가 드러나는 폭만 싣고,
  나머지는 "다른 폭에서도 확인했습니다" 한 줄로 대신한다

---

## 축이 없을 때 - 현황 브리핑

비교 없이 지금 상태만 훑는 문서다. 축이 없으므로 **훑는 순서가 곧 구조** 다.
사용자가 실제로 지나가는 순서를 따라간다. 화면 목록을 코드 디렉터리 순서로
늘어놓으면 읽는 사람이 자기 동선과 맞춰 보느라 지친다.
