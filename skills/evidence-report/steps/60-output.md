# HTML 한 장으로 내기

**로드 시점 - Step 6 에서 보고서를 HTML 로 쓰고 건넬 때.** 절을 어떻게 묶고 무엇을 싣는지는 [20-document](20-document.md), 여기는 템플릿을 채우고 화면, 인쇄, 결정, 전달을 확인하는 일이다.

산출물은 HTML 한 장이다. 받는 사람은 그것을 넓은 화면에서도, 휴대폰에서도 열고, 필요하면 브라우저 인쇄로 PDF 를 만든다. 템플릿이 세 경우를 다 맞춰 두었으니 그 틀을 깨지 않는 것이 이 단계의 대부분이다. PDF 는 산출물로 따로 만들지 않는다.

## 골격

`assets/web-report.html` 을 보고서 폴더의 `index.html` 로 복사해 시작한다. 쪽 나눔이 없는 한 열 문서이고, 발견 하나가 카드 하나다.

- **맨 위 세 가지**: 이 문서가 답하는 질문(제목), 결론 두세 문장, 센 수. 받는 사람은 여기서 멈춰도 된다
- **찍은 조건 한 문단**: 어떤 환경과 데이터에서, 어느 계정으로, 몇 폭으로 찍었나. 찍으면서 바꾼 것(로그인, 데이터)이 있으면 여기 적는다
- **기준 표**: 무엇으로 판정했는지. 점검축이면 원칙 목록이다
- **항목 목록**: 개선 보고와 명세 대조는 `.items` 로 항목마다 코드, 사실, 조치나 판정을 한 줄씩 둔다
- **묶음 절 -> 발견 카드**: 카드는 사진(또는 나란히 두 장) -> 캡션 -> 무엇이 / 근거 / 겪는 장면 / 처방
- **화면으로 못 보인 항목**: 같은 카드 모양에 "(코드 근거)"를 제목에 달고 사진 대신 못 찍은 이유를 적는다
- **잘 된 곳**: 고칠 때 기준으로 삼을 화면. 점검 보고에서 빠지면 문서가 "다 틀렸다"로 읽힌다
- **결정**: 받는 사람이 정해야 하는 것은 그 근거가 되는 카드 바로 아래에 결정 블록으로 둔다(-> [결정 받기](#결정-받기))
- **다음에 할 것**: 영향이 큰 순서로

근거 칸에는 저장된 값과 화면 값을 나란히 둔다. "DB 는 SKIPPED, 화면 속성은 PASSED" 한 줄이 문단 하나보다 강하다.

```html
<div class="evidence">DB    orders.status = CANCELLED
화면  data-status="PAID"</div>
```

세로로 긴 캡처(전체 화면 이어 붙인 것)는 `<figure class="tall">` 로 높이를 묶어 카드가 화면을 다 먹지 않게 한다. 같은 대상을 두 화면에서 비교하면 `<div class="pair">` 로 나란히 두고, 전후 비교면 각 그림 머리에 `<div class="lab b">개선 전</div>`, `<div class="lab a">개선 후</div>` 를 단다.

## 겹쳐 보기 - 나란히, 슬라이더, 차이

두 그림이 **픽셀 단위로 맞으면** `.pair` 에 `data-compare` 를 달고 `assets/compare.js` 를 보고서 폴더에 복사해 `report-nav.js` 뒤에 넣는다(골격에 이미 있다). 그림 위에 「나란히 / 슬라이더 / 차이」 막대가 생긴다.

- 맞는다 = 같은 대상을 같은 범위, 같은 축척, 같은 뷰포트로 찍어 두 장의 픽셀 크기가 같고 같은 좌표가 같은 자리를 가리킨다. 같은 화면을 코드 전후로 같은 뷰포트에서 찍은 것, 같은 도구로 같은 범위를 뽑은 도면(PCB 층, 회로도 시트), 같은 크기로 렌더한 3D 가 해당한다. 스크롤 위치나 레이아웃이 달라 내용이 밀린 캡처는 크기가 같아도 맞지 않는다. 그런 짝에는 달지 않는다
- 보는 방식은 페이지 전체의 상태 하나이고 기본은 슬라이더다. 어느 짝의 막대에서 바꿔도 모든 짝이 함께 바뀐다. 짝마다 처음 방식을 따로 정하지 않는다(`data-compare` 에 값을 달지 않는다). **왜** - 한 짝만 슬라이더로 바꾸고 나머지가 나란히로 남으면 받는 사람이 짝마다 다시 눌러야 하고 같은 방식으로 견주지 못한다.
- 두 장의 픽셀 크기가 다르면 스크립트가 슬라이더와 차이를 끄고 이유를 막대에 적는다. 그러니 달고 나서 세 모드를 모두 눌러 보고, 꺼져 있으면 Step 5 로 돌아가 같은 범위로 다시 자른다
- 차이 모드는 같은 픽셀을 흐린 회색, 전에만 진한 것을 빨강, 후에만 진한 것을 초록, 둘 다 바뀐 것을 자주로 칠하고 바뀐 픽셀 비율을 적는다. `report.html` 처럼 이미지를 넣은 파일과 서버로 연 화면에서 이렇게 나오고, 원본 폴더를 file:// 로 열면 픽셀을 읽을 수 없어 CSS 차이 합성(같으면 검정)으로 대신한다
- 슬라이더는 그림 어디를 눌러도 경계가 그 자리로 오고 그대로 끌면 따라온다. 그림을 누른 뒤에는 방향키(Shift 는 10칸)도 된다
- 캡션은 모든 모드에서 그대로 남는다. 인쇄에는 늘 나란히로 나온다

- **왜** - 같은 범위로 뽑은 PCB 도면 두 장을 나란히 두면 받는 사람이 두 그림 사이를 눈으로 오가며 다른 곳을 찾아야 했다. 겹쳐 보면 바뀐 자리가 그 자리에서 보인다.

## 목차와 읽은 위치

절이 셋을 넘는 보고서는 `assets/report-nav.js` 를 보고서 폴더에 복사해 `decisions.js` 뒤에 넣는다(골격에 이미 있다). 받는 사람이 처음 열었을 때 분량을 알고, 나눠 읽다 돌아왔을 때 어디까지 봤는지 알게 한다.

- 왼쪽 목차는 `<main>` 의 `h2` 가 절, 그 절 안의 카드 `h3` 가 항목이다. 따로 표시할 것은 없고, 목차에서 뺄 `h2` 에만 `data-nav="skip"` 을 단다. 그래서 **절 제목은 `h2`, 카드 제목은 `h3` 로만 쓴다.** 굵은 글자나 `div` 로 만든 제목은 목차에 안 잡힌다
- 맨 위에 문서 제목, 절과 사진과 결정 수, 예상 읽기 시간, 지나간 절과 정한 결정의 진행 막대가 나온다. 절 줄 끝에는 표시가 하나만 붙는다(남은 결정 수, 다 정함, 또는 지나간 절의 체크 원). 지금 보는 절은 흰 카드로 떠오르고 그 안의 항목이 번호 열과 한 줄 제목으로 펼쳐진다
- 다시 열면 「이어 보기」 가 마지막 위치로 데려간다. 키 `[` `]` 는 앞뒤 절. 1100px 미만에서는 왼쪽 위 「목차 n / m」 버튼이 서랍을 열고, 열린 동안 그 버튼은 오른쪽 위 「닫기」 가 된다. 인쇄에는 나오지 않는다
- 읽음은 절의 끝이 화면 아래에 닿은 것으로 판정한다. 훑어 내린 것도 읽음이 되므로, 받는 사람에게는 「지나간 곳」 이라고만 말한다
- 건네기 전에 직접 끝까지 내려 보고 목차의 체크와 수가 맞는지 확인한 뒤 「표시 지우기」 를 누른다. 같은 브라우저로 받는 사람이 열면 내가 읽은 표시가 남아 있다

- **왜** - 사진 71장, 결정 66개짜리 보고서를 받은 사람이 어디까지 봤는지, 얼마나 남았는지 모른 채 다른 이야기로 넘어갔고, 결정이 하나도 돌아오지 않았다.

## 디자인

골격의 스타일이 정본이다. 보고서마다 색이나 글꼴을 새로 고르지 않는다. 받는 사람이 여러 보고서를 같은 눈으로 읽게 하려는 것이다.

- 바탕은 종이(옅은 회색)와 카드(흰색) 두 톤, 글은 잉크 한 색이다. 색은 판정(심각 빨강, 중요 주황, 좋음 초록), 전후 표시(전 회색, 후 파랑), 결정(파랑)에만 쓴다. 강조를 색으로 늘리면 판정 색이 묻힌다
- 절 머리는 번호(회색 작은 숫자) + 제목, 위에 가는 줄. 카드는 둥근 모서리와 옅은 그림자 한 단계. 카드 안 순서는 머리(판정 + 제목) → 사진 → 캡션 → 본문 → 결정
- 숫자는 고정폭 숫자(`tabular-nums`). 표는 `.tw` 로 감싸 둥근 테두리 안에 두고, 금액·건수 열은 `td.num` 으로 오른쪽 맞춤
- 전후 짝은 `.pair` 안에서 두 그림의 머리 띠(`lab b` 「전 · 지금」, `lab a` 「후 · 시안」)와 캡션 높이가 맞게 나란히 선다. 두 장의 비율이 크게 다르면 같은 영역으로 잘라 맞춘다(Step 5)
- 본문 폭은 1040px 안. 목차가 왼쪽 288px 를 쓰므로 넓은 화면에서도 본문은 가운데 한 열이다

## 화면과 인쇄

템플릿은 세 보기를 따로 맞춘다.

| 보기 | 템플릿이 하는 일 |
|---|---|
| 넓은 화면 | 1120px 한 열. 두 장 비교는 좌우로 |
| 좁은 화면(720px 이하) | 두 장 비교, 항목 목록의 라벨, 근거 칸의 이름을 위아래로 쌓는다. 표는 `.tw` 안에서 가로로 밀린다 |
| 인쇄 | A4, 여백 14mm. 결정 막대와 빈 입력칸은 빠지고 고른 선택지만 진하게 남는다. 그림과 카드 머리는 쪽 사이에서 잘리지 않는다 |

그래서 쓰는 동안 지킬 것이 셋이다.

- **폭을 px 로 고정하지 않는다.** 인라인 `style` 에 `width:900px` 같은 값을 넣으면 좁은 화면이 깨진다
- **표는 `<div class="tw">` 로 감싼다.** 안 감싸면 좁은 화면에서 표가 화면 밖으로 나간다
- **템플릿의 `<style>` 을 보고서마다 고치지 않는다.** 고쳐야 할 것이 있으면 템플릿을 고친다

다 쓴 뒤 세 보기를 다 열어 본다.

```bash
bash scripts/check_print.sh <보고서 폴더>/index.html     # 확인용 PDF 와 쪽마다 PNG
```

PNG 를 전부 Read 로 연다. 그림이 쪽 사이에서 잘렸는지, 빈 쪽이 끼었는지 본다. 좁은 화면은 브라우저 도구로 폭을 390 으로 두고 전체를 찍어 연다. headless Chrome 의 `--window-size` 는 500 아래로 줄지 않으니 그것으로 재지 않는다.

## 결정 받기

보고서가 결정을 요청하면, 받는 사람이 문서 안에서 고르고 적은 것을 **그대로 대화에 붙여 넣을 수 있게** 한다. 답을 다시 문장으로 옮겨 적다가 빠지거나 바뀌는 일이 없어진다.

`assets/decisions.js` 를 보고서 폴더에 복사하고, 결정마다 블록 하나를 둔다. 블록 모양과 속성은 그 파일의 헤더 주석에 있고, `assets/web-report.html` 의 첫 카드에 예가 있다. 화면 아래 막대에는 정한 수와 `복사`, `지우기` 만 있다. 복사하면 정한 것만 Markdown 으로 묶이고, 묶은 글을 화면에 펼쳐 보이지 않는다.

- **결정은 그 근거가 되는 내용 바로 아래에 붙인다.** 발견 카드라면 카드 안 맨 끝이다. 문서 끝에 모으면 받는 사람이 고를 때마다 위로 올라가 내용을 다시 찾는다. 막대(`<div id="decisions"></div>`)만 문서 끝에 둔다
- 발견마다 결정이 필요하면 "이번에 고친다 / 나중에 / 고치지 않는다" 세 갈래가 기본이다. 정책처럼 고를 것이 따로 있는 발견은 질문과 선택지를 그 내용에 맞춘다
- **선택지마다 고르면 무엇이 일어나는지를 `data-then` 으로 단다.** 묶은 결과에 "답"과 함께 "그러면"이 실려 받은 쪽이 해석 없이 움직인다. 묶음에는 정한 것만 실리고 안 정한 것은 번호만 한 줄로 남는다
- **`data-then` 은 손으로 쓴다.** "이번에 고친다"에는 그 카드의 처방을 싣는다. 카드 본문을 스크립트로 잘라 넣으면 처방 칸이 없는 카드(표로 된 카드, 코드 근거 카드)에서 본문 앞부분이 들어가 받는 쪽이 할 일을 못 읽는다. 처방이 없는 카드면 처방부터 쓴다
- **결정 블록 위에는 판단 재료가 먼저 있다.** 블록마다 다섯 가지가 본문이나 힌트 어딘가에 있어야 한다. 하나라도 비면 받는 사람은 고르지 않고 넘어간다
  1. 배경: 왜 지금 이것을 정하나. 근거 원문(회의록, 요청)을 한두 문장 인용한다
  2. 실제 규모: 이 결정이 지금 몇 건에 걸리나. 운영 데이터를 읽기로 세고, 셀 수 없으면 셀 수 없다고 쓴다. 시연 데이터 숫자와 섞지 않는다
  3. 누가 무엇을 겪나: 고르면 실제 쓰는 사람(역할) 기준으로 달라지는 장면
  4. 되돌리는 법과 비용: 코드만 되돌리면 되나, 데이터 정리가 필요한가, 합칠 때 일이 얼마나 되나
  5. 추천과 이유: 추천 선택지를 맨 앞에 두고 라벨 끝에 「(추천)」. 근거가 약하면 추천 대신 무엇이 더 필요한지를 쓴다
- **선택지마다 그림과 장단을 둔다.** 선택지가 화면이나 데이터 모양을 바꾸면, 구현한 선택지는 찍은 사진을, 구현하지 않은 선택지는 실제 화면의 DOM 만 바꿔 찍은 목업(그림에 「목업」 표시)이나 데이터 구조·흐름 전후 그림(mermaid 를 SVG 로 미리 그려 넣는다. 파일 하나로 묶이므로 CDN 스크립트는 쓰지 않는다)을 붙인다. 블록 위에 선택지 비교 표(장점 · 단점 · 누가 무엇을 겪나)를 둔다. 글로만 쓴 선택지는 받는 사람이 머릿속으로 그려야 해서 고르지 못한다
- **무게를 꼬리표로 보인다.** 선택지와 맨 위 요약에 색 배지로 `DB 구조 변경`(새 테이블·칸·제약) · `데이터 정리 필요` · `API 바뀜`(다른 시스템이 쓰는 응답) · `화면만`, `공수` 소·중·대와 어림(반나절, 2~3일), `되돌리기 쉬움`/`되돌리기 어려움`을 단다. 공수가 크거나 구조가 바뀌는 결정은 맨 위에서 따로 강조한다
- **`data-context` 에 배경 한 줄**을 둔다. 묶은 결과만 받아도 무엇에 대한 답인지 알게 한다
- **결정 수를 줄인다.** 정말 받는 사람이 정해야 하는 것(돈, 법, 일하는 방식, 되돌리기 어려운 것)만 블록으로 두고, 추천이 분명하고 되돌리기 쉬운 세부 질문은 「추천대로 진행」 표 하나로 묶는다. 맨 위에 「꼭 정할 것 N개 / 추천대로 둘 것 M개」 를 센다
- **왜** - 시안 아홉 개를 전후 비교한 보고서(결정 66개)에 선택지와 짧은 힌트만 두었더니, 받은 사람이 배경과 자료가 모자라 하나도 고르지 못했다. 배경과 숫자를 채운 뒤에도 선택지마다 그림과 장단이 없고, 공수가 크거나 DB 구조가 바뀌는 결정이 가벼운 결정과 같은 모양이라 묻힌다는 지적이 이어졌다. 선택지만으로는 받는 사람이 처음부터 조사해야 한다
- 제목(`data-title`)을 생략하면 감싼 카드의 제목을 쓴다. `data-id` 는 카드 번호와 같게 둔다
- 속성값(`value`, `data-then`, `data-context`) 안에는 큰따옴표를 쓰지 않는다. 속성이 거기서 끝나 블록이 깨진다. 인용은 「」로 한다. `inline-images.py` 가 묶을 때 이것을 찾아 실패한다
- 여러 개를 고를 수 있으면 checkbox, 하나면 radio. 선택지에 없는 답과 조건은 메모 칸이 받는다
- 고른 것은 그 브라우저에 저장돼 다시 열어도 남는다. 다른 브라우저나 다른 기기에서 열면 비어 있다

건네기 전에 직접 하나 골라 `복사` 를 누르고 묶인 글을 확인한다. 확인하며 고른 값은 `지우기` 로 지운다. 같은 브라우저로 받는 사람이 열면 내가 고른 답이 미리 차 있다.

답이 대화로 돌아오면 그 Markdown 의 "그러면" 줄이 다음 할 일 목록이다. 메모가 선택지와 어긋나면(답은 "둔다", 메모는 "다음 분기에") 진행 전에 되묻는다.

## 받는 사람이 둘이면

배포 절차, 환경변수 이름, 스크립트 경로처럼 작업자만 알면 되는 내용은 템플릿 끝의 `<section id="internal">` 에 둔다. `report.html` 로 열면 빠지고 `report.html?internal` 로 열면 나온다. 파일은 하나라 두 벌이 갈리지 않는다.

내부 절에는 실제 이름을 적는다. "서버 설정이 추가됩니다" 로는 무엇을 해야 하는지 알 수 없다. 환경변수 이름, 실행할 스크립트, 누락 시 무슨 일이 생기는지를 쓴다. 비밀값은 값이 아니라 이름과 받는 곳만 쓴다.

## 파일 하나로 묶기

이미지를 `images/` 에 두고 `index.html` 로 쓴 뒤, 건넬 때 하나로 묶는다.

```bash
python3 scripts/inline-images.py index.html report.html   # 이미지와 decisions.js, report-nav.js, compare.js 를 함께 넣는다
```

`index.html` 은 고칠 때 쓰고, 건네는 것은 `report.html` 이다. 고치면 다시 묶는다.

- **왜** - 이미지 폴더와 떨어지면 깨지고, 간이 정적 서버는 여러 장을 동시에 받을 때 일부를 놓친다. 파일 하나는 링크로도 첨부로도 간다.

## 건네기

로컬 경로를 주지 않는다. 받는 사람 기기에서는 안 열린다. 길은 둘이다.

- **파일 그대로**: `report.html` 은 이미지와 스크립트가 든 파일 하나라 메일, 메신저, 공유 드라이브에 첨부하면 그대로 열린다. 기본은 이것이다
- **링크**: 받는 사람이 이미 접근하는 정적 호스팅(사내 위키의 첨부, 객체 저장소, 사내망 서버)에 올린다. 결정 막대의 복사는 HTTPS 이거나 파일로 열었을 때 클립보드를 바로 쓰고, 그 밖의 http 주소에서는 선택 복사로 대신한다

Tailscale 을 쓰는 환경이면 `serve-tailscale.sh` 가 보고서 폴더를 tailnet 안 HTTPS 주소로 내보낸다.

```bash
bash scripts/serve-tailscale.sh <보고서 폴더> 4590 report.html
# URL https://<기기 이름>.<tailnet>.ts.net:4543/report.html
# PID 12345
# 내리기: tailscale serve --https=4543 off && kill 12345
```

스크립트가 그 주소로 실제 응답을 받은 뒤에만 URL 을 낸다. 받는 사람에게 내리는 명령을 함께 알린다. tailnet 밖 사람에게는 이 링크가 안 열리니 그때는 파일을 보낸다.

## 건넨 화면 확인

건네기 전에 받는 사람이 여는 방식 그대로(파일이면 파일, 링크면 링크) 열어 읽는 사람의 눈으로 본다. 이미지 파일이 멀쩡해도 화면에서는 깨질 수 있다.

```js
// Playwright 나 쓰는 도구의 eval 로: 모든 이미지가 실제로 그려졌나
await page.goto('<URL 또는 file:// 경로>');
for (let i = 0; i < 20; i++) { if (await page.evaluate(() => [...document.images].every(i => i.complete && i.naturalWidth > 0))) break; await page.waitForTimeout(500); }
console.log(await page.evaluate(() => [...document.images].filter(i => !i.naturalWidth).length), '장 깨짐');
```

깨진 것이 0 이면 카드 서너 곳으로 스크롤해 찍고 Read 로 연다. 사진과 캡션의 번호가 맞는지, 표가 넘치지 않는지 본다.
