# 보여 주기

**로드 시점 - 결과나 의도를 글로 설명했거나 설명하려는데 읽는 사람이 한 번에 이해하기 어려울 때.** 받는 사람이 지금 대화 중인 사용자든 나중에 문서를 받을 남이든 같다. 화면에 드러나는 큰 작업을 마쳤으면 요청이 없어도 완료 보고를 여기서 시작한다.

## 목적

AI 의 결과물은 대부분 글로 나온다. 글은 한 줄씩 읽어야 하고, 읽는 사람은 그 줄들을 머릿속에서 화면, 구조, 순서, 크기로 다시 그려야 이해한다. 그 다시 그리기가 막히는 자리가 **이해 병목**이다. 어디 얘기인지 모른다, 무엇이 바뀌었는지 안 보인다, 셋이 어떻게 이어지는지 안 그려진다, 조건을 바꾸면 어떻게 되는지 상상이 안 된다, 이 숫자가 큰지 작은지 모른다. 이 스킬은 그 병목을 찾아 대신 그려 주는 페이지를 만든다.

그래서 형식이 정해져 있지 않다. 병목이 수단을 정한다. 실제 화면 두 장을 겹쳐 보이는 것이 맞는 자리가 있고, 바뀐 코드를 diff 로 보이는 자리, 구조도 한 장이면 끝나는 자리, 값을 직접 바꿔 봐야 이해되는 자리가 있다. 맞는 부품이 없으면 그 페이지 안에 HTML, CSS, JS 로 직접 만든다. 정식 보고서(판정, 결정 블록, 인쇄)도 그 수단 가운데 하나이고, 남에게 건네 남는 문서가 필요할 때 얹는다. 큰 작업을 끝내고 "완료했습니다" 한 줄로 넘기면, 받는 사람이 직접 화면과 코드를 열어 확인하는 비용이 그쪽으로 넘어간다.

결과물은 늘 HTML 한 장이다. 이미지와 스크립트를 안에 넣어 파일 하나로 열리고, 휴대폰에서도 읽히며, 받는 사람이 바깥 서버 없이 연다.

무게는 둘이고 Step 0 에서 고른다.

| 무게 | 받는 사람 | 얹는 것 |
|---|---|---|
| 빠른 보기 | 지금 대화 중인 사용자 | 병목을 푸는 데 필요한 것만. 판정 세기, 결정 블록, 인쇄 확인은 하지 않는다 |
| 보고 | 코드와 대화를 모르는 남, 나중에 다시 열 사람 | 질문 한 문장, 센 판정, 찍은 조건, 결정 블록, 좁은 화면과 A4 인쇄 확인 |

## 핵심 원칙

1. **병목부터 찾는다.** 무엇을 그릴지가 아니라 읽는 사람이 어디서 막히는지에서 시작한다. 늘 쓰던 카드 모양부터 채우면 병목은 그대로 남고 분량만 는다. 글로 충분히 읽히는 대목은 글로 둔다. -> Step 0
2. **보이는 것은 실제에서 온다.** 화면은 실제로 띄워 찍은 것, diff 는 실제 `git diff`, 숫자와 차트는 실제 쿼리와 명령 출력, 구조도는 코드나 문서를 읽어 확인한 관계다. 기억으로 "이랬을 것"을 그리면 거의 틀린다. 이전 화면에는 지금은 지워진 요소가 있었고, 플래그를 켜 보면 예상과 다른 화면이 나온다. 설명하려고 지어낸 예시나 목업은 그림에 그렇다고 적는다. 그래야 페이지에 "재현이 아니라 실제로 동작한 결과입니다"라고 쓸 수 있고, 그 한 문장이 페이지 전체의 신뢰를 정한다. -> Step 1
3. **보인 것 옆에 근거를 둔다.** 그림은 "이렇게 보인다"까지만 말한다. 저장된 값과 화면 값(`data-*` 속성, 화면 낭독 글), 파일과 줄, 명령과 출력을 옆에 적으면 "왜 그런가"까지 말한다. -> Step 1
4. **맞는 수단이 없으면 만든다.** 부품에 맞추려고 병목을 버리지 않는다. 단계를 따라가야 이해되는 것은 넘겨 보게, 조건을 바꿔 봐야 이해되는 것은 바꿔 보게 만든다. 만든 장치도 원칙 2 를 따른다. 실제 값으로 돌고, 실제 결과와 어긋나지 않는다. -> Step 3
5. **설명이 대상을 덮지 않는다.** 표시는 대상 안에서 요소를 찾아 그 자리에 그리고, 이미지에는 번호만 두고 설명은 캡션으로 뺀다. 좌표를 눈대중으로 넣으면 한 열씩 밀리고, 라벨을 그림 위에 얹으면 제목이나 옆 값이 가려진다. -> Step 3
6. **만든 것은 열어서 본다.** 도구가 성공을 돌려줬다는 것은 파일이 써졌다는 뜻일 뿐이다. 표시가 엉뚱한 요소에 갔는지, 조작 장치가 실제로 움직이는지, 첫 화면만 보고 답이 나오는지는 열어 봐야 안다. -> Step 4
7. **확인한 것과 안 한 것을 가른다.** 코드로는 확인했지만 화면으로 못 보인 것은 "(코드 근거)", 출처를 다시 열지 못한 것은 "(확인 못 함)"으로 따로 단다. 섞으면 확인한 것의 무게까지 의심받는다. -> Step 1, 2

## 정책

| 정책 | 언제 걸리나 | 내용 |
|---|---|---|
| **데이터와 설정은 읽기만, 바꾸려면 묻는다** | Step 1 | 사례를 찾는 쿼리는 자유다. 사례를 만들려고 개발 DB 를 바꾸는 것은 사용자 확인 뒤에만 하고, 바꾼 값을 적어 두었다가 되돌린다. 운영 DB 는 어떤 경우에도 대상이 아니다 |
| **만들면서 바뀐 것은 페이지와 보고에 적는다** | Step 1, Step 5 | 로그인 세션 생성, 외부 로그인 동의, 개발 DB 변경처럼 재료를 모으며 생긴 흔적 |
| **페이지는 바깥으로 요청하지 않는다** | Step 3 | CDN 스크립트, 웹 폰트, 외부 API 를 부르지 않는다. 받는 사람 기기에서 막히거나 내용이 바뀌고, 파일 하나로 묶이지 않는다. 라이브러리가 필요하면 그 코드를 페이지에 넣거나 미리 그려 SVG 로 넣는다. 비밀값과 로그인 상태 파일은 페이지에 넣지 않는다 |
| **받는 사람이 열 수 있는 형태로 건넨다** | Step 5 | 로컬 경로는 받는 사람 기기에서 안 열린다. `report.html` 파일을 보내거나 링크를 만들고, 링크면 실제로 열리는 것을 확인한 뒤 건넨다 |
| **바깥으로 보내는 것은 확인받는다** | Step 5 | 슬랙, 메일, 고객 전달은 초안으로 둘지 바로 보낼지 먼저 묻는다 |

## 절차

```
0. 병목과 무게   READ <- catalogs/bottlenecks - 병목마다 맞는 수단. 고르지 않고 시작하면 늘 쓰던 모양이 된다
1. 재료          READ <- 재료에 맞는 variants 하나 - screen(실제 화면), change(바뀐 코드와 문서), drawing(도면과 렌더), data(값과 출력)
                 보고에서 비교축이 있으면 variants/axes 의 그 절도 - 축마다 준비(코드 되돌리기, 데이터 바꾸기, 명세 읽기)가 다르다
2. 구조          보고면 READ <- steps/20-document - 항목을 묶는 기준, 판정 어휘, 요약. 빠른 보기는 Step 2 안의 세 줄로 끝난다
3. 수단          READ <- steps/40-build 와 catalogs/bottlenecks 의 그 수단 절 - 어기면 좁은 화면과 인쇄가 깨지고 파일 하나로 안 묶인다
4. 확인          (여는 문서 없음. 확인 목록은 Step 4 안에)
5. 내기          READ <- steps/60-output - 골격, 결정 받기, 화면과 인쇄, 묶기, 건네기
```

### Step 0. 병목과 무게

세 가지를 한 줄씩 적고, 보고면 항목 목록을 더한다.

1. **누가 무엇을 이해해야 하나.** "사용자가 이번 리팩터로 호출 순서가 어떻게 바뀌었는지", "기획자가 기획서 대비 남은 것"처럼 받는 사람과 대상을 함께 적는다. 받는 사람이 다르면 같은 결과라도 막히는 자리가 다르다. 개발자는 diff 로 이해하고 기획자는 화면으로 이해한다.
2. **글로 쓰면 어디서 막히나.** 지금까지 쓴 답이나 쓰려는 설명을 놓고, 읽는 사람이 머릿속에서 다시 그려야 하는 자리를 찾는다. [bottlenecks](catalogs/bottlenecks.md) 의 병목 표에서 해당하는 줄을 고르고 그 줄의 수단을 후보로 적는다. 병목이 여럿이면 가장 먼저 막히는 것부터 푼다.
3. **무게.** 받는 사람이 지금 대화 중인 사용자면 빠른 보기, 남이거나 문서로 남으면 보고다. 보고면 페이지가 답하는 질문을 한 문장으로 적는다("이번 주에 고친 것을 고객에게 설명한다"). 한 문장으로 안 써지면 페이지를 둘로 나눈다.
4. **보고면 항목부터 적는다.** 재료를 모으기 전에 다룰 것을 항목으로 적고, 각각에 참조 코드와 판정, 보일 재료를 단다([document §참조 코드](steps/20-document.md#참조-코드), [§판정 어휘](steps/20-document.md#판정-어휘)). 이 목록이 무엇을 찍고 무엇을 뽑을지 정한다. 캡처부터 시작하면 다시 찍게 된다.

끝나면 받는 사람, 병목과 후보 수단, 무게, 보고면 항목 목록이 정해져 있다. 병목이 하나도 안 나오면 글로 충분하다는 뜻이니 페이지를 만들지 않고 글로 답한다.

### Step 1. 재료

보일 것을 실제에서 모은다. 재료마다 모으는 법과 막히는 곳이 달라 해당하는 문서만 연다. 섞이는 것이 보통이다. 화면에 드러나는 변경이면 change 와 screen 을 함께 연다.

| 재료 | 문서 | 무엇을 모으나 |
|---|---|---|
| 실제 화면 | [screen](variants/screen.md) | 띄워 찍은 화면, 화면 안에 그린 표시, 화면 값과 저장된 값 |
| 바뀐 코드와 문서 | [change](variants/change.md) | 범위를 고른 diff, 바뀐 이유를 말하는 커밋과 대화 |
| 도면과 렌더 | [drawing](variants/drawing.md) | 같은 범위와 축척으로 뽑은 도면, 렌더, 데스크톱 앱 화면, 받은 이미지 |
| 값과 출력 | [data](variants/data.md) | 쿼리 결과, 명령 출력, 로그, 측정값. 원본 파일째로 |

대화에 이미 있는 것(조사해 정리한 내용, 설계 의도, 고른 안과 버린 안)도 재료다. 다만 그 안의 숫자와 관계는 원래 출처(도구 출력, 파일과 줄)를 다시 열어 맞는지 보고 싣는다. -> 핵심 원칙 2

모으는 동안 항목마다 근거(파일과 줄, 저장된 값, 명령)를 함께 적어 둔다. 나중에 되짚으려면 다시 들어가야 한다. 모으다 보면 보일 수 없는 것이 나온다. 그것은 그 자리에서 "(코드 근거)"나 "(확인 못 함)"으로 표시한다. -> 핵심 원칙 3, 7

끝나면 재료 폴더(`images/raw/`, `data/`, diff 파일)와 항목별 근거가 있다.

### Step 2. 구조

**빠른 보기**는 세 줄로 끝난다.

- 맨 위에 답 한두 문장. 무엇을 보면 되는지가 아니라 무엇이 결론인지를 쓴다
- 그 아래 병목 순서대로 수단을 하나씩 놓는다. 수단마다 무엇을 보라는 것인지 한 줄을 붙인다
- 근거와 세부는 `<details>` 로 접어 둔다. 궁금하면 펼친다

**보고**는 [document](steps/20-document.md) 를 따른다. Step 0 의 항목 목록에서 판정을 세어 첫 장에 올리고, 항목을 화면별, 판정별, 원인별, 항목별 중 하나로 묶는다. 작업 중 고친 것을 빠뜨리기 쉬우니 `git log` 를, 명세 대조라면 원문을 한 줄씩 훑어 목록을 채운다.

어느 무게든 받는 사람이 위에서부터 읽다가 언제든 멈춘다고 가정한다. 빈 절은 만들지 않는다.

끝나면 위에서 아래로 놓일 순서와 자리마다의 수단이 정해져 있다.

### Step 3. 수단

[build](steps/40-build.md) 를 연다. 있는 부품(겹쳐 보기, diff, 화면 표시, 결정 블록, 목차)이 맞으면 그것을 쓰고, 없으면 그 페이지 안에 직접 만든다. 수단마다 쓰는 법은 [bottlenecks §수단](catalogs/bottlenecks.md#수단) 에 있다.

- **템플릿의 토큰과 반응형 규칙 위에 짓는다.** `assets/web-report.html` 의 `:root` 변수와 좁은 화면, 인쇄 규칙을 덮어쓰지 않고, 새 부품의 스타일은 그 아래 따로 둔다
- **장치가 쓰는 값은 재료 파일에서 만든다.** 손으로 옮겨 적으면 실제 결과와 어긋난다. -> 핵심 원칙 2, 4
- **조작 장치는 처음 상태만으로도 뜻이 통하게 만든다.** 인쇄와 캡처에는 처음 상태만 남는다
- **비교하는 두 장은 같은 범위, 같은 축척, 같은 데이터로 맞춘다.** 그래야 겹쳐 보기와 차이가 성립한다

끝나면 보고서 폴더의 `index.html` 안에 모든 수단이 있다.

### Step 4. 확인

만든 것을 전부 연다. 이미지는 Read 로, 페이지는 브라우저로 열어 찍은 뒤 Read 로 본다. 확인할 것:

- **첫 화면만 보고 Step 0 의 병목이 풀리나.** 처음 보는 사람의 눈으로 맨 위만 읽고 무엇이 결론인지 말할 수 있는지 본다. 안 되면 순서나 수단이 틀렸다
- 표시가 강조 대상을 정확히 가리키나. 같은 글자의 다른 자리를 물지 않았나. 번호 배지가 내용을 덮지 않았나
- 조작 장치를 실제로 눌러 봤나. 상태마다 화면이 바뀌고 그 값이 재료와 맞나. 콘솔 오류가 없나
- 그림과 캡션이 같은 것을 말하나. "없다"고 쓴 것이 정말 없나(로그인이나 조건 때문에 안 보인 것이면 판정을 뒤집는다)
- 390px 폭에서 표나 그림이 화면 밖으로 나가지 않나

어긋난 것을 고치고 다시 연다. 한 번에 맞는 경우는 드물다. 재료별로 더 볼 것은 그 variants 의 확인 절에 있다. -> 핵심 원칙 6

### Step 5. 내기

[output](steps/60-output.md) 을 따른다.

1. `inline-images.py` 로 `report.html` 한 장으로 묶는다.
2. **빠른 보기**는 파일 경로를 알리고, 사용자가 다른 기기에서 보면 링크로 내보낸다. 대화에는 페이지가 무엇을 보여 주는지 한두 줄만 쓴다. 페이지 내용을 대화에 다시 풀어 쓰지 않는다.
3. **보고**는 넓은 화면, 390px 폭, `check_print.sh` 가 뽑은 인쇄 쪽을 모두 보고, 결정 블록이 있으면 하나 골라 복사해 본다. 파일을 보내거나 링크로 내보내고, 받는 사람이 여는 방식 그대로 열어 확인한다.

끝나면 `report.html` 이 받는 사람이 여는 방식으로 열리고, 보내는 일은 사용자 확인을 기다린다. 건넬 때는 만들면서 바꾼 것과 확인 못 한 항목을 함께 말한다.

## 자주 막히는 곳

| 증상 | 원인과 대응 |
|---|---|
| 페이지를 만들었는데 글로 쓴 것과 다를 바 없다 | 병목을 안 고르고 카드부터 채웠다. Step 0 으로 돌아가 막히는 자리를 고른다 |
| 그림이 많은데 무엇을 보라는지 모른다 | 수단마다 무엇을 보라는 한 줄이 없다. 캡션이나 그림 위 한 줄로 단다 |
| 휴대폰에서 표나 그림이 화면 밖으로 나간다 | 표를 `.tw` 로 안 감쌌거나 인라인 `style` 에 px 폭을 박았다. 템플릿 클래스와 % 폭을 쓴다 |
| 받은 쪽에서 그림이나 장치가 안 뜬다 | CDN 이나 웹 폰트를 불렀다. 코드를 페이지에 넣거나 SVG 로 미리 그린다 |
| 링크로 열면 이미지 몇 장이 빈다 | 간이 서버가 동시 요청을 놓친다. `inline-images.py` 로 파일 하나로 묶는다 |
| 그림이 프레임 안에서 작게 나온다 | 높이 제한에 걸려 축소된 것이다. 세로로 긴 이미지는 좌우 2단 배치로 바꾸면 커진다 |
| 변경이 너무 미묘해 보인다 | 비교 대상을 잘못 골랐다. 목록에서 컬럼명 하나 바뀐 것보다 그 값을 실제로 다루는 화면이나 diff 의 핵심 구간을 보인다 |
| 표가 빽빽해 읽기 어렵다 | 라벨을 왼쪽에 세우고 내용을 오른쪽에 두는 항목 목록으로 바꾼다. 그룹이 있으면 그룹 라벨을 행 왼쪽에 한 번만 둔다 |
| 고칠수록 길어지기만 한다 | 새 절을 만들었으면 그 내용을 담고 있던 기존 서술을 걷어낸다 |

화면을 찍다 막히는 곳은 [screen §자주 막히는 곳](variants/screen.md#자주-막히는-곳) 에 있다.

## 산출

보고서 폴더 하나(`<날짜>-<주제>/`): 고칠 때 쓰는 `index.html`, 재료(`images/raw/`, `data/`, diff 파일), 재료를 다시 만드는 파일(촬영 목록, 잘라 내기 좌표, 값을 페이지로 옮기는 스크립트), 건네는 `report.html`(이미지와 스크립트 포함 한 장). 건넬 때는 만들면서 바꾼 것과 확인 못 한 항목을 함께 말한다.

## 스킬 생태계에서의 위치

- **브라우저 도구** - 이 스킬은 고른 도구로 무엇을 찍어 어떻게 싣는지다. 도구를 고르고 세션을 격리하는 규칙이 환경에 따로 있으면 그것을 따른다
- **문서 스킬** - pptx, docx, 제출용 PDF 처럼 정해진 파일 형식이 필요하면 그 스킬의 몫이다. 이 스킬의 산출은 HTML 한 장이다
- **글 다듬기** - 페이지 문장과 구성을 다듬는 기준이 환경에 있으면 그것을 쓴다. 점검 보고에서 원칙의 출처가 되기도 한다
