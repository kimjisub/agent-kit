# 축 9. 다이어그램: 개선

**로드 시점: 개선 단계에서, 합의된 범위 안에서.** 무엇을 잴지는 `measure.md`, 실제 전후 모양은 `examples.md`.

## 원칙

한 그림에 한 층, 한 독자. 모든 요소에 타입과 한 줄, 모든 관계에 라벨, 모든 그림에 제목과 범례. 색과 선 모양은 범례에 뜻을 적은 것만 쓴다. 그림의 이름은 본문의 이름과 같다.

## 처방

**글로 쓴 흐름은 그린다.** 화살표로 이은 문장은 흐름도, 둘 이상이 부르고 답하는 문장은 순서도(생명선과 메시지), "A 는 B, C 로 나뉜다" 는 들여쓴 나무로 바꾼다. 문장은 그림이 못 말하는 이유 한 줄만 남긴다.

| 전 | 후 |
|---|---|
| "요청은 앱 -> API -> 캐시 -> DB 로 가고, 캐시에 없으면 DB 를 읽는다" | 앱, API, 캐시, DB 의 순서도. 캐시 메시지에 "없음" 을 점선으로 |
| "src 아래 api 와 cache 가 있고 cache 는 새로 생겼다" | 폴더 나무, cache 에 "새로" 꼬리표 |

**층을 가른다.** C4 네 층 중 독자에 맞는 하나만.

| 층 | 독자 | 요소 |
|---|---|---|
| Context | 경영진, 고객, 영업 | 우리 시스템 하나 + 사람 + 외부 시스템 |
| Container | 기술 결정자, 운영 | 배포 단위(앱, DB, 브로커)와 기술 |
| Component | 개발자 | 컨테이너 안의 모듈 |
| Code | 구현자 | 클래스, 함수 (보통 안 그림) |

방향성 문서의 제품 구조도는 Context와 Container 사이다. 제품(Link, Edge, Hub)과 외부(현장 장치, 소비자)를 그리고, Hub 안의 저장소는 한 상자로 접는다.

**요소마다 세 줄.** 이름, 타입, 한 줄 설명. 컨테이너면 기술도.

```
edge["IoT Edge<br/>[소프트웨어, Go]<br/>현장 장치를 수집해 Hub로 전송"]
```

**관계마다 라벨.** 무엇이 흐르는지 또는 무엇을 하는지.

| 전 | 후 |
|---|---|
| `edge --> hub` | `edge -->|"envelope (MQTT QoS1)"| hub` |
| `hub --> app` | `hub -->|"REST"| app` |

**선 모양에 뜻을 하나씩.** 실선은 데이터 흐름, 점선은 제어 명령, 굵은 선은 주 경로. 정했으면 범례에 적고 그림 전체에서 지킨다.

**범례.** mermaid는 범례 노드를 subgraph로 둔다.

```
subgraph legend["범례"]
    l1["실선: 데이터"] -.- l2["점선: 제어 명령"]
end
```

이미지면 그림 모서리에 범례 박스.

**제목.** 그림 위에 "그림 N. <무엇>의 <어느 층>". "그림 1. IoT 플랫폼 제품 구조 (Container)".

**경계를 subgraph로.** 현장 / Hub / 소비자처럼 물리적 또는 소유 경계를 subgraph로 묶는다. 경계가 없는 그림은 상자가 떠다닌다.

**약어를 푼다.** 범례에 "DCU: Data Collection Unit (Edge 박스)". 본문에서 정의했어도 그림은 따로 읽히니 그림 안에.

**색은 보조.** 그룹을 색으로만 나누지 않는다. subgraph 경계와 라벨이 먼저이고 색은 그 위에. 흑백으로 인쇄해 구분되는지 본다.

**선 교차를 줄인다.** 방향(LR 또는 TB)을 바꿔 보고, 교차가 남으면 요소 순서를 바꾸거나 그림을 나눈다.

**요소 15개를 넘으면 나눈다.** Context 한 장 + Container 한 장. 또는 서브시스템별로.

**그림과 본문의 이름을 맞춘다.** 이름을 바꿨으면 그림도 grep해서 바꾼다.

**가져온 그림에는 출처를 붙인다.** 남의 발표자료, 기사, 논문에서 가져온 그림은 그림 바로 아래에 출처 한 줄을 둔다. 본문에 "아래 그림은 OO 발표자료입니다"로 쓰지 않는다. 그림과 출처가 떨어지면 다음 사람이 그 그림만 잘라 다른 문서에 옮긴다. 캡션 형식은 `<만든 곳> <자료 이름>` 한 줄이고, 그림이 여럿이면 전부 같은 문구를 쓴다.

| 전 | 후 |
|---|---|
| (그림만 있음) | 그림 아래 `<발표자> 발표자료` |
| 본문 끝에 "그림 출처: 강연자 제공" 한 번 | 그림마다 캡션 한 줄 |

**그림 안 글은 명사구로.** 요소 설명, 표 칸, 범례, 보기 설명, 그림에 붙는 노트는 명사구로 끝낸다. 그림은 훑어보는 매체라 문장 종결이 있으면 한 칸을 문단처럼 읽게 된다. 노트는 `주제: 내용` 꼴로 쓰면 앞의 주제만 훑어도 무엇에 관한 줄인지 보인다. 질문형 설명("잃으면 되살릴 수 있나")은 그 질문이 다루는 대상을 이름으로 바꾼다. 숫자, 날짜, 고유명사는 그대로 두고, 누가 하는지는 `A 의 B`, `A 가 한 B` 로 남긴다.

| 전 | 후 |
|---|---|
| 잃으면 되살릴 수 있나 (보기 설명) | 저장소별 백업 여부와 복구 가능성 |
| 운영 core 는 HPA 최대치 4개에 붙어 있고 메모리가 목표 80% 를 넘는 87% 다 | 운영 core: HPA 최대치 4개, 메모리 사용률 87% 로 목표 80% 초과 |
| 복구를 해 본 적 없다 (표 칸) | 복구 실행 이력 없음 |
| 사람이 손으로 (범례) | 수동 작업 |

**ERD 는 몇 대 몇을 보이는 그림이다.** 테이블 관계도를 읽는 사람이 찾는 것은 "고객사 하나에 포지션이 여럿인가", "같은 쌍이 두 번 들어갈 수 있는가"다. 컬럼 목록은 스키마 파일이 정본이라 그림에서 뺀다.

- 상자에는 한글 이름과 테이블 이름만 둔다.
- 연결 테이블(두 테이블을 잇기만 하는 것)은 상자로 그리지 않고 N : M 선의 이름으로 접는다. 상자 수가 절반 가까이 준다.
- 선마다 "1 : N", "0..1 : N" 라벨을 달고, 끝에는 갈퀴(여러 행), 막대(하나), 동그라미(없거나 하나)를 둔다. 라벨은 왼쪽(위)에서 오른쪽(아래) 순서로 읽는다고 그림 안 범례에 적고, 세로선의 라벨도 그 순서를 지킨다.
- 자동 배치(graphviz, mermaid erDiagram)는 허브 테이블에 선이 몰려 곡선이 엇갈린다. 상자가 열 개를 넘으면 좌표를 정해 직각선으로 그린다. 여러 곳에 닿는 연결(맥락 연결처럼 셋에 붙는 것)은 버스선 하나로 묶는다.
- 거의 모든 테이블에 붙는 FK(팀, 작성자)는 선을 빼고 캡션에 한 줄로 적는다.
- 그림 밑에 "관계 | 몇 대 몇 | 뜻" 표를 붙인다. 고유 제약(같은 쌍은 한 번), FK 가 비어도 되는지, DB 가 아니라 코드가 막는 규칙은 그림보다 표에서 읽힌다.

| 전 | 후 |
|---|---|
| graphviz 자동 배치, 상자 21개(연결 테이블 8개 포함), 컬럼 목록, 곡선 교차, 범례 없음 | 상자 12개, 연결 테이블은 "N : M 롱리스트" 같은 선 이름, 직각선, 그림 안 범례, 아래에 관계 표 12행 |

## 흔한 실수

- 한 그림에 모든 것을 넣는다. 경영진용 그림에 Postgres 테이블이 있다.
- 화살표를 그리면서 라벨을 미룬다. 나중에 무엇이 흐르는지 본인도 모른다.
- 색을 먼저 칠하고 뜻은 안 적는다.
- mermaid가 알아서 배치한 것을 그대로 둔다. 교차선이 다섯이면 방향을 바꿔 본다.
- 본문에서 이름을 바꾸고 그림은 옛 이름이다.
- 노트와 표 칸만 명사구로 바꾸고 보기 설명, 범례, 머리말 부제, 영역 부제는 문장으로 둔다. 그림 안의 글은 자리를 가리지 않고 전부 같은 규칙이다.
- 명사구로 줄이면서 주어를 버린다. "크롬 확장과 에이전트 저장소가 수집"에서 주어를 빼면 누가 수집하는지 사라진다.

## 검증

- 라벨 없는 화살표 grep이 0인지 본다.
- 요소마다 타입과 설명이 있는지 센다.
- 범례 subgraph가 있고 그림에 쓴 선 모양이 전부 들어 있는지 본다.
- 그림 안 이름이 본문에 전부 있는지 grep한다.
- 렌더해서 교차선과 겹침을 눈으로 본다.
