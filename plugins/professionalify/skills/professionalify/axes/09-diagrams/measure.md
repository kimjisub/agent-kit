# 축 9. 다이어그램: 측정

**로드 시점: 측정과 검증 단계에서.** 켜지는 조건과 왜는 `axis.md`, 고치는 법은 `improve.md`.

## 신호

| 신호 | 어떻게 보이나 | 심각도 |
|---|---|---|
| 타입 없는 요소 | 상자에 이름만. 사람인지 시스템인지 컨테이너인지 모름 | S1 |
| 설명 없는 요소 | "Hub"만 있고 무엇을 하는지 없음 | S2 |
| 라벨 없는 관계 | 화살표에 글자 없음. 무엇이 흐르는지 모름 | S1 |
| 화살표 뜻 혼용 | 같은 실선이 호출, 데이터 흐름, 의존을 번갈아 뜻함 | S1 |
| 범례 부재 | 색, 점선, 굵기, 도형 모양의 뜻이 그림 어디에도 없음 | S1 |
| 층 혼재 | 한 그림에 "고객사"(Context)와 "Postgres 테이블"(Code)이 같이 | S1 |
| 제목 부재 | 그림이 무엇의 어느 층인지 없음 | S2 |
| 기술 미표기 | 컨테이너에 무엇으로 만들었는지(Go, NestJS, Postgres) 없음 | S2 (기술 독자) |
| 약어 미설명 | DCU, UNS, MDL이 범례 없이 | S2 |
| 색만으로 구분 | 색을 빼면 그룹이 사라짐 | S2 |
| 교차하는 선 | 선이 서로 넘어가 어디로 가는지 따라가야 함 | S3 |
| 요소 과다 | 한 그림에 상자 15개 이상 | S2 |
| 그림과 본문 불일치 | 그림의 이름과 본문의 이름이 다름 (Core vs Hub) | S1 |
| 출처 미표기 | 남의 자료(발표자료, 기사, 논문, 고객사 문서)에서 가져온 그림에 어디서 왔는지가 없음 | S2 |
| 문장형 항목 | 요소 설명, 노트, 표 칸, 범례, 보기 설명이 서술어(-다, -한다, -없다)나 의문형(-나, -까)으로 끝남. 그림 안 글이 본문 문단처럼 읽혀 훑어볼 수 없음 | S2 |
| ERD 의 관계 수가 묻힘 | 테이블 그림에 컬럼을 늘어놓거나 연결 테이블까지 상자로 그려 상자가 15개를 넘고, 자동 배치 곡선이 엇갈려 "1 : N" 라벨이 어느 선의 것인지 모름. 갈퀴, 막대, 동그라미의 뜻과 라벨 읽는 방향이 그림 안에 없음 | S1 |
| 글로 쓴 흐름과 계층 | 그림 없이 한 문장에 화살표가 둘 이상("앱 -> API -> 캐시 -> DB"), "먼저 ... 그다음 ..." 이 셋 넘게, "A 는 B, C, D 로 나뉘고 B 는 ..." 가 문단으로. 읽는 사람이 상자와 선을 머리로 그린다 | S2 |

## 측정 방법

mermaid는 텍스트라 grep이 된다.

```bash
# mermaid 블록 수
grep -c '```mermaid' <file>
# 라벨 없는 화살표 (--> 뒤에 | 가 없음)
awk '/```mermaid/{f=1;next} /```/{f=0} f' <file> | grep -E '(-->|==>|-\.->)' | grep -v '|' 
# subgraph 수 (경계 표시)
awk '/```mermaid/{f=1;next} /```/{f=0} f' <file> | grep -c 'subgraph'
# 노드 수
awk '/```mermaid/{f=1;next} /```/{f=0} f' <file> | grep -oE '^\s+[a-zA-Z0-9_]+\[' | wc -l
# 문장형 항목: 코드로 그린 그림(React Flow, D3 등)의 따옴표 안 한글 중 서술어나 의문형으로 끝나는 것
grep -noE "['\"][^'\"]*[가-힣][^'\"]*(다|나|까)['\"]" <그림 소스 파일들>
# 그림 안 이름이 본문에 있는가
for n in $(awk '/```mermaid/{f=1;next} /```/{f=0} f' <file> | grep -oE '"[^"]+"' | tr -d '"' | head -20); do grep -q "$n" <file> || echo "본문에 없음: $n"; done
# 그림을 읽는 문장: 닫는 펜스 다음 비어 있지 않은 줄
grep -nA2 '^```$' <file> | grep -B1 -A1 mermaid | head
```

닫는 펜스 다음 줄은 awk로 잡기 어렵다(펜스가 열고 닫는 데 같은 문자열). 위 grep으로 위치만 찾고 눈으로 본다. 라벨 없는 엣지 수와 전체 엣지 수를 함께 적는다("10개 중 7개 라벨 없음").

이미지 다이어그램은 눈으로 본다.
- 우리가 그린 그림인가, 가져온 그림인가. 가져온 것이면 그림마다 출처 한 줄이 붙어 있는가
- 모든 상자에 이름 + 타입 + 한 줄이 있는가
- 모든 선에 라벨이 있는가, 선 종류(실선, 점선, 굵기)가 둘 이상이면 범례가 있는가
- 이 그림의 독자가 누구이고 그 층(Context / Container / Component)만 있는가
- 그림을 흑백으로 인쇄해도 구분되는가
- 그림 없이 본문만 읽어도 같은 내용이 있는가 (있으면 그림이 부속, 없으면 그림이 정본이라 더 엄격히)

## 채점 (0~20)

steps/scoring.md의 "디테일 정확성"에 들어간다.

| 점수 | 기준 |
|---:|---|
| 20 | 모든 요소에 타입과 설명, 모든 관계에 라벨, 범례와 제목, 한 층 |
| 15 | 설명 누락 1~2개 또는 범례 일부 |
| 10 | 라벨 없는 화살표 있음 또는 층 혼재 |
| 5 | 범례 없고 화살표 뜻이 섞임 |
| 0 | 그림이 본문과 다른 이름을 씀 |

## 오탐 주의

- 문장형 항목 검사를 조사와 연결어미 끝(-로, -과, -서, -가)까지 넓히면 `경로`, `결과`, `문서`, `평가` 같은 명사가 걸린다. 서술어와 의문형 grep 에도 `하나` 처럼 '나'로 끝나는 명사가 걸린다. 기계로는 서술어와 의문형만 세고, 나머지는 걸린 줄을 전부 눈으로 읽어 가른다. `필요`, `없음`, `불가`, `미확인` 으로 끝나는 것은 명사구다.

- 스케치 단계 화이트보드 사진은 이 축 대상이 아니다. 문서에 넣기로 한 그림만.
- 시퀀스 다이어그램은 화살표 라벨이 메시지 이름이라 "라벨 없음"이 거의 안 난다. 대신 참여자 타입을 본다.
- 한 층에 요소가 15개를 넘는 것이 실제 구조면 그림을 나눈다. 요소 수 자체는 위반이 아니다.
- mermaid의 `-.->`(점선)와 `==>`(굵은 선)는 문법이 뜻을 갖지 않는다. 범례가 뜻을 준다.
