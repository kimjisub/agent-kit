# 축 16. 기술 문서

## 정의

개발자와 운영자가 읽는 문서(README, API 문서, 설치 가이드, 설계 문서, 런북, CLI 도움말)가 독자의 상황에 맞는 종류로 쓰였는가. Diátaxis의 네 종류(tutorial: 배우기, how-to: 일 끝내기, reference: 찾아보기, explanation: 이해하기)를 섞지 않았는가, 2인칭 현재형 능동태인가, 코드 예시가 실행되는가, 전제와 버전이 적혀 있는가.

## 켜지는 조건

README, API 문서, 설치와 배포 가이드, 런북, 설계 문서(plan, ADR), CLI `--help`, 스킬 문서를 쓰거나 고칠 때 켠다. 제안서, 기획서, 슬라이드는 끈다. 코드 주석은 이 축의 대상이 아니다(코드 리뷰의 영역).

## 왜

Diátaxis는 문서가 실패하는 이유를 "네 가지 다른 필요를 한 문서에 섞기 때문"이라고 진단한다. 배우려는 사람에게 reference를 주면 어디서 시작할지 모르고, 일을 끝내려는 사람에게 tutorial을 주면 짜증이 난다. 각 종류는 목적, 어투, 구조가 다르다. tutorial은 "따라 하면 된다"이고 how-to는 "이 목표면 이렇게", reference는 "사실만 정확하게", explanation은 "왜 이렇게 됐나". Google 개발자 문서 스타일은 2인칭("you"), 현재형, 능동태, 접근성과 지역화를 위한 평이한 문장을 요구한다. 코드 예시가 안 돌면 문서 전체가 의심받고, 전제(버전, OS, 권한)가 없으면 첫 명령에서 막힌다.

출처: Daniele Procida, Diátaxis (diataxis.fr). Google developer documentation style guide(highlights). Write the Docs 커뮤니티 관행. `skill-authoring` 스킬(이 키트)(스킬 문서의 골격과 로드 시점).

## 경계

- 스킬 문서(SKILL.md)의 골격, 파일 분할, 검증은 `skill-authoring`이 정본이다. 여기는 그 문서도 기술 문서로서 네 종류 중 무엇인지, 어투가 맞는지만.
- 논리 구조(결론 먼저)는 축 4. reference는 결론이 없으니 축 4의 두괄식 검사만 끈다. 헤더 형태, 중복, 위계는 문서 종류와 무관하게 축 4에서 본다.
- 화면 문구와 CLI 출력 메시지는 축 12. `--help`는 여기와 축 12가 같이.
- 다이어그램은 축 9, 표는 축 7.

## 읽기 순서

`measure.md`의 종류 판정(이 문서는 넷 중 무엇인가, 섞였는가)을 먼저 한다. 개선은 `improve.md`의 종류별 골격과 문체 규칙. 실제 README와 런북 전/후는 `examples.md`.
