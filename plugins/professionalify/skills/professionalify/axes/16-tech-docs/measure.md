# 축 16. 기술 문서: 측정

**로드 시점: 측정과 검증 단계에서.** 켜지는 조건과 왜는 `axis.md`, 고치는 법은 `improve.md`.

## 신호

| 신호 | 어떻게 보이나 | 심각도 |
|---|---|---|
| 종류 혼재 | 설치 가이드(how-to) 중간에 아키텍처 설명(explanation)이 세 문단 | S1 |
| tutorial에 선택지 | "A 또는 B를 고르세요". 배우는 사람은 고를 수 없다 | S1 |
| how-to에 배경 설명 | 목표를 향한 단계 사이에 "왜 이렇게 설계됐냐면" | S2 |
| reference에 의견 | "권장합니다", "보통 이렇게 씁니다"가 사실 목록에 섞임 | S2 |
| explanation에 절차 | "왜"를 설명하다 명령어 목록으로 빠짐 | S2 |
| 전제 부재 | 버전, OS, 권한, 선행 설치가 첫 명령 앞에 없음 | S1 |
| 코드 예시 미실행 | 복사해서 돌리면 안 됨. 플레이스홀더가 표시 없이 | S1 |
| 3인칭, 수동태 | "사용자는 ~할 수 있다", "파일이 생성된다" | S2 |
| 미래형 | "~될 것입니다" (현재형이 맞음) | S3 |
| 결과 없음 | 명령 뒤에 무엇이 보여야 성공인지 없음 | S1 |
| 오류 대응 없음 | 흔한 실패와 그때 할 일이 없음 (how-to, tutorial) | S2 |
| 시작점 없음 | README에 "5분 안에 돌려 보기"가 없음 | S2 |
| 갱신일과 버전 없음 | 언제 어느 버전 기준인지 없음 | S2 |
| 링크 깨짐 | 상대 링크와 앵커가 죽어 있음 | S1 |
| 용어 불일치 | 같은 것을 "박스", "Edge", "DCU"로 번갈아 | S2 |

## 측정 방법

**종류 판정.** 문서(또는 절)마다 넷 중 무엇인지 적는다.

| 종류 | 독자의 상황 | 판정 질문 |
|---|---|---|
| tutorial | 처음이고 배우고 싶다 | "따라 하면 끝에 무엇이 만들어지는가"가 첫 줄에 있는가 |
| how-to | 목표가 있고 끝내고 싶다 | 제목이 "~하는 법"이고 단계가 번호인가 |
| reference | 일하는 중이고 찾아보고 싶다 | 사실만, 일관된 구조, 완전한 목록인가 |
| explanation | 이해하고 싶다 | "왜"에 답하고 절차와 명령이 없는가 |

한 문서에 둘 이상이면 어느 절이 어느 종류인지 표시하고, 섞인 절을 센다.

```bash
# 절 제목에서 종류 추정
grep -nE '^#+ ' <file> | grep -iE "시작|따라|튜토리얼|getting started|tutorial"     # tutorial
grep -nE '^#+ ' <file> | grep -iE "하는 법|how to|설치|배포|설정하기"                  # how-to
grep -nE '^#+ ' <file> | grep -iE "API|옵션|명령어|reference|파라미터|스키마"          # reference
grep -nE '^#+ ' <file> | grep -iE "왜|배경|설계|원리|architecture|explanation"        # explanation
# 3인칭과 수동태
grep -cE "사용자는|사용자가|개발자는|될 수 있|생성된다|처리된다|실행된다" <file>
# 미래형
grep -cE "될 것입니다|할 것입니다|될 예정" <file>
# 플레이스홀더 표시
grep -oE "<[a-z_-]+>|\{[a-z_-]+\}|YOUR_[A-Z_]+" <file> | sort -u
# 전제 절
grep -nE '^#+ .*(전제|요구 사항|Prerequisites|Requirements|사전)' <file>
# 버전과 갱신일
grep -nE "v[0-9]+\.[0-9]+|20[0-9]{2}-[0-9]{2}-[0-9]{2}|버전" <file> | head -3
```

**코드 예시 실행.** 예시 블록을 실제로 돌려 본다. 플레이스홀더를 채웠을 때 성공하는가, 결과가 문서와 같은가.

```bash
# 링크 검사 (skill-authoring의 스크립트)
python3 <skill-authoring 경로>/scripts/check-links.py <문서 폴더>
```

**용어.** 같은 개념의 이름을 뽑아 하나인지 본다.

## 채점 (0~20)

steps/scoring.md의 "문서 목적과 완결성"과 "디테일 정확성"에 나눠 들어간다.

| 점수 | 기준 |
|---:|---|
| 20 | 종류 하나(또는 절마다 명확), 전제와 버전, 예시 전부 실행, 2인칭 현재형, 링크 0 결함 |
| 15 | 문체 이탈 몇 건 |
| 10 | 종류 혼재 절 있음 또는 전제 부재 |
| 5 | 예시가 안 돌아감 |
| 0 | 독자가 첫 명령에서 막힘 |

## 오탐 주의

- 미래형 grep에 "됩니다"를 넣지 않는다. "저장됩니다"는 현재형 정중체라 전부 걸린다. 2026-09-18 실측 전 패턴에 들어 있어 뺐다.
- "될 수 있"은 3인칭 수동이 아니라 가능 표현일 때가 많다("두 방식 다 될 수 있습니다"). 걸린 줄을 읽고 주어가 "사용자는"인 것만 센다.

- README는 관례상 네 종류가 한 파일에 짧게 다 있다. 절마다 종류가 갈려 있으면 된다. 길어지면 파일로 가른다.
- 설계 문서(plan, ADR)는 explanation이고 절차가 없는 것이 정상이다.
- reference의 "권장" 표기는 기본값 설명이면 된다("기본값은 8883입니다"). 의견("8883을 쓰는 것이 좋습니다")만 문제.
- 스킬 문서의 골격은 `skill-authoring`이 정하니 그 규약과 충돌하면 그쪽이 이긴다.
