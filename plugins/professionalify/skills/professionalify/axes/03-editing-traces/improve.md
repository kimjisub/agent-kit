# 축 3. 편집 흔적: 개선

**로드 시점: 개선 단계에서, 합의된 범위 안에서.** 무엇을 잴지는 `measure.md`, 실제 전후 모양은 `examples.md`.

## 원칙

수정은 덧붙이기가 아니라 최종 상태로 덮어쓰기다. 변경 이력은 문서가 아니라 git, PR, 대화에 산다. 원인이 생성 단계에 있으므로(수정을 대화 턴으로 취급, 변경을 증명하려는 충동, 국소 편집, 손실 회피) 사후 청소보다 고치는 순간 최종형으로 쓰는 것이 답이다. 코드에서 지운 코드를 주석으로 남기지 않는 규칙의 산문판이다.

## 처방

**5단계.**

1. 고칠 영역 전체를 읽는다. 흔적은 지점만 보고 손댈 때 생긴다. 문단, 절, 참조 사슬을 통째로 본다.
2. 최종 상태를 먼저 정한다. "오늘 이걸 처음부터 쓴다면, 최종 결정을 아는 채로 뭐라고 쓸까?" 그것을 쓴다.
3. 주석 말고 덮어쓴다. 옛 내용을 최종형으로 교체하고, 무엇이 바뀌었는지를 산출물 안에 표시하지 않는다.
4. 이력은 문서 밖으로. 변경 추적은 git diff, PR, 대화의 몫이다.
5. 처음 읽는 사람처럼 다시 읽는다. 수정된 적 있다는 티가 나면 흔적이 남은 것이다.

**유형별.**

| 유형 | 흔적 | 최종 상태 |
|---|---|---|
| 1 삭제 메모 | `~~기존 안~~ (삭제)` | 그냥 지운다. 있었던 적이 없는 것처럼 읽힌다 |
| 2 변경 내역 | `v2에서 추가:` | 본문은 현재 상태만. 이력은 CHANGELOG, frontmatter, 커밋 메시지로 |
| 3 병치 | `기존에는 5명이었으나 이제 3명이다` | `3명이다`. 대비는 그 대비 자체가 정보일 때만 |
| 4 작업 보고 | `요청하신 대로 반영했습니다` | 문서에는 없다. 대화나 PR에서 말한다 |
| 5 화해 잔여물 | `(확정)`, `TODO` 곳곳에 | 해결한다. 채우거나 자른다. 진짜 미정이면 정해진 한 곳에 `미정` 하나 |
| 6 안 읽고 쌓은 중복 | "추가 분석" 절 신설 | 이미 어디 있는지 먼저 찾아 그 자리에 통합하고 낡은 원본은 지운다 |
| 7 포맷 부스러기 | 고아 헤더, 반쯤 바뀐 참조 | 편집한 영역 전체를 다시 읽어 한 덩어리로 흐르는지 본다 |

**"빼라"는 지시.** 그 대상을 지우라는 뜻이다. 뺀 이유를 남기고 싶으면 답변에 쓴다. "A 대신 B"는 A를 지우고 B를 넣으라는 뜻이다. 둘 다 두고 "A는 안 쓴다"를 덧붙이지 않는다.

**새 절을 만들었으면** 그 내용을 담고 있던 기존 서술을 걷어낸다. 고칠수록 분량이 늘기만 하면 무엇을 지웠어야 했는지 되짚는다.

## 흔한 실수

- 이름을 바꾸면서(Core -> Hub) 옛 이름을 "(구 Core)"로 본문 곳곳에 남긴다. 이름 표 한 곳에만 둔다.
- 절을 재배열한 뒤 "위에서 말한 대로"가 아래를 가리키게 된다.
- 문서 끝에 "변경 사항 요약" 절을 만든다. 그것은 PR 설명이다.
- 여러 번 고치면서 "최신 버전"이 어느 것인지 문서 안에서 갈린다.

## 검증

- `measure.md`의 grep 7종을 다시 돌려 전부 0인지 본다.
- 편집한 절을 처음부터 끝까지 한 번에 읽는다. 앞뒤 절과 이어지는지 본다.
- 이름이나 경로를 바꿨으면 옛 이름을 문서 전체에서 grep한다.
