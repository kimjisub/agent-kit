# 축 3. 편집 흔적: 사례

**로드 시점: 개선 중 처방의 실제 모양이 필요할 때.** 규칙은 `improve.md`가 정본이고 여기는 사례만.

## 우리 사례

### 이름 변경 뒤 옛 이름 (2026-09-18, IoT 제품 방향성 문서)

Core -> Hub, OS -> Edge로 이름을 바꾸면서 본문 전체를 치환하고, 옛 이름은 6.5절 이름 표의 "이전 이름" 열 한 곳에만 두었다. `grep -c "Core"`가 1이 되는 것으로 확인했다. 본문 곳곳에 "(구 Core)"를 남기면 읽는 사람이 두 이름을 계속 대응시켜야 한다.

### 절 재배열 뒤 참조 (같은 문서)

전략을 위로 기술을 아래로 옮기면서 "근거는 13절에 있습니다" 같은 참조가 12곳이었다. 재배열 뒤 전부 다시 맞추고, 문서 상단에 "1절부터 5절이 전략, 6절부터 8절이 제품 정의, 9절부터 12절이 기술 설계"를 한 줄로 선언했다. 반쯤 바뀐 참조가 7유형이다.

### 수정 작업 보고 (이 스킬의 이전 버전)

전: SKILL.md 3단계 목록 앞에 "가장 자주 위반되는 5가지만 여기 둔다"라고 쓰고 여섯 번째를 추가한 뒤 숫자를 안 고쳤다.
후: "6가지만". 작은 것이지만 읽는 사람은 다섯을 세다 여섯을 만난다.

### 새 절을 만들고 옛 서술을 안 걷은 것 (같은 문서 초안)

8절 "설계 제약"을 새로 쓰면서 6.2절의 "런타임 하나 = 테넌시 하나"와 11.1절의 "Edge가 세 번째 복제본"을 8절에서 다시 풀었다. 세 곳에 같은 문장이 생겼다. 8절은 제약 네 문단만 남기고 상세는 해당 절로 돌려보냈다.

## 모범 원본

- git의 커밋 메시지와 PR 설명. 변경 이력이 살 자리가 문서 밖에 이미 있다는 증거다.
- CHANGELOG 형식(Keep a Changelog). 대비가 콘텐츠인 문서는 이렇게 따로 둔다.

## 반례

- "빼라"는 지시에 대상을 지우고 "(삭제됨)"을 남긴 것. 빼라는 지우라는 뜻이다. 이유는 답변에 쓴다.
- "A 대신 B"에 둘 다 두고 "A는 안 쓴다"를 덧붙인 것. A를 지우고 B를 넣으라는 뜻이다.
- 문서 끝에 "변경 사항 요약" 절을 만든 것. 그것은 PR 설명이다.
