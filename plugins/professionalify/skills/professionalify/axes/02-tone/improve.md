# 축 2. 톤과 디테일: 개선

**로드 시점: 개선 단계에서, 합의된 범위 안에서.** 무엇을 잴지는 `measure.md`, 실제 전후 모양은 `examples.md`.

## 원칙

정중한 격식에 자연스러운 흐름. "사람이 쓴 것처럼"을 구어체로 직역하지 않는다. 원본 필자의 톤(매우 격식이든 캐주얼이든)을 평준화하지 않고, 한 문서 안에서만 일관되게 맞춘다. SLA와 계약서에 들어갈 수 있는 표현은 한 단계 보수적으로.

## 처방

**대등한 상대에게는 부탁과 함께 정하기로.** 외주 디자이너, 협력사, 파트너처럼 계약상 대등한 상대에게 보내는 문서는 의무를 바람으로, 허락을 권유로, 결재를 함께 정하기로 바꾼다. 계약상 의무(사용 전 공유 등)도 내용은 그대로 두고 어투만 바꾼다.

| 전 | 후 |
|---|---|
| 유료 폰트는 쓰기 전에 공유하고 확인받기 | 꼭 맞는 유료 폰트가 있다면 사용하시기 전에 가격과 라이선스 범위를 알려 주세요. 함께 보고 정하겠습니다 |
| 16px에서도 형태를 알아볼 수 있어야 합니다 | 16px에서도 형태가 알아보이도록 부탁드립니다 |
| 근거가 있으면 벗어나도 됩니다 | 더 맞는 방향이 있다면 얼마든지 벗어나셔도 좋습니다 |
| 원본으로 주세요 | 원본이면 좋겠습니다 |

**격조와 구어의 적정선.**

| 너무 격식 | 너무 구어 | 적정 |
|---|---|---|
| 본 제안은 ~ 위함입니다 | ~ 들여다봤습니다 | 본 제안서는 ~ 회신입니다 |
| ~할 수 있도록 노력하겠습니다 | ~ 거의 정리됐고 | 검토했습니다 / 확인했습니다 |
| ~를 통해 가능하게 합니다 | ~ 잡는 데 집중합니다 | 기술 리스크가 낮다고 판단됩니다 |
| ~하겠사오니 | ~ 따라가겠습니다 | ~를 따릅니다 |

**내부 조어는 무엇을 하겠다는 것인지로 바꾼다.** 우리 문서에서 정의한 이름은 그 문서를 읽은 사람에게만 통한다. 이름을 풀어 쓰는 것이 아니라 **행동으로** 바꾼다 — "프로브를 돌립니다"는 "프로필 판정 절차를 돌립니다"가 아니라 "후보 두 분을 보여드릴 테니 맞는지 봐주시겠어요"다. 이름을 꼭 써야 하면 그 자리에서 한 번 풀어 쓰고("프로필 전체를 읽는 단계(정독)") 다음부터 짧게 쓴다.

**평가 문서는 판단하는 사람의 말로, 구현 대응은 한 곳에.** 항목을 「무엇을 했나」로 쓴다. "게이트 축 합의 전 intent Write 0건"이 아니라 "핵심 판단 다섯에 컨설턴트가 동의하기 전에는 재정의 문서를 만들지 않았다". 확인할 기록도 "대화", "작업 기록", "검색 계획"처럼 쉬운 이름으로 쓰고, 그 이름이 어느 파일인지는 채점하는 사람용 문서 한 곳에 목록으로 둔다. 금지어를 예로 들어야 하는 항목(「쉬운 말」)만 구현 용어를 그대로 쓴다.

**대상은 읽는 사람이 부르는 이름으로 부른다.** 묶음 이름을 지을 때 그 안에 든 것이 실제로 무엇인지 먼저 본다. 구독해서 쓰는 SaaS, API, 폰트 라이선스를 모은 절은 「거래처」가 아니라 「외부 서비스」다. 「거래처」는 회계와 영업에서 물건과 돈이 오가는 상대를 부르는 말이라, 개발 인수인계서에서 읽으면 계약이나 매출 이야기로 먼저 읽힌다. 묶음 이름을 바꿨으면 절 제목, 표 머리, 본문 문장, 목차, 다른 문서의 참조까지 같은 말로 맞춘다.

**번호 식별자는 떼고 이름으로 부른다.** 항목마다 겹치지 않는 짧은 이름을 붙이고, 다른 자리에서 부를 때는 「」로 그 이름을 쓴다. "R65 가 실패다"가 아니라 "「전략을 줄이지 않음」이 실패다". 이름이 겹치면 번호를 붙이지 말고 이름을 고친다.

**막는 자리는 정본 한 곳이다.** 용어 표는 문체 규칙에 두고, 그 용어가 정의되는 자리마다 "이 말은 독자에게 쓰지 마라" 주석을 달지 않는다. 규칙이 두 곳이 되면 어느 것이 정본인지 사라지고, 용어가 늘 때마다 주석도 함께 늘어난다.

**진짜 발생지는 템플릿이다.** 보고 서식·진행 표시·상태 문구에 내부어가 박혀 있으면 문체 규칙만으로는 안 막힌다 — 쓰는 쪽이 서식을 그대로 채우기 때문이다. 표를 고쳤으면 **서식도 함께 훑는다.**

**사람은 소개하는 곳에서 한 번 성과 이름을 쓰고, 나머지는 "이름+님"으로 부른다.** 사람 소개 표나 첫 등장처럼 누구인지 선언하는 자리에만 "홍길동"이라고 쓰고, 본문, 표 칸, 괄호 속 출처 표기는 모두 "길동님"으로 맞춘다. 소개 표에 없는 사람은 처음 나올 때만 "김철수님"처럼 성까지 쓴다. 필자 본인의 이름은 이 규칙에서 뺀다. 바꿀 때 조사를 함께 본다. 모음으로 끝나는 이름에 "님"이 붙으면 받침이 생겨 "민수가"는 "민수님이", "민수와"는 "민수님과"가 된다. 계정과 코드 표기(`gildong@`, `honggildong`)는 바꾸지 않는다.

**작성자가 아는 사실은 작성자의 시점으로 직접 쓴다.** 인수인계서·경험담·업무 설명을 편집할 때, 편집자가 자료를 읽었다는 사실을 본문의 화자로 바꾸지 않는다. "ERP 실무는 길동님이 이어받는 것으로 기록돼 있고" -> "ERP 실무는 길동님이 이어받고". 작성자가 직접 수행한 일, 알고 있는 역할 분담, 확정한 합의에 “기록상”, “~로 보인다”를 덧붙이지 않는다. 시점에 따라 달라지는 정보는 “문서에 기록된 상태” 대신 “2026-09-23 기준”처럼 확인일을 붙인다. 타인의 기록을 인용하는 문장과 실제 미확인 사실은 출처·유보를 유지하며, 편집자의 추측을 작성자의 확정 사실로 바꾸지 않는다. 한 문장을 지적받으면 역할·연혁·합의·현황을 설명하는 다른 문장도 같은 원인으로 검사한다.

**종결어미.** 메일과 공문은 "~합니다 / ~드립니다 / ~부탁드립니다". 제안서와 보고서 본문은 개조식 "~함 / ~임"이 표준이다(축 14). 한 문서에 섞지 않는다.

**과장을 중립으로.**

| 과장 | 중립 |
|---|---|
| 운영 영향 0 / 완전 독립 | 운영 시스템 직접 변경 없음 / 영향 최소화 |
| 100% 보장 | 보장합니다 / 책임집니다 |
| 절대 안전 | 안전 / 안전 운영 |
| 모든 리스크 해결 | 핵심 리스크 해소 |
| 완벽한 솔루션 | (뺀다) |
| 즉시 대응 | 신속 대응 / 영업일 내 대응 |

**약어.** 첫 사용에 한글로 풀고 괄호에 약어: "본 계약 합의서(SOW)". 이후는 하나로 통일. 기술 기업 대상이면 약어 그대로 써도 되지만 첫 1회는 푼다. 한국어 용어가 있으면 한국어 우선.

| 약어 | 한글 |
|---|---|
| SOW | 본 계약 합의서 / 기술 협의서 |
| MoU | 양해각서 |
| NDA | 비밀유지 합의 |
| RFP | 제안 요청서 |
| KPI | 핵심 성과 지표 |
| PoC, API | 그대로 (산업 표준) |

**기호.** `§3-4 참조` -> "위 3-4 항목 참조". `★★★ 권장` -> "권장드립니다". `✓` -> 비교 표 1열 말고는 뺀다. `→` -> 표와 다이어그램에서만, 본문은 동사("로 이어집니다") 또는 `->`. 이모지 -> 뺀다.

**법인격과 약칭.** 도입부에서 모든 당사자의 정식 법인격을 한 번 쓰고 이하 역할 호칭으로 통일한다.

> 본 문서는 (주)A사(이하 "고객사")가 발주하는 C사 공정 데이터 연동 PoC에 대해 B 유한책임회사(이하 "개발사")가 수행 범위와 비용을 제안하는 자료임.

| 관계 | 호칭 쌍 |
|---|---|
| 발주-수행 (일반 SI) | 고객사 / 개발사, 고객사 / 수행사 |
| 정부 과제 | 발주처 / 주관사, 발주처 / 수행기관 |
| 컨소시엄 | 주관사 / 참여사 / 위탁기관 |
| 단순 거래 | 공급사 / 수요사 |
| 위탁 개발 | 위탁사 / 수탁사 |

풀 법인격은 표지, 계약서 제목과 서명란, 법적 책임 조항, 인보이스에 남긴다. 영어는 `hereinafter, "Customer"` 패턴이 같다. 법인격을 모르면 약식으로 쓰고 "정식 계약 단계에서 확정함" 한 줄을 둔다.

**시간.** 날짜 `2026-05-11` 또는 `2026년 5월 11일` 중 하나로 통일. 기간 `2026.06 ~ 2026.09`. 시각 `14:30`. 마감은 "5월 말까지"가 아니라 `2026-05-31까지`.

**숫자.** 금액 `1,000만 원` 또는 `10,000,000원`. VAT는 `공급가 1,000만 원 (VAT 포함 1,100만 원)`. 백분율 `10%`. 범위 `5~10건`.

**자기 PR을 사실 진술로.** "풍부한 경험을 바탕으로" -> "시찰(2026-04-24)과 현장 시스템 사본 분석으로 ~를 확인했습니다". 자랑하지 말고 한 일을 기록한다.

**요구는 단정한다.** 필수와 선택을 가르고, 필수는 흐리지 않는다. 전: "키컬러와 보조색, 무채색. 어렵다면 키컬러만이라도". 후: "키컬러와 함께 쓸 보조색, 무채색을 부탁드립니다". 정말 선택이면 "선택"이라고 따로 적는다.

**클로징을 행동 유도로.** 마지막 줄에 누구에게, 무엇을, 언제까지.

| 전 | 후 |
|---|---|
| 감사합니다. | 회신은 홍길동에게 부탁드립니다. 2026-06-30까지 의견 주시면 정식 견적서로 이어 정리드리겠습니다. |
| 검토 후 의견 주시면 감사하겠습니다. | 현장 일정 조율을 위해 2026-05-31까지 시나리오 선택 회신 부탁드립니다. |
| 언제든 연락 주세요. | 본 견적의 유효 기간은 2026-06-30입니다. |
| (계약 뒤 작업자에게 건네는 의뢰서) 로고가 마무리되면 이어서 할 수 있는 작업을 알려 주세요. 후속 계약으로 진행할 수 있습니다. | 작업하시면서 조율이 필요한 부분은 언제든 편하게 말씀해 주세요. 함께 만들어 주셔서 감사합니다. |

행동 유도 클로징은 결정이나 회신을 받아야 하는 문서의 규칙이다. 계약이 끝난 상대에게 건네는 의뢰서는 할 일이 이미 계약에 있으니, 끝을 새 사업 이야기로 열지 않고 조율 환영과 감사로 닫는다.

**필자를 주어로 회고하지 않고 받는 사람의 일로 쓴다.** 연혁과 출처처럼 필자가 사실의 주어여야 하는 자리가 아니면, 필자 이름 주어 문장을 받는 사람이 이어받는 일로 바꾼다.

- 전: "엔지니어 온보딩 가이드에 \"인프라 관리자\"로 적힌 자리(계정 발급, 서버 접근)도 홍길동이었습니다."
- 후: "엔지니어 온보딩 가이드에 \"인프라 관리자\"로 적힌 자리(계정 발급, 서버 접근)도 이번에 이어받는 일입니다."

**이력서와 경력기술서도 본문은 ~합니다체다.** 이력서는 ~했다체나 명사형으로 쓰는 관행이 있지만, 사용자가 산출물 어체를 ~합니다체로 정해 두었으면 이력서도 본문 완결 문장을 ~합니다체로 통일한다. 표 칸, 숫자 칸, 기술 목록처럼 문장이 아닌 자리는 명사구로 둔다.

## 흔한 실수

- 격식을 빼려다 구어체로 떨어뜨린다. "들여다봤습니다"는 회사명이 들어가는 문서에서 어색하다.
- 인용문 안의 어조까지 바꾼다.
- 약칭을 정의해 놓고 표지와 서명란까지 약칭으로 쓴다.
- 내부 조어를 용어 표에만 넣고 그것을 찍어 내는 서식은 안 고친다. 표는 깨끗한데 출력에는 그대로 나온다.
- 과장을 중립으로 바꾸면서 약속 자체를 지운다. "보장합니다"는 남긴다.
- "감사합니다"를 지우고 행동 유도를 안 넣는다.

## 검증

- `measure.md`의 grep을 다시 돌린다. 종결어미 혼용, 과장, 기호, 모호한 마감이 0인지 본다.
- 도입부 약칭 정의와 마지막 줄 행동 유도를 눈으로 확인한다.
- 시간과 숫자 표기가 한 형식인지 본다.


### 표 칸과 괄호까지 한 어체로

외부에 나가거나 남이 읽는 문서는 본문, 표 칸, 목록, 괄호 속 보충 설명을 모두 "~합니다", "~입니다"로 맞춘다. 명사구로 끝나는 설명("원천 기록", "기본 경로", "회사 Google 로그인")은 그대로 둔다. 문장 끝을 바꾸는 일은 `scripts/to-hapnida.py` 로 하고, 바꾼 쌍 목록을 전부 읽는다. "~마다", "~보다"처럼 다로 끝나는 조사와, 받침 없는 명사 뒤 "~다"(서버다 -> 서버입니다)를 잘못 바꾸기 쉽다.

| 전 | 후 |
|---|---|
| 배포 때 infrastructure 에 태그를 커밋한다 | 배포 때 infrastructure 에 태그를 커밋합니다 |
| (두 사본이 같다) | (두 사본이 같습니다) |
| 검색 시간을 줄인다, 미팅 뒤 반복 업무를 줄인다처럼 | 검색 시간 단축, 미팅 뒤 반복 업무 줄이기처럼 |
