# 축 2. 톤과 디테일: 사례

**로드 시점: 개선 중 처방의 실제 모양이 필요할 때.** 규칙은 `improve.md`가 정본이고 여기는 사례만.

## 우리 사례

### 작성자의 사실을 외부 기록처럼 서술 (2026-09-30, 인수인계서)

전: "ERP 실무는 길동님이 이어받는 것으로 기록돼 있고"
후: "ERP 실무는 길동님이 이어받고"

작성자가 직접 정한 역할 분담을 설명하는 문장이었다. 편집자가 문서를 읽는 입장을 본문에 넣어 작성자를 외부 조사자로 바꿨다. 같은 문서의 "이 문서에 기록된 브랜치 상태", "재적용분뿐인 것으로 기록돼 있습니다"도 확인일을 붙인 직접 서술로 고쳤다. 데이터 이관 경위나 분석 이벤트의 출처처럼 실제 확인하지 못한 내용의 유보는 유지했다.
### 외주 의뢰서의 지시 어투 (2026-10-02, 외주 디자이너용 브랜드 디자인 의뢰서)

계약서 조항(유료 폰트는 사용 전 공유와 확인)을 옮기면서 "쓰기 전에 공유하고 확인받기"가 규격 예시 표에 들어갔고, 사용자가 "너무 싸가지가 없다"고 했다. 같은 원인으로 훑어 의무 3곳("~있어야 합니다"), 허락 7곳("~도 됩니다" 6, "괜찮습니다" 1), 명령 6곳("~주세요"로 끝나는 요청 중 결과물 요구)을 부탁과 바람으로 고쳤다. "의견이나 훈수도 편하게 주세요", "편하게 제안해 주세요"는 권유라 남겼다.

### 법인격 약칭 (2026-05, 제조 공정 데이터 연동 PoC 제안서)

전: "(주)A사가 B사에게 의뢰한 ..."
후 (도입부): "본 문서는 (주)A사(이하 "고객사")가 발주하는 C사 공정 데이터 연동 PoC에 대해 B 유한책임회사(이하 "개발사")가 수행 범위와 비용을 제안하는 자료임."
후 (본문): "고객사가 개발사에게 ..."

표지와 서명란은 풀 법인격 그대로 두었다.

### 종결어미 혼용 (2026-09, IoT 제품 방향성 문서)

내부 회의 자료라 "~입니다" 정중체로 통일했고, 5.2 포지션 문장의 "두셔도 되고 저희 클라우드를 쓰셔도 됩니다"는 영업 시뮬레이션 인용이라 그대로 두었다. 인용 안의 구어체는 정보다.

### 사람 호칭 통일 (2026-09-30, 인수인계서, 런북, 내부 문서)

같은 사람이 "홍길동", "홍길동님", "길동님"으로 섞여 있었다. 사용자 지적: "나를 제외한 다른사람들의 이름은 선언하는 곳 외에는 ㅇㅇ님으로 호칭 통일". 세 문서에서 115곳을 바꿨고 "홍길동이"처럼 조사가 바뀌는 곳 11곳을 함께 고쳤다. 첫 시도에서 사람 소개 표의 이름 칸까지 바뀌어 되돌렸다. HTML 을 태그로 쪼개면 붙은 태그 사이에 빈 조각이 끼어 "표 첫 칸" 판정이 빗나간다.

### 외부 서비스를 「거래처」로 부른 장 (2026-09-28, 인수인계서)

인수인계서 한 장의 제목이 「거래처와 브랜드 자산」이었고 절 제목 여섯 개, 표 머리 「거래처」, 본문 문장, 내부 체크리스트 일곱 곳이 같은 말을 썼다. 안에 든 것은 Cloudflare, AWS, Slack, LLM API, 폰트 라이선스 같은 구독 서비스였다. 장 제목을 「외부 서비스와 브랜드 자산」으로, 표 머리를 「서비스」로 바꾸고 두 문서에서 「거래처」 0건을 확인했다.

### 구현 용어로 쓴 평가 항목 (2026-09-28, 하네스 검증 시나리오)

평가 항목 109개가 `intent.md`, `cycles.plan`, `check-cycle.js`, 앵커, 적재, 게이트, 프로브, 층3 같은 말로 쓰여 있었다. 문서를 쉬운 말로 다시 쓰고(예: "앵커가 OR union" -> "볼 인원을 조건 중 하나라도 맞는 사람 전부로 잡았다", "층3 끌어냄" -> "속사정 끌어냄"), 「확인」 자리의 쉬운 이름 열여섯 개와 실제 파일의 대응은 판정표 문서로 옮겼다. 항목 수는 109개 그대로다.

### 판정 항목 번호 (2026-09-28, 하네스 검증 시나리오)

판정 항목 101개에 `R41`, `P13`, `Q5.3` 같은 번호를 붙이고 본문이 "R65 가 실패", "Q29~Q36 이 측정불가"로 불렀다. 접두 글자는 항목이 원래 있던 표를 뜻했는데 한 문서로 합친 뒤에는 의미가 없었다. 번호를 전부 떼고, 겹치던 이름 하나(「근거 선행」 둘)를 「발굴 원본 선행」, 「intent 선행」으로 갈랐고, 참조 열다섯 곳을 「」 이름으로 바꿨다.

### 내부 조어가 사용자 발화로 새는 것 (2026-09-23, 에이전트 하네스 문서)

한 에이전트 하네스에서 사용자에게 "프로브를 다시 돌립니다"라는 문장이 나갔다. 「프로브」는 그 하네스의 스킬 문서가 정의한 인터뷰 기법 이름이고, 사용자는 그 문서를 읽지 않는다. 사용자 지적: "이 스킬의 사용자는 컨설턴트이기 때문에 조금 더 직관적인 단어를 사용해줘. 비개발 용어들로."

처음에는 그 용어가 정의된 문서에 "이 말은 사용자에게 쓰지 않는다" 주석을 달았다. 두 번째 지적이 왔다. "프로브뿐만 아니야. 전반적으로 우리 스킬 내부에서 정의된 단어도 직관적인 용어를 써줘. 84번째 줄같은 쓸데없는 말 추가하지 말고." 둘이 한 원인이었다. 범위가 하나가 아니라 전수였고, 막는 자리는 정의 자리가 아니라 문체 규칙 한 곳이었다.

전수로 세어 보니 문서에 정의된 이름이 서른 남짓이었고, 그중 실제로 발화에 새는 것이 열여덟이었다. 그리고 **진짜 발생지는 보고 서식**이었다. 서식 자체에 내부어가 박혀 있어 쓰는 쪽이 그대로 채우고 있었다. 용어 표(정본 한 곳) + 서식 넷을 함께 고쳤고, 정의 자리에 달았던 주석은 지웠다.

### 요구의 말 흐림과 의뢰서의 끝맺음 (같은 의뢰서)

"키컬러와 함께 쓸 보조색, 무채색. 어렵다면 키컬러만이라도"에 사용자가 "말 흐리지 마"라고 했다. 공고 문구("빡세면 최소한 키컬러라도")를 옮기다 생겼다. 계약서에 컬러 시스템이 결과물로 있어 단정형으로 고쳤다. 마지막 절은 후속 계약 제안으로 닫았다가 "저내용 굳이 꺼내진 말고, 조율 필요한거 얼마든지 이야기해달라, 함께하게 되어서 고맙다"로 바꿨다.

### 필자의 3인칭 과거 회고 (2026-10-12, 인수인계서)

"인프라 관리자로 적힌 자리도 홍길동이었습니다"(필자 자신)를 지적받고 같은 결의 "홍길동이 맡던 범위에는", "홍길동 몫을 이어받을 사람은"을 받는 사람의 일로 바꿨다. 연혁("홍길동이 Product Engineer 로 입사했고")과 출처("홍길동 개인 비밀번호 관리자에 모아 두었던")는 필자가 사실의 주어라 남겼다.

## 반례

- 격식을 빼려다 "들여다봤습니다", "거의 정리됐고"로 떨어진 것. 회사명이 들어가는 문서에서 어색하고 기술적 약속의 강도가 깎인다.
- "100% 보장"을 중립으로 바꾸면서 "보장합니다"까지 지운 것. 약속 자체는 남겨야 한다.
- 약칭을 정의해 놓고 서명란까지 "개발사"로 쓴 것. 서명란, 인보이스, 법적 조항은 풀 법인격이다.
