### 인수인계서의 흩어진 코드 위치 (2026-10-13)

인수인계서 본문에 코드 파일 경로가 60여 개 절에 204곳, 작업 통계("커밋 약 1,700개, 2025-09 ~ 11 이 정점", "커밋 218개, 그 가운데 절반이 작업 화면")가 섞여 있었다. 지적: "이런 쓸모없는 내용 다 제거해줘. 그리고 코드 위치를 직접 언급하지 말고, 코드베이스의 폴더구조 아키텍처, path map, 스튜디오가 어떻게 claude code 와 연계되는지 등에 대한 내용을 잘 담아야 할듯". 저장소 넷의 역할 표, core 와 대시보드의 폴더 트리, HTTP 입구 접두사 표, 대시보드 주소 지도, 에이전트 저장소와 워크스페이스 트리, 스튜디오와 Claude Code 연결 표를 새로 두고, 본문의 파일 이름은 그 구조 절에서 찾아갈 수 있는 개념 이름으로 바꿨다. 런북의 실행 스크립트와 서버 설정 경로는 남겼다.

### 인수인계서의 못 여는 포인터 (2026-10-13)

넘기는 사람의 개인 저장소 경로, git 밖 폴더, 개인 Gmail 조직, "넘기는 사람 맥의 DB" 출처, 개인 메일로 가입한 외부 서비스 계정 이름이 12곳 있었다. 요지가 필요한 사무실 네트워크 가설은 본문으로 옮기고, git 밖 자산 표는 절째 내부 문서로 넘기고(이전 할 일은 이미 내부 문서에 있었다), 나머지는 포인터를 지웠다. 컨설턴트 기기나 서버의 경로(`~/.cdp/sessions`, 서버의 `~/caddy`)는 받는 사람이 실제로 쓰는 곳이라 남겼다.

### 윗단만 자세한 인계서 (2026-10-07, 인수인계서)

사용자 지적: "지금 제품과 프로젝트가 어디까지 왔고, 기술적으로 어떤 디테일한 결정들이 있었는지 유의해야되는지가 잘 녹아있어야 하는데 너무 윗단의 내용들만 다뤄진느낌이다?" 절별 글자 수를 재니 관측과 알림 5,100자, 외부 서비스 4,000자인데 백엔드 설계 결정은 2,900자였고, 결정 표 둘은 "이유 기록 없음"이었다. 알려진 함정 여덟 줄은 디자인 토큰과 인프라 이야기였다. 읽기 전용 조사 둘(업무 시스템, 에이전트 저장소)로 커밋과 기획 문서를 훑어 기능별 상태 표, 도메인 모델에서 지킬 것, 매칭과 임베딩, Context 수집, 에이전트 구성 요소 상태와 계획 대조, 검색 기능의 결정, git 밖 자산, 실패 기록을 넣었다. "이유 기록 없음" 둘은 프롬프트 diff 와 커밋 흐름에서 이유를 찾았고, 하나는 사실과 달라 고쳤다.

### 인계 문서에 넘기는 사람의 할 일이 섞임 (2026-09-21, 인수인계 문서)

계정 문서를 `자산 | 현재 명의 | 이관 대상 | 이관 방법 | 완료` 표로 썼다. 사용자 "이거 전달해줄 문서가 맞아? 내가 해야될 투두리스트처럼 보이는데?". 받는 사람이 그 표로 할 수 있는 일이 없었다. 계정 문서는 "값은 어디에, 로그인 방식은, 관리자는 누구, 인프라 자격증명은 어떻게"로 다시 쓰고, 이관과 회수 체크리스트는 넘기는 사람의 체크리스트로 옮겼다. 같은 형태가 벤더 문서 끝 "넘길 것"과 인프라 문서의 키 회수 항목에도 있었다.

### 남는 쪽이 더 잘 아는 것을 넘기려 함 (같은 문서)

사람과 연락처 문서(팀 구성, 사람별 역할, 채널 접두사)를 만들었다. 사용자 "사람에 대해서 인수인계 안해도 돼. 그건 잔류인원이 알아서 하겠지. 내 업무를 인수인계 하면 돼". 문서를 지우고, 넘기는 사람의 자리에 걸려 있던 역할(인프라 관리자) 한 문단만 운영 문서로 옮겼다.

### 거래처 표에 이름과 계정만 (같은 문서)

벤더 표가 `거래처 | 무엇 | 로그인 계정 | 결제 | 갱신` 이었고 "무엇" 열이 "LLM API", "음성 인식"처럼 한 단어였다. 사용자 "벤더는 그게 뭐고 우리는 어디에 쓰이는지 구체적으로 작성해줘야돼". 코드와 인프라 설정과 DNS 에서 사용처를 찾아 "무엇인가 | 우리는 어디에 쓰나" 두 열로 바꿨고, 못 찾은 것은 "코드도 문서도 없다. 해지 후보"로 적었다.

### 체크박스가 아닌 모양으로 다시 들어온 넘기는 사람의 할 일 (2026-09-30, 인수인계서)

"화자의 할 일이 독자 문서에"를 두 번 고친 뒤에도 인수인계서에 23곳이 남아 있었다. 체크박스는 없었고 "조심할 것" 상자("LLM 청구 계정을 회사 org 로 옮기고 운영 키를 다시 발급합니다"), 표 칸("넘기는 사람 개인 PAT", "관리자는 네 사람, 그중 하나가 넘기는 사람"), 경고 상자(저장소에 커밋된 `secrets.zip`) 모양이었다. 사용자 지적: "인수인계서에서 git secret 이라던가, 내가 정리하고가야될만한것틀 추려봐. 그런것들은 인수인계서에서 빼고, 내 todo로 넘겨야돼거든". 넘기는 사람의 이름과 "떠날 때", "옮겨야", "개인 명의"로 86문장을 뽑아 모두 읽고, 넘기는 사람이 끝내면 거짓이 되는 23곳을 빼서 내부 체크리스트로 옮겼다(새 행 다섯, 나머지는 이미 있던 행). 서버 한 대의 재구축과 클러스터 관리자 인증서 교체는 받는 사람에게 남는 위험이라 남겼다.

### 넘기는 사람의 개인 세팅이 인계 내용으로 (2026-09-30, 인수인계서와 런북)

Cloudflare 절에 "OAuth 하나로 여러 회사와 개인 계정에 접근하니 변경 전에 계정을 확인한다, DNS 변경은 사용자 확인 뒤에 한다"가 들어가 있었다. 둘 다 넘기는 사람의 인증 범위와 자기 에이전트 규칙이다. 같은 원인으로 두 문서를 훑어 16곳을 고쳤다(개인 OAuth 범위 셋, 넘기는 사람 맥의 VPN, 클라우드 키, 폰트 파일, 설치 버전, 개인 전역 스킬, 개인 스킬 정본, 넘기는 사람의 기억, 에이전트용 "사용자 확인 뒤에" 둘, "이 맥 밖에서"). 개인 결제에 걸린 LLM 청구 org, 개인 토큰에 걸린 배포, Super Administrator 의 개인 메일은 받는 사람이 처리할 위험이라 남겼다.

### 목적이 문서 뒤쪽에, 현황은 빈칸으로만 (2026-09-28, 인수인계 문서 묶음)

입구 README 가 제목, 작성자, 용어표 12행, 표 셋 순서였다. 목표 문장("빠져도 지금 수준이 유지되고 전화하지 않아도 되는 상태")은 아래쪽 "인계 일정" 절 가운데에 있었다. 표 셋은 칸 대부분이 비어 있었는데(끝낼 일 8건 중 담당 7건 공란, 승계 7영역 중 6 공란), 그 사실을 적은 문장이 없었다. 사용자 "문서의 목적이나 내용이 잘 안 읽히는 것 같아". 묶음의 다른 문서 열 개 중 넷은 첫 문단에 독자가 없었고 하나는 첫 문단이 아예 없었다. 문서마다 첫 두 문단(목적과 독자, 지금 위험한 것 서너 개와 절 번호)을 쓰고, README 는 순서를 바꾸고 용어표를 맨 끝으로 옮겼다. 문서끼리 절 번호로 참조하고 있어 절 번호는 그대로 뒀다.

### 같은 지적이 두 번째로 들어옴: 결정 대기가 첫 장에 (2026-09-28, 인수인계서 HTML)

md 묶음을 단일 HTML 로 옮기면서 입구 README 의 순서(지금 상태, 결정 대기, 넘기기 전 할 일, 일정, 인수 확인)를 그대로 첫 장으로 가져왔고, 11장에 로컬 자산을 두었다. 사용자 "맨 앞에 결정 대기 이런건 우리 내부 문서로 내리고 딱 사람이 읽기 좋은 구조로만 만들어줘. 로컬 자산과 그 밖의 저장소 이런것도 우리가 정리할 내용인거지 인수인계서에 있을 내용이 아니잖아". 2026-09-21 의 "화자의 할 일이 독자 문서에" 신호로 걸렸어야 할 것이다. 인수인계서는 받는 사람 기준 10장(한눈에 보기, 일하는 방식, 작업 환경, 업무 시스템 운영, 인프라, 계정, 거래처, 보안, 행사 운영, 에이전트)으로 다시 짜고, 빠지는 것은 `internal.md` 로 모았다. 장마다 "지금 위험한 것"을 "먼저 알아 둘 것"으로 바꿔 받는 사람의 운영 관점으로 다시 썼다.

### 계약서와 어긋난 의뢰서, 바깥에 보일 것 (같은 의뢰서)

예산을 이유로 결과물을 로고와 색 둘로 줄였는데, 그 뒤 받은 서명 계약서에는 결과물이 여섯(폰트 정보, 명함 포함)이었다. 사용자가 "계약서대로 싹 진행해줘"라고 해 번호와 일정까지 계약서에 맞췄다. 같은 문서에서 팀 굿즈와 여행("외부에서 비쳐지는 모습이기에 빼도 됨"), 팀 인원 8명("시작이 8이지 달라질 수 있어서 쓰기 위험해"), 도메인 등록 기간을 뺐다.

### 의뢰서의 순서와 내부 사정 (2026-10-02, 외주 디자이너용 브랜드 디자인 의뢰서)

### 관행에서 옮겨 온 항목 (2026-10-02, 외주 디자이너용 브랜드 디자인 의뢰서)
