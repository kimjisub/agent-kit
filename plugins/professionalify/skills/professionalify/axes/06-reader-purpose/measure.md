# 축 6. 독자와 목적: 측정

**로드 시점: 측정과 검증 단계에서.** 켜지는 조건과 왜는 `axis.md`, 고치는 법은 `improve.md`.

## 신호

둘 이상이면 분리를 검토한다.

| 신호 | 어떻게 보이나 | 심각도 |
|---|---|---|
| 세 목적 동거 | 가격, 일정 표와 기술 다이어그램과 시스템 명세가 한 문서에 | S1 |
| 결정에 기술 디테일이 필요 | 의사결정자가 OK를 하려면 JSON 스키마까지 읽어야 함 | S1 |
| 같은 메시지 4\~5회 | 목적이 흐려 같은 것을 여러 각도로 반복 | S2 (축 4와 겹침) |
| 규모 대비 분량 | 1천만원대 PoC에 본문 7쪽 이상 | S2 |
| 사용자 체감 | "내용이 너무 많다", "어디부터 봐야 할지 모르겠다" | S2 |
| 코드 블록이 외부 견적서에 | JSON, SQL, 코드가 발송용 견적 문서 본문에 | S1 |
| 행동 유도 부재 | 문서 끝에 무엇을 정해 달라는지 없음 | S1 |
| 형식적인 승인 요청 | 받는 사람이 어차피 하는 일(검토, 의견)을 "이대로 가도 될까요?" 결정 칸으로 묻는다. 선택지가 "좋음 / 고칠 것 있음 / 다시 얘기" 처럼 무엇을 정하는지 없이 같은 셋이 반복된다. 진짜 결정 칸이 그 사이에 묻히고, 받는 사람은 정할 것이 없는 칸을 채운다 | S2 |
| 목차만 있는 부록 | "부록: 전체" 라는 절에 전체를 이루는 묶음 하나(루트, 표지, 목차 그림)만 있다. 읽는 사람은 나머지를 어디서 보는지 몰라 "이것만 보여주면 뭐 어쩌라는 거지" 가 남는다. 부록은 전체를 다 싣고 항목마다 무엇이 들었는지 한 줄을 단다 | S2 |
| 자리와 어긋난 화자 위치 | 이력서나 소개서가 지원하려는 자리보다 낮은 층(기술 하나, 맡은 기능)으로 사람을 소개함. 첫 쪽이 기술 목록과 구현 항목으로 차 있고 무엇을 결정했는지가 없음 | S1 |
| 이력서의 수단 앞세움 | "LLM, MCP 를 활용한 자동화"처럼 도구 이름이 한 일의 주어가 되고, 시스템이 어떤 구조였는지가 앞에 없음. "React 로 화면을 만들고", "NestJS, PostgreSQL 로 서버를 만들고"처럼 어느 개발자나 쓰는 기본 스택을 수단 구로 문장 앞에 둔 것도 같다 | S1 |
| 이력서의 자기 서술 | 일하는 원칙, 강점, 철학처럼 읽는 사람이 확인할 수 없는 문장이 첫 쪽을 차지함. 결정권자는 "말로는 의미가 없고 뭘 했는지를 본다" | S2 |
| 포트폴리오의 작업량 지표 | 커밋 수, 코드 줄 수, 파일, 테스트, 모듈 개수와 구현 세부가 쪽 위쪽이나 칸을 채움. 어떤 상황에서 무엇을 정했고 왜 정했는지가 그 아래에 묻힘 | S1 |
| 5분짜리 한 줄 | 누구나 에이전트에게 시키면 5분 안에 나올 일을 성과처럼 씀("탐색했다", 작은 도구 이름 나열) | S2 |
| 상위 문서와 어긋남 | 계약서, 공고, 이미 보낸 메시지가 정한 범위, 번호, 일정과 다르게 씀. 결과물을 합치거나 빼거나 새 날짜를 정함 | S1 |
| 바깥에 보일 것이 아닌 정체성 | 팀 내부 상징(굿즈, 회식, 여행), 바뀔 수 있는 운영 숫자(팀 인원, 등록 기간)를 회사 정체성처럼 외부 문서에 씀 | S2 |
| 화자의 할 일이 독자 문서에 | 넘기는 사람이 해야 할 이관, 회수, 통보가 체크박스와 "완료" 열로 받는 사람 문서에 들어 있음. 결정 대기 목록, 퇴사 전 할 일, 미결 목록, 넘기는 사람의 로컬 자산 정리, 존속 판단 자료도 같다. 받는 사람은 그 문서로 무엇을 해야 할지 모른다. 체크박스가 없어도 같다. "조심할 것" 상자와 표 칸에 산문으로 들어간 "퇴사 때 ~를 지웁니다", "~로 옮겨야 합니다", "<넘기는 사람> 개인 PAT", "관리자는 ... <넘기는 사람>" 도 넘기는 사람이 끝내면 거짓이 되는 문장이다 | S1 |
| 독자가 이미 아는 것 | 조직 구성, 사람별 역할, 채널 목록처럼 남는 쪽이 넘기는 쪽보다 잘 아는 것을 넘기는 문서에 씀 | S2 |
| 아는 독자에게 배경을 다시 설명 | 독자가 정해진 문서(인계서, 팀 보고)에 그 독자가 이미 만들었거나 매일 쓰는 것의 설명이 본문에 섞여 있다. 독자별로 "이 사람이 이미 아는가"를 근거(커밋 작성자, 담당 영역, 회의 참석)로 가르면 본문의 상당 부분이 걸린다 | S2 |
| 남의 이야기가 섞인 인물 소개 | 한 사람의 소개 칸에 다른 사람과 함께 하는 일("회사 차원의 결정은 대표님과 함께")이나 받는 사람이 할 일과 무관한 업무("채용 1차 인터뷰를 함께 본다", "입퇴사 처리")가 들어간다. 소개는 그 사람이 맡는 일과 받는 사람이 그 사람에게 가져갈 일만 쓴다. 이 일을 맡지 않게 된 사람은 명단에서 뺀다 | S2 |
| 인물 소개가 부속 사실로 | 함께 일할 사람 표에 그 사람이 무엇을 맡고 어떤 일로 찾아가면 되는지 대신 직함 한 단어나 명의, 소유자, 결제 계정 같은 부속 사실만 있음. 받는 사람은 그 사람에게 무엇을 물어야 하는지 모르고, 소개받는 사람에게는 무례하게 읽힌다 | S2 |
| 정해지지 않은 일정 | 미정이거나 바뀔 일정(교육일, 배포일, 목표일)을 날짜로 적어 받는 사람이 확정된 약속으로 읽는다. 연혁 표에 "(예정)"으로, 현황 표와 타임라인에 날짜로 들어간다 | S2 |
| 화자의 개인 환경이 독자 문서에 | 넘기는 사람의 장비, 개인 계정 권한, 개인 도구, 자기 에이전트에게 준 규칙에서만 성립하는 문장이 받는 사람의 사실이나 절차로 적힘. "OAuth 하나로 우리 회사와 다른 회사, 개인 계정에 모두 접근하므로 변경 전에 계정을 확인한다", "변경은 사용자 확인 뒤에 한다", "이 맥에 다른 VPN 이 떠 있으면", "<넘기는 사람> 맥에 프로필 키가 있다", "개인 전역 스킬로 교차 검토를 돌렸다", "<넘기는 사람>의 기억은 ~였다". 받는 사람이 열 수 없는 위치를 가리키는 포인터도 같다. 넘기는 사람의 개인 저장소 경로, git 밖 폴더, 개인 메일 조직, 넘기는 사람 기기에서 확인했다는 출처("<넘기는 사람> 맥 DB 에 사이클 53개"). 받는 사람의 환경에서는 참이 아니거나 할 일이 생기지 않거나 "그래서 어쩌라고"가 남음 | S2 |
| 외부 회사와 개인의 단서 | 넘기는 사람의 다른 소속(겸직 회사, 그 회사의 계정 번호, 제품, "두 회사가 같이 쓰는 자산"), 동료의 개인 메일 주소, 고객사 이름이 문서나 화면 캡처에 남음. 산출물 파일 안에 빌드한 사람의 로컬 경로(`/Users/<이름>/...`, 개발 빌드의 소스 경로)가 박힌 것도 같다. 받는 사람의 일에 필요한 것은 거래처 이름과 연락 경로까지다 | S2 |
| 흩어진 코드 위치와 작업 통계 | 인계, 온보딩 문서의 본문 곳곳에 파일 이름과 경로, 만든 사람과 고친 사람의 이력("처음 만든 사람은 첫 담당자이고 이후 <넘기는 사람>과 다른 동료가 고쳤습니다"), 조사 근거(커밋 해시, "커밋 흐름에서 읽은 것이다", PR 번호)가 근거나 안내로 박힘("백엔드는 `order.resolver.ts`(1,299줄)", "코드는 `plugins/.../dashboard/`"). 넘기는 사람이 일한 양을 재는 숫자가 사실처럼 끼어 있음("커밋 약 1,700개, 2025-09 ~ 11 이 정점", "가장 많이 고친 스킬, 커밋 218개"). 받는 사람에게는 구조 지도가 없어 경로를 외워야 하고, 파일이 옮겨지면 문서가 통째로 낡는다. 통계는 받는 사람의 할 일을 바꾸지 않는다 | S2 |
| 끝난 일을 진행 중처럼 소개 | 종료된 프로젝트의 장이 진행 중인 제품처럼 구조, 흐름, 관리자 기능, 다음 회차 재사용까지 담는다. 장 첫 문장에 "종료된 프로젝트입니다"와 남은 일(내리기, 파기)을 쓰고 그 일에 필요한 것만 남긴다 | S2 |
| 조사 흔적 | 쓰는 사람이 조사하며 만든 문서(인계서, 현황 보고서)에 조사 과정이 남음. 여덟 갈래다: 확인 경위("2026-09-28 에 CLI 로 조회했습니다"), 기준 시점 표기("2026-10-07 기준 상태입니다", "(두 사본이 같다, 2026-09-28 확인)"), 실측 런 결과("실측 런에서 162분에 완주했고 23항목 중 22개 통과"), 지금 수치 스냅샷("v21 이 8,380건이고 오늘도 생성됐다", "메모리 사용 74%"), 날짜 붙은 변경 경위("2026-03-10 에 단계 순서를 버리고 바꿨다"), 점검 결과 서술("가이드는 수동 동기화라고 적었지만 실제와 다릅니다"), 확인 못 한 것 고지("매각했는지는 확인하지 못했다"), 근거 칸(표의 "근거", "기록 위치" 열). 받는 사람은 지금 상태와 지킬 규칙만 쓰는데 문장마다 언제 누가 무엇으로 쟀는지가 따라와 길어지고, 날짜와 숫자는 읽는 날 이미 틀려 있다 | S2 |
| 읽는 사람이 쓰지 않는 상세 | 조사 흔적을 걷어낸 뒤에도 남는 내용 군더더기. 여섯 갈래다: 코드 식별자(enum 값 `AUTO_MAPPED`, 컬럼 `calc_stageStatus`, 채널 상수 `SLACK_CHANNEL_AP_FINAL`, 내부 클래스와 파일 이름), 비밀 보관소 항목 이름이 본문 곳곳에 반복(`GitHub - <공용 계정>`, `Sentry - <공용 계정>`), 문서 안 상호 참조("(4장 6절)", "12장 5절에 있다", 칸 전부가 참조인 "자세히" 열), 절 머리 예고 문장("~를 모았습니다", "앞 장의 시스템은 이 역할의 수단입니다"), 화면이나 코드를 보면 아는 괄호 속 나열("(인적 정보, 처우, 희망, 스킬, 학력, 경력, 커리어 여정, 목표)"), 같은 경고의 반복(같은 장 안에서 두 번 권고). 읽는 사람이 쳐서 쓰지 않는 이름은 해독할 거리만 늘리고, 참조와 반복은 읽는 순서를 끊는다 | S2 |
| 인계 시점의 진행 스냅샷 | 인계 문서에 "진행 중인 일" 장이 따로 있음. 열린 PR, 진행 중이던 기획, 합의 현황 표가 넘기는 날의 상태로 박혀 있다. 받는 사람은 그 일을 GitHub, Linear 에서 최신으로 보고, 문서 속 표는 한 주만 지나도 틀린다 | S2 |
| 할 일을 바꾸지 않는 운영 지표 | 인계, 운영 문서에 월별 추이 차트, 숫자 상자("월 40~60건", "N명 신청"), 최근 N일 사용량과 비용, 방문자 수가 들어감. 그 숫자로 받는 사람이 정할 것이 없고 조회 시점이 지나면 바로 낡는다. 남길 숫자는 받는 사람의 판단을 바꾸는 것뿐이다(파기 기한, 한도, 단가, 관문 기준선) | S2 |
| 고유명사만 나열 | 서비스, 도구, 거래처 이름과 계정만 표에 있고 그것이 무엇인지와 우리에게 무엇인지가 없음. 독자가 이름을 모르면 행 전체가 정보가 아니다 | S1 |
| 목적이 첫 화면 밖 | 제목 다음에 용어표나 양식 표가 먼저 오고, "이 문서가 무엇을 하려는가"와 "누가 읽고 무엇을 정하나"가 뒤쪽 절 가운데에 있거나 없음. 입구 문서와 묶음의 각 문서 모두 해당 | S1 |
| 빈칸이 현황을 대신함 | 담당, 승계자, 결정권자 칸이 대부분 비어 있는데 그 사실을 적은 문장이 없음. 가장 중요한 현황이 빈칸으로만 전달되고, 표는 미완성 양식으로 읽힌다 | S1 |
| 인계 문서의 깊이 쏠림 | 인계 문서에서 이어받는 실무자가 코드를 고칠 때 필요한 층(기능별 현재 상태, 결정마다 이유와 코드 위치와 지킬 것, 함정)이 한 줄 요지나 "이유 기록 없음"으로만 있고, 배경, 합의, 관문, 계정 같은 윗단은 자세하다. 절별 글자 수를 재면 제품 장이 인프라 장의 절반 아래로 나온다 | S1 |
| 의뢰서가 소개로 시작 | 외주·발주 문서의 첫 쪽이 의뢰 범위(무엇을, 어디까지, 언제)가 아니라 회사 소개다. 받는 사람은 자기 일이 무엇인지 몇 쪽을 넘겨야 안다 | S1 |
| 내부 사정 노출 | 받는 사람의 일을 바꾸지 않는 우리 쪽 정보(누가 최종 결정하는지, 내부 결재 구조, 내부에서 먼저 정할 것)가 외부 문서에 있다 | S2 |
| 작성 과정이 비교 대상에게 | 만든 사람의 검토 이력(누가 몇 번 지적했나, 지적별로 고친 것, 도구를 고친 경위), 다음 할 일, 결정 요청이 그 결과를 검토받을 사람에게 가는 문서에 남음. 받는 사람은 결과를 판단하려고 읽는데 과정이 절을 차지한다. 결정 항목도 "근거: 스킬 몇 절"처럼 만든 쪽의 출처만 있고 무엇을 내줬는지가 없다 | S1 |
| 관행에서 옮겨 온 항목 | 업계 가이드를 조사해 "보통 이런 것이 들어간다"며 넣은 항목(사용 비율 60/30/10, 명도 대비, Pantone 별색, 안전 영역)이 이번 거래 규모와 계약 범위를 넘거나, 설명 없이 용어만 남음. 읽는 사람이 "이게 뭐야"를 묻게 됨 | S2 |
| 참석자 회의록의 앞이 논의 경과 | 참석자가 읽는 회의록의 첫 화면이 논의 흐름 서술이고, 정해진 것과 사람별 할 일이 문단 속이나 문서 뒤쪽에 있음. 본문이 열 쪽을 넘김 | S2 |

## 측정 방법

```bash
# 조사 흔적 여덟 갈래를 센다. 걸린 줄은 후보이고 규칙, 한도, 단가, 보존 기한, 연혁은 남긴다
python3 scripts/research-traces.py <file> [--all]
# 읽는 사람이 쓰지 않는 상세 여섯 갈래를 센다. 코드 식별자 비율이 본문의 15% 를 넘으면 신호다
python3 scripts/detail-noise.py <file> [--all]
# 코드 블록과 스키마
grep -c '^```' <file>
grep -cE '"[a-z_]+":' <file>                     # JSON 키

# 가격과 기술이 같이 있는가
grep -cE "원\)|만 원|VAT" <file>
grep -cE "API|스키마|다이어그램|프로토콜|엔드포인트" <file>

# 분량
wc -l <file>; grep -vc '^\s*$' <file>

# 행동 유도
tail -8 <file> | grep -cE "까지|회신|확정|선택|결정"

# 화자의 할 일 잔존 (넘기는 문서, 인계 문서)
grep -c '\- \[ \]' <file>; grep -cE "완료 \||이관 대상" <file>
grep -nE "<넘기는 사람 이름>|퇴사 (때|전)|옮겨야|옮깁니다|맥에만|정해야 합니다|재발급|개인 (명의|토큰|PAT|org|메일)" <file>   # 산문으로 들어간 넘기는 사람의 할 일. 걸린 줄을 전부 읽는다
grep -nE "<넘기는 사람 이름>(의)? ?(맥|로컬|개인)|git 밖|gitignore|~/GitHub/|_<개인 저장소>/|개인 (Gmail|1Password|저장소)" <file>   # 받는 사람이 못 여는 포인터. 서버와 받는 사람 기기의 경로(~/.kube, 서버의 ~/caddy)는 오탐
grep -nE "(React|Next\.js|NestJS|Node\.js|GraphQL|PostgreSQL|MongoDB|WebSocket|Redis|AWS|Docker|Firebase)[^.]{0,30}(로|으로) [^.]{0,30}(만들|구현|개발)" <file>   # 이력서에서 기본 스택이 수단 구로 문장 앞에 옴. 구조 결정(서비스 9개를 하나로 합쳤다)이면 오탐
# 외부 회사와 개인의 단서. 이름 목록은 추측으로 만들지 않고 원천에서 가져온다
#   고객사: 업무 시스템의 고객사 테이블 이름 전부를 본문, 그림 SVG, 번들 HTML 과 대조한다 (일반 단어와 겹치는 짧은 이름은 오탐)
#   캡처: 화면 캡처는 grep 이 안 되므로 한 장씩 눈으로 본다. 목록 카드, 브레드크럼, 상세 머리에 고객사 이름이 남는다
#   번들: grep -c "/Users/" <번들 HTML>  # 0 이 아니면 개발 빌드다. NODE_ENV=production 으로 다시 빌드한다
grep -nE "@gmail\.com|CTO|겸직|두 회사" <file>   # 개인 메일과 다른 소속
# 저장소 안처럼 보이는 경로도 실제로 인계되는지 잰다. 문서의 <code> 경로마다 해당 저장소에서
#   git -C <repo> check-ignore -q <path>   # 0 이면 gitignore 라 clone 해도 없다
# 걸린 경로가 ".env", ".mcp.json" 처럼 받는 사람이 스스로 만들거나 시크릿 묶음으로 전달되는 것이면 오탐.
# 그 밖(보고서 폴더, 계획 문서, 데이터 폴더)이면 "인계 때 전달한다"는 문장이 실제 전달 목록과 맞는지 본다
grep -nE "커밋 (약 )?[0-9,]+ ?개|[0-9,]+ ?줄[).,]|정점|<code>[^<]*\.(ts|tsx|py|js|sql)</code>" <file>   # 작업 통계와 산발적 파일 경로. 실행하는 명령과 스크립트(런북), 폴더 구조 절 안의 경로는 오탐
```

체크리스트:
- [ ] 리드와 첫 화면의 문장을 하나씩 지워도 읽는 사람이 할 일이 그대로인가 (그렇다면 그 문장은 자리만 차지한다)
- [ ] 처음 1쪽만 읽고 의사결정자가 결정할 수 있는가
- [ ] 실무자가 사양 회신에 필요한 정보를 찾을 수 있는가
- [ ] 두 독자가 같은 절을 읽고 있는가 (그렇다면 목적 혼재)
- [ ] 마지막에 무엇을, 언제까지, 누가 정하는지 있는가
- [ ] 넘기는 문서라면, 이 문서로 받는 사람이 하는 일과 넘기는 사람이 하는 일이 갈려 있는가 (체크박스가 있으면 누구 것인지)
- [ ] 형식을 바꾸거나 여러 문서를 하나로 묶었으면(md 에서 HTML 로, 문서 묶음에서 단일 문서로) 이 체크리스트를 다시 돈다. 변환은 내용을 옮기는 일이라 독자 판단이 따라오지 않는다
- [ ] 표의 각 행에 "무엇인가"와 "우리에게 무엇인가"가 있는가. 이름과 계정만 있으면 독자가 모르는 행이다
- [ ] 첫 두 문단 안에 이 문서가 무엇을 하려는지, 누가 읽고 무엇을 정하는지, 지금 상태가 있는가. 여러 문서 묶음이면 문서마다 본다
- [ ] 빈칸이 많은 표가 있으면 빈칸 수를 센 문장이 표 위에 있는가

## 채점 (0\~20)

steps/scoring.md의 "문서 목적, 완결성" 차원이다.

| 점수 | 기준 |
|---:|---|
| 20 | 단일 목적, 1쪽으로 결정 가능, 행동 유도(기한, 담당자) 명시, 분량 적정 |
| 15 | 하나 약함 (행동 유도가 모호하거나 분량 약간 김) |
| 10 | 둘 약함 (목적 일부 혼재 + 분량 김) |
| 5 | 다수 약점. 의사결정자가 길게 검토해야 함 |
| 0 | 목적 혼재, 행동 유도 부재 |

분량 가이드:

| 거래 규모 | 적정 |
|---|---|
| 1천만원 미만 | 1\~2쪽 |
| 1천\~5천만원 | 3\~7쪽 |
| 5천만\~3억 | 7\~15쪽 |
| 3억 이상 | 15\~50쪽 |

## 오탐 주의

- 1천만원 미만 단순 견적은 한 문서가 맞다.
- 상대가 단일 문서 양식(RFP 응답서)을 요구하면 분리하지 않는다.
- 내부 방향성 문서는 전략과 기술 설계가 한 문서에 층으로 있는 것이 의도일 수 있다. 그때는 분리 대신 축 4의 순서(전략 위, 기술 아래)를 본다.
- 사용자가 한 문서를 원하면 분리하지 않고 위계를 강화한다.

## 독자 역량과 설명량 점검

- 해야 할 일 뒤에 독자가 자연히 알아낼 준비 단계나 도구 부재를 덧붙였는가?
- 바로 앞 문장과 같은 뜻의 미확정·미완료 상태를 다시 설명하는가?
- 순서대로 읽을 내용에 장·절 참조를 반복해서 붙이는가?
- 부연이나 참조를 지워도 판단과 실행이 같다면 과잉 설명으로 센다. 빈도는 발견한 문장 수로 기록한다. 비자명한 제약, 운영 위험, 필수 입력, 초보자 튜토리얼의 준비 단계는 제외한다.
