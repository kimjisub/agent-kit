# council - 여러 모델의 독립 답변, 익명 상호 평가, 의장 종합

**로드 시점 - 한 질문에 대해 여러 모델의 답을 받아 비교하고 하나로 종합하고 싶을 때.** 역할을 나눠 모델마다 다른 질문을 주는 일은 오케스트레이션 스킬의 몫이고, 이 스킬은 모두에게 같은 질문을 주고 서로 평가시킨다.

## 목적

**같은 질문에 대한 여러 모델의 답을 출처를 가린 채 서로 평가시켜, 어느 답이 왜 나은지를 근거로 최종 답을 만드는 절차다.** 답을 나란히 놓기만 하면 읽는 사람이 모델 이름에 끌려 판단한다. 출처를 가리고 모델끼리 순위를 매기게 하면 어느 답이 실제로 나은지, 어디서 의견이 갈리는지가 드러나고, 의장은 그 신호를 보고 종합한다.

원본 karpathy/llm-council 은 OpenRouter API 로 모델을 부른다. 이 스킬은 이 기기에 로그인된 CLI 를 읽기 전용으로 부르므로 API 키가 필요 없고 각 구독 한도 안에서 돈다. 어느 CLI 가 깔려 있고 로그인돼 있고 어떤 플랜인지는 기기와 사람마다 다르므로, 시작할 때 실제로 불러 보고 쓸 수 있는 위원만 고른다. 역할 셋(위원, 익명 평가자, 의장)과 순위 형식은 원본을 따랐고, 프롬프트 문구는 원본 저장소에 라이선스가 없어 새로 썼다.

설계 판단, 계획 검토, 의사결정처럼 따질 측면이 여럿인 질문은 관점 단계를 더한다. 관점은 위원들에게서 받아 의장이 정리하고, 정리한 관점 묶음을 모든 위원에게 한 번에 던진다. 의견의 다양성은 모델에서 얻고, 관점은 답이 빠뜨리기 쉬운 측면을 빠짐없이 묻는 데 쓴다. 이렇게 나눈 근거는 아래 "근거" 절에 있다.

아래에서 의장은 이 절차를 돌리는 세션의 모델을 가리킨다. Claude Code 면 Claude, Codex 면 GPT, Hermes 면 그 설정의 모델이다. 의장은 독립 답 하나를 쓰고 마지막에 종합한다.

## 핵심 원칙

1. **질문은 대화를 모르는 사람이 읽어도 서야 한다.** 외부 CLI 는 이 대화를 못 본다. "이거", "아까 그 함수" 가 남은 질문을 보내면 의장만 맥락을 가진 채 답하고, 순위는 맥락 유무를 잰 것이 된다. 필요한 배경, 파일 경로, 제약을 질문 안에 적는다. 적용 -> Step 1
2. **관점은 살필 측면이고 맡을 역할이 아니다.** "2년 운영비" 는 관점이고 "너는 CFO 다" 는 아니다. 역할극은 정확도를 올리지 못하거나 깎고, 겹치는 역할일수록 손해가 크다. 관점마다 답이 다뤄야 할 질문과 틀렸다고 볼 기준을 적는다. 적용 -> Step 2
3. **관점은 위원마다 한 번에 던진다.** 의견이 갈리는 폭은 관점보다 모델 계열에서 크게 나온다. 관점마다 따로 부르면 비용이 관점 수만큼 늘지만 다양성은 그만큼 늘지 않는다. 한 관점을 깊게 파야 할 때만 나눠 부른다. 적용 -> Step 2, Step 4
4. **의장의 답은 다른 답을 보기 전에 쓴다.** 남의 답을 본 뒤 쓰면 독립 답이 아니라 종합이 되고, 평가에서 그 답이 유리해진다. 관점 정리는 위원들의 관점 제안을 보고 하지만, 답은 관점 정리 뒤 남의 답을 보기 전에 쓴다. 적용 -> Step 3
5. **자기 답에 준 표는 세지 않는다.** 모델은 출처를 가려도 자기 답을 알아보고 높게 친다. 실측에서 평가자 넷 중 셋이 자기 답을 1위로 꼽았다. 그래서 의장은 평가에 끼지 않고, 외부 위원의 순위는 자기 답을 뺀 나머지로 평균을 낸다. 적용 -> Step 5
6. **답을 섞지 않고 주장을 고른다.** 1위 답을 그대로 옮기지도, 모든 답을 고르게 버무리지도 않는다. 섞으면 좋은 답이 묽어진다. 주장 단위로 쪼개 어느 모델이 지지하는지 보고, 채택한 주장마다 출처를 남긴다. 적용 -> Step 6
7. **다수가 동의해도 정답이라는 보장은 없다.** 모델들은 같은 오답에 몰리는 경향이 있고, 같은 회사 모델끼리는 더 그렇다. 한 위원만 낸 주장이 맞는 경우도 적지 않다. 소수 주장과 위원끼리 갈린 사실 판단은 직접 확인한 뒤 넣는다. 적용 -> Step 6
8. **빠진 위원을 숨기지 않는다.** 로그인이 안 됐거나 시간 초과로 빠진 위원은 이유와 함께 보고한다. 위원이 둘이면 셋일 때와 같은 무게로 읽히면 안 된다. 적용 -> Step 0, Step 4, Step 6
9. **위원끼리, 그리고 의장과 모델 계열이 겹치지 않는다.** 같은 모델이 두 자리에 앉으면 순위가 한 모델의 의견을 두 번 센 것이 된다. cursor 의 무료 플랜은 다른 회사 모델로 돌고, agy 는 Claude 모델도 고를 수 있어 겹치기 쉽다. 스크립트가 계열을 보고 뒤 순위 위원을 뺀다. 적용 -> Step 0

## 절차

```
0. 위원 파악       scripts/council.py members  - 실제 호출로 로그인, 버전, 플랜, 모델 계열
1. 질문 세우기     run 폴더와 question.md
2. 관점 세우기     scripts/council.py lenses   - 선택. 위원들의 관점 제안을 의장이 lenses.md 로 정리
3. 의장 답         stage1/chair.md
4. 1차 답변        scripts/council.py stage1   - 쓸 수 있는 외부 위원 병렬, 관점 묶음을 한 번에, 읽기 전용
5. 익명 평가       scripts/council.py stage2   - 라벨 섞기, 외부 위원이 순위
6. 의장 종합       주장 지도, final.md 와 보고
```

산출물은 run 폴더 하나에 모인다. 위원 파악 결과는 기기마다 하나인 캐시에 남는다.

```
~/.council/members.json              Step 0, 위원별 상태와 모델. 6시간 동안 재사용
~/.council/runs/<YYYYMMDD-HHMM>-<영문 슬러그>/
  question.md            Step 1
  lenses/<위원>.md       Step 2, 위원별 관점 제안 (관점을 쓸 때만)
  lenses/chair.md        Step 2, 의장의 관점 제안
  lenses.md              Step 2, 의장이 정리한 관점 묶음
  stage1/chair.md        Step 3 (의장이 어느 모델이든 파일 이름은 chair.md)
  stage1/<위원>.md       Step 4, status.json 에 위원별 결과
  stage1/<위원>.lens<N>.md   Step 4, --split-lenses 일 때 관점별 답. <위원>.md 는 이것을 이어 붙인 것
  labels.json            Step 5, Response A.. 와 위원 대응
  stage2/<위원>.md       Step 5, 평가문
  ranking.json           Step 5, 평균 순위와 위원별 순위
  claims.md              Step 6, 주장 지도 (관점을 썼거나 위원이 셋 이상일 때)
  final.md               Step 6
```

### Step 0. 위원 파악 - 이 기기에서 쓸 수 있는 위원

```bash
timeout 400 python3 <이 스킬>/scripts/council.py members [--chair claude]
```

1. 위원마다 한 단어 질문을 읽기 전용으로 실제로 던진다. CLI 의 로그인 상태 명령은 토큰이 만료돼도 로그인됐다고 답하므로 믿지 않는다. 병렬이라 20초 안팎이다.
2. 위원별로 쓸 모델을 고른다. agy 는 Gemini 계열, cursor 는 Composer 를 고른다. 각 CLI 의 기본값이 다른 회사 모델로 갈 수 있어서다. `--model cursor=<id>` 로 바꿀 수 있다.
3. `--chair` 에 의장 계열(`claude`, `gpt`, `gemini`, `grok`)을 준다. 기본은 `claude` 다. 의장과 같은 계열 위원, 그리고 우선순위(codex, antigravity, grok, cursor)에서 앞 위원과 계열이 겹치는 위원은 `skip` 이 된다.
4. 결과는 `use`/`skip` 줄과 `fix:` 줄로 나온다. `fix` 는 사용자가 할 일이다.

| status | 뜻 | fix |
|---|---|---|
| `ok` | 답을 받았다 | - |
| `auth_required` | 로그인 안 됨. 인증 화면이 떠서 즉시 끊었다 | 그 CLI 의 로그인 명령 |
| `auth_expired` | 로그인 기록은 있지만 서버가 401 로 거부 | 다시 로그인 |
| `outdated` | 서버가 CLI 버전을 거부(426 등) | CLI 업데이트 |
| `plan_limited` | 플랜 밖 모델. cursor 무료 플랜은 모델 지정 자체가 막혀 `auto` 만 된다 | 플랜을 올리거나 그 위원을 뺀다 |
| `missing_cli` | CLI 없음 | 설치 |
| `timeout`, `error`, `empty` | 그 밖의 실패. `empty` 는 한 번 다시 묻고도 비었을 때다 | `~/.council/members.json` 의 `detail` 을 본다 |
| `same_family:<계열>` (skip 사유) | 의장이나 앞 위원과 모델 계열이 같다 | 의도한 것이 아니면 `--model` 로 다른 계열을 고른다 |

`fix` 가 로그인이면 사용자에게 그 명령을 직접 실행해 달라고 한다(Claude Code 면 프롬프트에 `!` 를 붙여 그 세션에서 돌린다). 기다리지 않고 쓸 수 있는 위원으로 진행한다. CLI 설치, 화면 없는 기기에서의 로그인, CLI 별 함정은 `references/member-cli-setup.md` 에 있다.

끝나면 `use` 가 하나 이상이다. 0 이면 council 이 아니다. `fix` 를 보고하고 멈춘다.

Step 2 와 Step 4 는 캐시가 없거나 6시간이 지났으면 이 단계를 스스로 먼저 돈다. 사용자가 방금 로그인했으면 `members --only <위원>` 으로 그 위원만 다시 잰다.

### Step 1. 질문 세우기 - 맥락 없이 읽히는 질문

1. run 폴더를 만든다. `RUN=~/.council/runs/$(date +%Y%m%d-%H%M)-<슬러그>`
2. 사용자의 질문을 `question.md` 에 쓴다. 대화에서 정해진 배경, 대상 파일의 절대 경로, 지켜야 할 제약, 원하는 답의 분량을 질문 안에 넣는다. 위원은 `--cwd` 로 준 폴더의 파일을 읽을 수 있으니 코드 질문이면 그 저장소를 `--cwd` 로 잡고 경로를 적는다.
3. 질문을 사용자가 준 문장에서 바꿨으면 바꾼 질문을 보여 주고 진행한다.

질문이 "이거 어때" 처럼 대화에 기대고 있으면 그대로 보내지 않는다. -> 핵심 원칙 1

끝나면 `question.md` 하나만 읽고도 답할 수 있다.

### Step 2. 관점 세우기 - 선택, 따질 측면이 여럿일 때

**쓰는 때:** 설계나 아키텍처 판단, 계획과 기획 검토, 둘 이상의 선택지를 놓고 정하는 질문, 사용자가 "여러 관점으로", "다각도로" 를 요청했을 때. **건너뛰는 때:** 사실 하나를 묻는 질문, 답이 하나로 정해지는 계산이나 디버깅. 이때는 Step 3 으로 간다.

```bash
timeout 1900 python3 <이 스킬>/scripts/council.py lenses "$RUN" --cwd <질문이 가리키는 폴더> [--chair claude]
```

1. 백그라운드로 돌린다. 위원마다 `prompts/lens.md` 로 질문에 답하지 말고 관점 3~6개와 관점별 질문을 내게 해 `lenses/<위원>.md` 에 쓴다.
2. 기다리는 동안 의장도 같은 형식으로 `lenses/chair.md` 를 쓴다. 관점 생성을 모델 하나에 맡기면 그 모델의 사각지대가 관점 목록에 그대로 들어가므로 의장 것도 여러 제안 중 하나로 둔다.
3. 끝나면 의장이 제안들을 합쳐 `lenses.md` 를 쓴다.
   - 3~5개로 줄인다. 한 프롬프트에 관점이 많을수록 관점마다 답이 얕아진다.
   - 뜻이 겹치는 관점은 하나로 합친다. 여러 위원이 낸 관점과, 한 위원만 냈지만 다른 측면을 여는 관점을 함께 남긴다.
   - 관점마다 `## <이름>` 제목, 이 질문에서 중요한 이유, 답이 다뤄야 할 질문 2~4개, 틀렸다고 볼 기준을 적는다. 역할 이름("CTO 관점")은 쓰지 않는다. -> 핵심 원칙 2
   - 관점마다 어느 위원이 냈는지 제목 아래 한 줄로 남긴다(`출처: codex, grok`).
4. 정리한 관점을 사용자에게 한 줄씩 보여 주고 진행한다.

끝나면 `lenses.md` 에 `## ` 로 시작하는 관점이 3~5개 있다.

### Step 3. 의장 답 - 남의 답을 보기 전에

1. `stage1/chair.md` 에 의장의 답을 쓴다. 다른 위원과 같은 조건이 되도록 `question.md` 에 적힌 것을 기준으로 답한다.
2. `lenses.md` 가 있으면 위원과 같은 구조로 쓴다. 관점마다 `## <관점 이름>` 절, 끝에 `## Overall` 절이다(`prompts/member-lenses.md`).
3. 이 파일은 Step 4 가 덮지 않는다. 이름을 `claude.md` 로 쓰지 않는다. 대소문자를 가리지 않는 파일시스템(macOS 기본)에서 Claude Code 가 그 폴더의 `CLAUDE.md` 지시 파일로 읽어 들인다.

끝나면 `stage1/chair.md` 가 있고, 그때까지 외부 위원의 답을 하나도 열지 않았다. -> 핵심 원칙 4

### Step 4. 1차 답변 - 외부 위원 병렬 호출

```bash
timeout 1900 python3 <이 스킬>/scripts/council.py stage1 "$RUN" --cwd <질문이 가리키는 폴더> [--chair claude] [--split-lenses]
```

1. 백그라운드로 돌리고(Claude Code 면 Bash 의 `run_in_background`) 완료 알림을 기다린다. 위원 하나당 기본 900초(`--timeout`)이고 바깥 `timeout` 이 전체 상한이다.
2. `--members` 를 안 주면 Step 0 캐시에서 `use` 인 위원만 부른다. `--members codex,grok` 처럼 주면 캐시를 거치지 않고 그 위원을 부른다. 한 위원만 다시 돌릴 때 쓴다.
3. `lenses.md` 가 있으면 관점 묶음 전체를 프롬프트에 붙여 위원마다 **한 번** 부른다. -> 핵심 원칙 3
4. `--split-lenses` 는 관점마다 따로 불러 `stage1/<위원>.lens<N>.md` 에 쓰고 `<위원>.md` 로 이어 붙인다. 호출 수가 위원 수 x 관점 수라 구독 한도를 그만큼 쓴다. 관점마다 파일을 길게 읽어야 하거나, 묶어 던진 답이 관점을 얕게 다뤘을 때만 쓴다. 이 모드의 답에는 `## Overall` 절이 없다.
5. stderr 의 위원별 한 줄과 마지막 요약 JSON 을 본다. `ok` 가 아닌 위원은 `status.json` 의 `detail` 로 이유를 확인한다. 로그인, 버전, 플랜 문제로 실패한 위원은 캐시에도 반영돼 다음 실행에서 빠진다.

위원은 모두 읽기 전용 모드로 불린다(codex `-s read-only`, agy `--mode plan --sandbox`, grok `--permission-mode plan`, cursor `--mode ask`). cursor 의 `--trust` 는 작업 폴더를 신뢰한다는 확인을 건너뛸 뿐 쓰기 권한을 주지 않는다. 쓰기와 명령 실행은 `--force` 가 있어야 하고 쓰지 않는다. codex 는 사용자 설정의 추론 강도 대신 `high` 로 부른다. 바꾸려면 환경변수 `COUNCIL_CODEX_EFFORT` 를 준다(빈 값이면 사용자 설정을 따른다). status 의 뜻은 Step 0 표와 같다.

끝나면 `stage1/` 에 의장을 포함해 답이 둘 이상 있다. 외부 `ok` 가 0 이면 멈춘다.

### Step 5. 익명 평가 - 외부 위원의 순위

```bash
timeout 1900 python3 <이 스킬>/scripts/council.py stage2 "$RUN" --cwd <Step 4 와 같은 폴더>
```

1. 스크립트가 답의 순서를 섞어 `Response A..` 로 가리고 `labels.json` 에 대응을 남긴다. 의장의 답도 섞인다.
2. Step 4 에서 `ok` 였던 외부 위원만 평가한다. 평가 프롬프트는 `prompts/reviewer.md` 이고 원본 llm-council 의 순위 형식을 따른다.
3. `lenses.md` 가 있으면 평가자에게 관점마다 가장 잘 다룬 답과, 한 답만 낸 주장의 옳고 그름을 함께 적게 한다(`prompts/reviewer-lenses.md`). 순위는 관점 커버리지가 아니라 답 전체로 매긴다.
4. 각 평가문 끝의 `FINAL RANKING:` 을 읽어 `ranking.json` 에 평균 순위(`average_rank`, 낮을수록 좋다)와 위원별 순위를 쓴다. 평균은 평가자가 자기 답에 준 표를 뺀 값이다. 자기 표를 넣은 평균(`average_rank_with_self`)과 평가자마다 자기 답을 몇 위에 뒀는지(`self_rank`)도 함께 남는다.

평가자가 하나뿐이면 순위는 한 모델의 의견이다. 보고에서 그렇게 부른다. -> 핵심 원칙 8

끝나면 `ranking.json` 이 있고 평가자마다 순위가 파싱됐다. 파싱된 순위가 빈 평가자는 평가문을 직접 읽어 보고에 적는다.

### Step 6. 의장 종합 - 주장 지도, 최종 답과 보고

1. `stage1/*.md`, `stage2/*.md`, `ranking.json`, `labels.json` 을 읽는다.
2. 원본 의장 프롬프트가 보라는 셋을 본다. 각 답의 통찰, 상호 순위가 말하는 품질, 위원 간 합의와 불일치.
3. 관점을 썼거나 위원이 셋 이상이면 `claims.md` 에 주장 지도를 만든다. 답을 주장 단위로 쪼개 한 줄씩 적고, 주장마다 지지한 위원(관점을 썼으면 어느 관점에서)과 반대한 위원을 단다. 주장은 세 갈래로 나눈다.
   - 여러 계열이 지지한 주장. 지지한 위원이 같은 회사 모델뿐이면 이 갈래로 치지 않는다.
   - 한 관점에서만 나온 주장. 그 관점이 아니면 안 보였던 것이다.
   - 한 위원만 낸 주장, 그리고 위원끼리 갈린 사실 판단. 평가문이 이 주장을 어떻게 봤는지 함께 적는다.
4. 세 번째 갈래는 문서, 코드, 실행으로 확인한 뒤 채택하거나 버린다. 확인 못 하면 확인 못 했다고 쓴다. 첫 번째 갈래도 결론을 좌우하는 사실이면 같은 수준으로 확인한다. -> 핵심 원칙 7
5. `final.md` 에 최종 답을 쓴다. 답들을 버무리지 않고 확인을 거친 주장을 골라 세운다. 결론을 좌우하는 주장에는 어느 위원, 어느 관점에서 왔는지 남긴다. -> 핵심 원칙 6
6. 사용자에게 아래 형식으로 보고한다.

```markdown
<최종 답. 질문에 대한 답 자체를 먼저>

**위원회 결과**
| 위원 | 평균 순위 | 비고 |
|---|---|---|
| codex | 1.0 | ... |

- 관점: <쓴 관점과, 관점별로 가장 잘 다룬 위원> (관점을 썼을 때)
- 합의: <여러 계열이 같이 짚은 것>
- 소수 의견: <한 위원만 낸 주장, 확인 결과, 채택 여부>
- 갈린 지점: <무엇이 갈렸고 의장이 어느 쪽을 왜 택했나>
- 빠진 위원: <위원, 이유, fix>
- 기록: `<run 폴더>`
```

끝나면 `final.md` 가 있고, 보고에 소수 의견의 확인 결과, 빠진 위원, 갈린 지점이 들어 있다.

## 근거

관점 단계와 종합 규칙은 다중 모델 의견 수렴 연구에서 가져왔다. 2026년 논문 일부는 초록 기준이다.

- 다양성은 모델에서 나온다. 서로 다른 모델의 답이 같은 모델 여러 개보다 크게 기여한다(ReConcile, ACL 2024. Mixture-of-Agents, ICLR 2025). 페르소나는 정확도를 거의 올리지 못하거나 낮추고, 겹치는 페르소나일수록 손해가 크다(Zheng et al., EMNLP 2024 Findings. Beyond Symmetric Agents, 2026). 역할 대신 풀이 전략을 다르게 주는 편이 낫다(DMAD, ICLR 2025). -> 핵심 원칙 2, 3
- 관점은 따로 발견한다. 관점을 먼저 뽑고 관점별 질문을 만들면 바로 묻는 것보다 넓게 다룬다(STORM, NAACL 2024). -> Step 2
- 효과의 대부분은 첫 독립 답에서 나온다. 토론 효과의 대부분은 첫 답의 다수결로 설명되고(Debate or Vote, NeurIPS 2025), 토론을 거듭하면 의견이 쏠리고 다양성이 준다(Creative-MAD, EMNLP 2026. DEAR, NeurIPS 2026). 그래서 이 스킬은 토론 라운드를 두지 않는다. -> 핵심 원칙 4
- 다수는 틀릴 수 있다. 두 모델이 함께 틀릴 때 같은 오답을 고르는 비율이 높고, 같은 회사 모델일수록 더 그렇다(Correlated Errors, ICML 2025). 의견이 갈린 사례의 약 4분의 1에서 소수가 맞았다(Minority Sentinel, 2026). -> 핵심 원칙 7
- 섞기보다 고르기. 답을 하나로 합성하면 심판이 하나를 고르는 방식보다 크게 떨어진다(When Agents Disagree, 2026). 계열이 다른 심판 패널은 자기 답 선호를 줄인다(PoLL, 2024). 출처를 가려도 모델은 자기 글을 알아보고 높게 친다(Panickssery et al., NeurIPS 2024). -> 핵심 원칙 5, 6

## 산출

run 폴더 하나(`~/.council/runs/<...>/`), 위원 캐시(`~/.council/members.json`), 사용자에게 하는 보고. 스킬 저장소에는 아무것도 쓰지 않는다.

## 스킬 생태계에서의 위치

- **역할을 나누는 오케스트레이션** - 요청을 나눠 모델마다 다른 질문을 주고 종합한다. 상호 평가가 없다. 일을 나눠 맡기고 싶으면 그쪽, 같은 질문의 답을 견주고 싶으면 이 스킬이다. 이 스킬의 관점 단계는 모든 위원에게 같은 관점 묶음을 준다.
- **페르소나별 리뷰** - 산출물을 면접관, CTO 같은 페르소나로 리뷰받는 일이다. 이 스킬은 페르소나 대신 살필 측면(관점)을 질문으로 준다.
- **원본 karpathy/llm-council** - 웹앱과 OpenRouter. 역할 셋과 순위 형식, 순위 파싱 규칙(`parse_ranking`)을 따랐다.
