# spec: 내용 구조 가이드

## 작성 원칙

1. **구현자가 문서만 보고 구현할 수 있어야 한다.** 필드 이름, 타입, 필수 여부, 허용 값, 예시가 모두 있어야 한다.
2. **필드는 표로, 전체 모양은 예시로.** 필드 표(이름, 타입, 필수, 설명)와 예시 JSON 을 함께 둔다. 둘이 어긋나면 안 된다.
3. **미정을 숨기지 않는다.** 정해지지 않은 값은 `open` 상자로 드러내고, 누가 언제까지 정하는지 적는다.
4. **양쪽의 몫을 가른다.** 우리가 제공하는 것과 상대가 구현해야 하는 것을 따로 적는다.
5. **상태를 항목마다 표시한다.** 구현 예정이거나 합의 대기인 항목은 `badge` 로 표시한다.
6. **한 개념은 한 이름으로.** 필드 이름과 본문의 호칭을 섞지 않는다(`order_id` 를 본문에서 "주문번호", "오더 ID"로 번갈아 부르지 않는다).

## 결정 공란

작성 전에 아래 공란을 사용자와 해소한다(문법: [conventions.md](../../conventions.md#결정-공란ask)).

@ASK(spec-status): 이 명세는 지금 어느 단계인가요? [초안(합의 대기) | 합의 완료 | 구현 반영 완료]
> 표지 버전 줄과 본문의 상태 표시 밀도가 달라집니다. 초안이면 미확정 절이 필수이고, 구현 반영 완료면 `badge` 가 남아 있으면 안 됩니다.

@ASK(implementer-side): 이 명세대로 누가 구현하나요? [상대측이 구현 | 우리가 구현 | 양측이 나눠 구현]
> "상대측 구현 항목" 절의 유무와 무게가 달라집니다.

@ASK(auth-scheme): 인증과 서명 방식이 정해졌나요? [정해짐(방식 알려주기) | 미정(미확정 절에 둔다)]
> 공통 규약 절의 인증 항목에 들어갑니다. 미정이면 후보 방식을 `open` 상자에 적습니다.

## 권장 본문 흐름

| 절 | 내용 | 쓰는 컴포넌트 |
|---|---|---|
| 1. 개요와 범위 | 목적, 연동 방향, 현재 상태, 범위 밖 | `summary`(라벨 "개요") |
| 2. 연동 방식 | push(Webhook), pull(조회 API), 파일 등 채널 구분과 흐름 | 연동 채널 표, `pre` |
| 3. 공통 규약 | 전송, 인증, 서명, 헤더, 멱등성, 재시도, 시간 형식, 인코딩, 오류 형식 | 표, 오류 응답 표 |
| 4. 이벤트, 엔드포인트 명세 | 항목마다 엔드포인트, 필드 표, 예시 | `endpoint`, `table.fields`, `pre` |
| 5. 상대측 구현 항목 | 받는 쪽이 구현할 것 체크리스트 | 목록 |
| 6. 미확정, 합의 필요 | 정해지지 않은 항목, 결정 주체, 기한 | `open` |
| 부록 | 변경 이력, 용어 | 변경 이력 표 |

### 1. 개요와 범위
- `summary` 하나에 목적 한 문장, 연동 방향(A 에서 B 로), 현재 상태(`spec-status`), 범위 밖 항목을 적는다.

### 2. 연동 방식
- 채널마다 방향, 트리거, 빈도를 표로 쓴다.
- 흐름이 셋 이상 오가면 순서를 번호 목록이나 `pre` 안의 텍스트 도식으로 보인다. 화살표는 `->` 로 쓴다.

```html
<pre><code>주문 시스템 -> (POST /webhooks/shipments) -> 물류 시스템
물류 시스템 -> 200 OK (5초 이내)
주문 시스템 -> (GET /shipments/{id}) -> 물류 시스템   # 결과 조회</code></pre>
```

### 3. 공통 규약
- 모든 엔드포인트에 공통인 것은 여기에 한 번만 쓴다. 엔드포인트 절에서 반복하지 않는다.
- 시간 형식(예: ISO 8601, UTC), 문자 인코딩, 숫자 단위(원, 그램, 밀리초)를 명시한다.
- 오류 응답 형식과 상태 코드 표를 둔다.
- 재시도 정책(횟수, 간격)과 멱등성 키를 적는다.

### 4. 이벤트, 엔드포인트 명세
항목마다 같은 순서로 쓴다.
1. `endpoint` 한 줄(메서드와 경로, 또는 이벤트 이름). 메서드 배지는 메서드와 맞춘다. 구현 전이면 줄 끝에 `badge`
2. 한 문장 설명: 언제 호출되거나 발생하는지
3. 필드 표(`table.fields`): 이름, 타입, 필수, 설명(허용 값, 단위 포함)
4. 요청과 응답 예시 JSON(`pre`)
5. 오류 경우가 이 항목에만 있으면 그 표

### 5. 상대측 구현 항목
- 받는 쪽이 구현해야 할 것을 체크리스트로 쓴다(수신 엔드포인트, 서명 검증, 중복 처리, 응답 시간).

### 6. 미확정 사항
- `open` 상자 하나에 항목 하나. 무엇이 미정인지, 선택지, 결정 주체, 기한을 적는다.
- 본문 중간의 미정 값에도 `badge` 를 달고 이 절을 가리킨다.

## 필드 표와 예시

필드 표는 `table.fields` 로, 열은 필드, 타입, 필수, 설명 순서다.

| 필드 | 타입 | 필수 | 설명 |
|---|---|---|---|
| `shipment_id` | string | 예 | 출고 건 식별자. 최대 32자 |
| `weight_g` | integer | 예 | 총중량. 단위 그램 |
| `requested_at` | string | 예 | ISO 8601, UTC |
| `items[].sku` | string | 조건부 | `items` 가 있으면 필수 |

- 타입은 JSON 타입(string, integer, number, boolean, object, array)으로 쓴다. 날짜는 string 에 형식을 적는다.
- 필수 칸은 `예`, `아니오`, `조건부` 중 하나. 조건부면 설명에 조건을 쓴다.
- 중첩 객체는 `items[].sku` 처럼 경로로 쓴다.

예시 JSON 은 `<pre><code>` 로 쓰고 들여쓰기는 2칸이다. 예시 값은 실제처럼 보이되 실제 고객 데이터가 아니어야 한다. 필드 표에 있는 필드와 예시의 필드가 같아야 한다.

```html
<pre><code>{
  "shipment_id": "SHP-20261015-0001",
  "weight_g": 12500,
  "requested_at": "2026-10-15T01:20:00Z"
}</code></pre>
```

## 표 패턴

### 연동 채널 표

| 채널 | 방향 | 트리거 | 빈도 |
|---|---|---|---|
| 출고 Webhook | 주문 -> 물류 | 주문 확정 | 건당, 일 2,000건 |

### 오류 응답 표

| 상태 코드 | 오류 코드 | 뜻 | 보내는 쪽 조치 |
|---|---|---|---|
| 409 | `DUPLICATE_SHIPMENT` | 같은 멱등성 키로 이미 처리됨 | 재시도하지 않는다 |

### 변경 이력 표(부록)

| 버전 | 날짜 | 변경 |
|---|---|---|
| v0.1 | 2026-10-15 | 초안 |

## 표지 변수

```bash
KIND=spec [LAYOUT=a4|web] [BRAND=<brand>] <변수...> bash scripts/build.sh scaffold <문서 폴더>
```

표지 메타 라벨은 [kind.md](kind.md) 의 `labels` 가 정한다. 변수와 라벨의 짝은 이렇다.

| 변수 | 표지 라벨 | 예시 |
|---|---|---|
| `CATEGORY` | 카테고리 | 비우면 `INTERFACE SPEC`. 연동이 아닌 기술 명세는 `TECHNICAL SPEC` |
| `DOC_TITLE` | 탭 제목 | `출고 연동 인터페이스 명세서` |
| `DOC_HEADER` | 러닝 헤더 | `출고 연동 명세 v0.1`(버전을 넣는다) |
| `SUBTITLE` | 부제 | `Webhook, 조회 API 규격` |
| `COVER_TITLE` | 메인 제목(`<br>` 가능) | `출고 연동<br>인터페이스 명세서` |
| `COVER_FROM` | 작성 | 명세를 쓴 쪽. 비우면 브랜드 기본값 |
| `COVER_TO` | 수신 구현 | `물류 시스템 개발팀(구현 예정)` |
| `COVER_TARGET` | 연동 대상 | `주문 시스템 <-> 물류 시스템` |
| `COVER_PERIOD` | 버전 | `v0.1, 초안(합의 대기)`. 번호와 상태를 함께 |
| `COVER_OWNER` | 작성자 | 작성자. 비우면 표지에서 생략 |
| `COVER_CONFIDENTIAL` | 기밀 조항 | 필요할 때만. 비우면 브랜드 기본값, 브랜드도 비면 상자가 사라진다 |

`COVER_TARGET` 의 양방향 표시는 `<->` 를 그대로 쓴다. 화살표 기호로 바꾸지 않는다.

## 호출 예시

```bash
DOC_TITLE="출고 연동 인터페이스 명세서" \
SUBTITLE="Webhook, 조회 API 규격" \
DOC_HEADER="출고 연동 명세 v0.1" \
COVER_TITLE="출고 연동<br>인터페이스 명세서" \
COVER_TARGET="주문 시스템 <-> 물류 시스템" \
COVER_TO="물류 시스템 개발팀(구현 예정)" \
COVER_PERIOD="v0.1, 초안(합의 대기)" \
KIND=spec bash <skill-dir>/scripts/build.sh scaffold "/path/to/명세서"

# <명세서>.html 의 본문 자리에 본문 HTML 을 작성한 뒤
bash <skill-dir>/scripts/build.sh pdf "/path/to/명세서"
```

화면용으로 뽑으려면 `LAYOUT=web` 을 붙인다. a4 컴포넌트 마크업은 [a4 layout.md](../../layouts/a4/layout.md#컴포넌트-카탈로그) 에 있다.
