# spec: 내용과 문체 검증 체크리스트

표현(컴포넌트, 표, 코드 블록, 쪽 경계, 표지 렌더) 검증은 고른 레이아웃의 `layouts/<layout>/review.md` 다(a4 는 [a4 review.md](../../layouts/a4/review.md)). 문체의 베이스는 `brands/<brand>/voice.md` 다. 아래는 spec 의 내용과 톤 항목이다.

## 구현 가능성

- [ ] 구현자가 이 문서만 보고 요청을 보내고 받을 수 있다
- [ ] 모든 엔드포인트에 `endpoint` 한 줄(메서드, 경로), 설명, 필드 표, 예시가 이 순서로 있다
- [ ] 필드마다 타입, 필수 여부, 허용 값이나 단위가 있다
- [ ] 필드 표의 필수 칸이 `예`, `아니오`, `조건부` 중 하나다
- [ ] 필드 표와 예시 JSON 의 필드가 같다(이름, 타입, 누락)
- [ ] 예시 JSON 이 문법상 유효하고 들여쓰기 2칸이다
- [ ] 예시 값에 실제 고객 데이터가 없다

## 공통 규약

- [ ] 인증과 서명 방식이 적혔거나 `open` 에 올라 있다
- [ ] 시간 형식, 시간대, 인코딩, 숫자 단위가 명시됐다
- [ ] 재시도 정책과 멱등성 기준이 있다
- [ ] 오류 응답 형식과 상태 코드 표가 있다
- [ ] 공통 규약이 엔드포인트 절에서 반복되지 않는다

## 분담과 상태

- [ ] `summary` 가 1절에 하나만 있고 목적, 방향, 상태, 범위 밖이 적혔다
- [ ] 우리가 제공하는 것과 상대가 구현할 것이 나뉘어 있다(`implementer-side` 결정대로)
- [ ] 구현 예정, 합의 대기 항목에 `badge` 가 있다
- [ ] `spec-status` 가 구현 반영 완료면 `badge` 와 `open` 이 남아 있지 않다

## 미확정

- [ ] 미정 값이 숨지 않고 `open` 상자로 드러나 있다
- [ ] `open` 상자 하나에 항목이 하나이고, 선택지, 결정 주체, 기한이 있다
- [ ] 본문의 미정 값이 미확정 절을 가리킨다

## 일관성

- [ ] 한 개념을 한 이름으로 불렀다(필드 이름과 본문 호칭이 같다)
- [ ] 표지 버전과 부록 변경 이력의 최신 버전이 같다
- [ ] 결정 공란(`@ASK`)이 남은 채 본문을 쓰지 않았다

## 표지 값

- [ ] `CATEGORY` 가 `INTERFACE SPEC` 이나 `TECHNICAL SPEC` 계열이다
- [ ] 버전(`COVER_PERIOD`)에 번호와 상태가 함께 있다
- [ ] 러닝 헤더(`DOC_HEADER`)에 버전이 있다

## 톤: 건조하고 정확하게

spec 은 voice.md 기조에서 설득을 모두 뺀다. 형용사 대신 값과 조건을 쓴다.

- [ ] "빠르게", "안정적으로" 대신 수치(응답 5초 이내, 재시도 3회)를 썼다
- [ ] "해야 한다", "할 수 있다"를 구분해 썼다(필수와 선택)
- [ ] 필드 이름, 경로, 헤더 이름을 인라인 코드로 썼다
- [ ] 이모지와 느낌표가 없다
