# spec: 연동, 기술 명세서

시스템 사이의 연동 규격(API, Webhook, 데이터 포맷)을 **양쪽이 합의하고 그대로 구현할 수 있게** 적는 문서다. "무엇을 어떤 형식으로 주고받는가"가 본질이다.

## 쓰는 자리

- 두 시스템의 연동 인터페이스를 확정하고 공유할 때
- 기획 단계에서 미리 합의해야 할 API, Webhook 규격을 문서로 남길 때
- 일부가 아직 구현 전이면 항목마다 상태(구현 예정, 합의 대기, 미확정)를 표시한다
- 예: 주문 시스템과 물류 시스템 사이의 출고 Webhook 명세, 외부 파트너용 조회 API 명세, 데이터 내보내기 파일 포맷 명세

## 다른 종류와의 차이

| 종류 | 핵심 질문 | 목적 |
|---|---|---|
| **spec** | "무엇을 어떤 형식으로 주고받나?" | 구현 규격 합의. 정확성이 전부 |
| manual | "어떻게 쓰고, 문제가 생기면 어떻게 하나?" | 운영자를 위한 사용 안내 |
| proposal | "왜 이것을 해야 하나?" | 설득 |
| analysis | "무엇을 확인했나?" | 사실과 근거 기록 |

연동을 하자고 설득하는 단계면 proposal 이고, 하기로 한 뒤 규격을 정하는 단계면 spec 이다.

## 이 폴더 구성

| 파일 | 역할 |
|---|---|
| `kind.md` | 이 문서. 정체성, 다른 종류와의 차이, 레이아웃별 차이 |
| [structure.md](structure.md) | 작성 원칙, 권장 본문 흐름, 항목별 순서와 표 패턴, 결정 공란, 표지 변수, 호출 예시 |
| [inputs.md](inputs.md) | 작성 전에 갖춰야 할 재료 체크리스트 |
| [review.md](review.md) | 내용과 문체 검증 체크리스트 |

문체의 베이스는 `brands/<brand>/voice.md`, 표현(컴포넌트, 쪽, 표지)은 고른 레이아웃의 `layouts/<layout>/layout.md` 다. 이 폴더는 spec 에서 달라지는 내용만 적는다.

## 레이아웃별 차이

| 레이아웃 | 언제 | 달라지는 점 |
|---|---|---|
| `a4`(기본) | 버전을 매겨 양측이 합의 문서로 주고받는 명세 | [structure.md](structure.md) 의 흐름 그대로. 긴 예시 JSON 은 쪽 경계에서 나눠 싣는다 |
| `web` | 구현자가 화면에 띄워 두고 엔드포인트를 찾아 읽는 명세 | 절이 장이 되어 옆 목차에 뜨고, 엔드포인트마다 소절 제목을 달아 목차에서 바로 찾게 한다. 쪽 경계 걱정 없이 예시를 통째로 싣는다. 흐름과 컴포넌트 이름은 같다 |

web 의 장 구성과 컴포넌트는 `layouts/web/layout.md` 에 있다. 거기에 없는 컴포넌트는 그 카탈로그의 같은 뜻 컴포넌트로 바꿔 쓴다.
