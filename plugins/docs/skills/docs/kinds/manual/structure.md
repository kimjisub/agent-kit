# manual: 내용 구조 가이드

## 작성 원칙

1. **사용자 관점만 쓴다.** 빌드, 코드, 내부 구현은 뺀다. 화면에 보이는 것과 누를 것을 중심으로 쓴다.
2. **쓰는 순서대로 쓴다.** 켜기, 최초 설정, 화면 보는 법, 평소 운영, 운영 도구, 문제 대응, 자주 묻는 질문, 문의 순서다.
3. **쉬운 말로 쓴다.** 전문 용어는 풀어 쓰고, 꼭 필요하면 처음 나올 때 한 번 설명한다.
4. **한 단계에 한 동작을 쓴다.** "설정을 열고 값을 바꾼 뒤 저장합니다"는 세 단계로 나눈다.
5. **화면의 글자를 그대로 쓴다.** 버튼과 메뉴 이름은 화면 표기와 똑같이, 굵게 쓴다(예: **저장** 버튼).
6. **문제 대응을 반드시 넣는다.** "이런 증상이면 이렇게" 표가 사용 설명서의 가치 대부분이다.

## 결정 공란

작성 전에 아래 공란을 사용자와 해소한다(문법: [conventions.md](../../conventions.md#결정-공란ask)).

@ASK(reader-level): 이 설명서를 누가 읽나요? [개발자가 아닌 현장 운영자 | 사내 IT 담당자 | 개발자]
> 독자에 따라 용어를 풀어 쓰는 정도와 문제 대응의 깊이가 달라집니다. 현장 운영자면 1차 대응까지만 쓰고 나머지는 문의로 넘깁니다.

@ASK(support-contact): 문제가 해결되지 않을 때 어디로 문의하나요? 연락처와 응답 시간을 알려 주세요.
> 마지막 절(문의와 지원)에 그대로 들어갑니다. 정해지지 않았으면 본문에 "미정"으로 두지 말고 이 답을 먼저 받습니다.

@ASK(capture-source): 화면 캡처를 넣을까요? [넣는다(캡처 제공) | 넣지 않는다(글과 표로만)]
> 넣으면 번들의 `assets/` 에 두고 `src="assets/..."` 로 참조합니다.

## 권장 본문 흐름

| 절 | 내용 | 쓰는 컴포넌트 |
|---|---|---|
| 1. 이 프로그램은 무엇인가 | 한 문단 소개와 "한눈에" 요약 | `summary`(라벨 "한눈에") |
| 2. 시작하기 | 켜기, 최초 설정 | `step`, `tip`, `warn` |
| 3. 화면 보는 법 | 상태 표시, 수치, 버튼의 뜻 | 화면 영역 표, `metrics` |
| 4. 설정 항목 | 항목, 기본값, 바꾸면 달라지는 것 | 설정 항목 표 |
| 5. 평소 운영 | 매일, 매주 할 일과 손대지 않아도 되는 것 | `step`, `note` |
| 6. 운영 도구 | 언제 쓰고 어떻게 쓰나 | `step`, `warn` |
| 7. 문제가 생기면 | 증상, 원인, 조치 | 문제 대응 표, `warn` |
| 8. 자주 묻는 질문 | 질문과 짧은 답 | `h3` + 문단 |
| 9. 문의와 지원 | `support-contact` 의 답, 계약 조건 | 문단, 표 |

없는 절은 뺀다. 순서는 바꾸지 않는다.

### 절별 컴포넌트 배치

- `summary` 는 1절에 하나만 둔다.
- 절차는 `step` 으로 쓰고, 단계 번호는 절마다 1부터 다시 센다. 한 단계에 동작이 둘이면 나눈다.
- `tip` 은 알면 편하지만 몰라도 진행에 지장 없는 것에, `warn` 은 되돌릴 수 없거나 장애로 이어지는 동작 앞에만 쓴다. 남발하지 않는다.
- `warn` 은 결과를 쓴다("설정이 지워집니다"). "조심하세요"만 쓰면 무엇을 조심할지 모른다.
- `metrics` 는 화면의 상태 수치를 설명할 때 쓰고, 라벨에 정상 범위를 함께 적는다(예: "전송 대기(정상: 0)").
- `note` 는 표나 절차 바로 아래의 참고에 쓴다.

### 1. 이 프로그램은 무엇인가
- 첫 문장에 "무엇을 하는 프로그램인지"를 쓴다.
- `summary` 상자에 할 수 있는 일 3\~5개와 운영자가 매일 할 일을 요약한다.

### 2. 시작하기
- 켜는 방법부터 최초 설정 완료까지를 `step` 으로 번호를 붙여 쓴다.
- 단계마다 "되었는지 확인하는 방법"(표시등, 화면 문구)을 붙인다.
- 되돌릴 수 없는 동작(초기화, 삭제) 앞에는 `warn` 을 둔다.

### 3. 화면 보는 법
- 화면 영역별로 무엇이 보이는지 표로 쓴다.
- 상태 색이나 수치가 있으면 "정상 범위"와 "이상일 때"를 함께 적는다.

### 4. 설정 항목
- 항목, 기본값, 범위, 바꾸면 달라지는 것을 표로 쓴다.
- 운영자가 바꾸면 안 되는 항목은 따로 표시한다.

### 5. 평소 운영
- 무인으로 도는 부분과 사람이 확인할 부분을 나눈다.
- 확인 주기(매일, 매주)를 적는다.

### 7. 문제가 생기면
- 증상, 원인, 조치 3열 표로 쓴다. 증상은 운영자가 화면에서 보는 말로 쓴다.
- 조치로 해결되지 않으면 무엇을 적어 문의할지(화면 캡처, 발생 시각, 오류 문구)를 적는다.

## 표 패턴

### 화면 영역 표

| 영역 | 보이는 것 | 이럴 때 확인 |
|---|---|---|
| 오른쪽 위 상태 표시등 | 동기화 상태(초록, 주황, 빨강) | 아침 출근 직후 |

### 설정 항목 표

| 항목 | 기본값 | 범위 | 바꾸면 |
|---|---|---|---|
| 동기화 주기 | 30분 | 10\~120분 | 짧을수록 최신이지만 매장 회선 사용량이 는다 |

운영자가 바꾸면 안 되는 항목은 "바꾸면" 칸에 "바꾸지 않습니다(문의)"로 쓴다.

### 문제 대응 표

| 증상 | 원인 | 조치 |
|---|---|---|
| 상태 표시등이 빨간색 | 네트워크 끊김 | 랜선을 뽑았다 다시 꽂고 1분 기다립니다 |

증상 칸은 운영자가 보는 말로, 조치 칸은 동작으로 쓴다. 조치가 3단계를 넘으면 표 아래 `step` 으로 푼다.

## 화면 캡처

`capture-source` 가 "넣는다"면 캡처를 번들 `assets/` 에 두고 `<img src="assets/파일명.png" alt="..">` 로 넣는다. 캡처 바로 아래에 무엇을 보라는 것인지 한 줄을 쓴다.

## 독자별 조정

| `reader-level` | 조정 |
|---|---|
| 현장 운영자 | 용어를 모두 풀어 쓴다. 문제 대응은 1차 조치까지, 그 뒤는 문의 |
| 사내 IT 담당자 | 로그 위치, 재시작 절차, 설정 파일 위치까지 쓴다 |
| 개발자 | 명령어와 설정 키를 그대로 쓴다. 구현 설명은 spec 으로 넘긴다 |

## 표지 변수

```bash
KIND=manual [LAYOUT=a4|web] [BRAND=<brand>] <변수...> bash scripts/build.sh scaffold <문서 폴더>
```

표지 메타 라벨은 [kind.md](kind.md) 의 `labels` 가 정한다. 변수와 라벨의 짝은 이렇다.

| 변수 | 표지 라벨 | 예시 |
|---|---|---|
| `CATEGORY` | 카테고리 | 비우면 `USER MANUAL`. `USER MANUAL / 사용 설명서` |
| `DOC_TITLE` | 탭 제목 | `재고 관리 프로그램 사용 설명서` |
| `DOC_HEADER` | 러닝 헤더 | `재고 관리 프로그램 사용 설명서` |
| `SUBTITLE` | 부제 | `설치, 운영, 문제 대응 안내` |
| `COVER_TITLE` | 메인 제목(`<br>` 가능) | `재고 관리 프로그램<br>사용 설명서` |
| `COVER_FROM` | 제공 | 제품을 제공하는 주체. 비우면 브랜드 기본값 |
| `COVER_TO` | 대상 독자 | `매장 운영 담당자` |
| `COVER_TARGET` | 대상 제품 | `재고 관리 프로그램 v2` |
| `COVER_PERIOD` | 버전 | `v1.0, 2026-10` |
| `COVER_OWNER` | 작성 | 작성자. 비우면 표지에서 생략 |
| `COVER_CONFIDENTIAL` | 기밀 조항 | 필요할 때만. 비우면 브랜드 기본값, 브랜드도 비면 상자가 사라진다 |

## 호출 예시

```bash
DOC_TITLE="재고 관리 프로그램 사용 설명서" \
SUBTITLE="설치, 운영, 문제 대응 안내" \
DOC_HEADER="재고 관리 프로그램 사용 설명서" \
COVER_TITLE="재고 관리 프로그램<br>사용 설명서" \
COVER_TARGET="재고 관리 프로그램 v2" \
COVER_TO="매장 운영 담당자" \
COVER_PERIOD="v1.0, 2026-10" \
KIND=manual bash <skill-dir>/scripts/build.sh scaffold "/path/to/사용설명서"

# <사용설명서>.html 의 본문 자리에 본문 HTML 을 작성한 뒤
bash <skill-dir>/scripts/build.sh pdf "/path/to/사용설명서"
```

화면용으로 뽑으려면 `LAYOUT=web` 을 붙인다. a4 컴포넌트 마크업은 [a4 layout.md](../../layouts/a4/layout.md#컴포넌트-카탈로그) 에 있다.
