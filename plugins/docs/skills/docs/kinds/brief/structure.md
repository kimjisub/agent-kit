# brief: 내용 구조 가이드

## 순서의 원리

받는 사람이 처음 찾는 것은 "내가 무엇을, 어디까지, 언제 만드나"다. 그것을 첫 쪽에 두고, 판단 재료(우리는 누구인가, 원하는 방향, 참고 자료)를 뒤에 둔다. 회사 소개로 시작하면 받는 사람은 자기 일을 찾으려고 몇 쪽을 넘긴다.

## 결정 공란

작성 전에 사용자와 푼다(문법: [conventions.md](../../conventions.md#결정-공란ask)).

@ASK(contract-source): 범위와 일정의 정본은 무엇인가요? [서명한 계약서 | 계약 조건 메시지 | 아직 없음]
> 계약서가 있으면 결과물 목록, 번호, 일정, 비용 조건을 그대로 따릅니다. 이 문서는 계약서를 풀어 쓰는 것이지 새 조건을 더하는 것이 아닙니다.

@ASK(anchoring): 우리가 먼저 그려 본 시안이나 정해 둔 색을 보여 줄까요? [보여 주지 않는다 | 방향 참고로만 보여 준다]
> 우리 시안은 작업자의 출발점을 좁힙니다. 기본은 보여 주지 않고, 외부 레퍼런스와 규격, 원하는 인상으로 방향을 전합니다.

@ASK(fee-scale): 이번 대가에 맞는 작업량은 어디까지인가요? [계약 결과물만 | 계약 결과물과 가벼운 제안]
> 대가에 비해 요구가 많으면 안 됩니다. 계약 밖의 적용(명함 배치, 화면 적용 등)은 우리가 하고 피드백만 부탁하거나, 후속 계약 거리로 둡니다.

## 표준 절 구성

| 절 | 내용 | 쓰는 컴포넌트 |
|---|---|---|
| 제목과 맥락 | 회사가 어떤 상태에서(막 설립, 리뉴얼 등) 무엇을 의뢰하는지 두 문단. 정해진 것이 없으면 없다고 쓰고 함께 가닥을 잡자고 쓴다 | 첫 쪽 `h1`, `lead` 문단 |
| 의뢰 범위 | 계약서 결과물을 같은 번호로 한 줄씩. 표 아래 일정 한 줄 | 표 |
| 회사 소개 | 업종이 낯선 독자를 위해 업종이 하는 일 한 문단, 우리가 다른 점 서너 개, 브랜드를 보게 될 사람 | 문단, 나란한 항목 목록 |
| 떠올리게 하는 것 | 이름의 뜻, 일과 가치처럼 형태와 질감의 단서가 될 말. 묶음별 목록 | 묶음 목록 |
| 원하는 인상 | 지향, 지양, 핵심 글자 같은 제약을 문장으로 | 문단 |
| 스타일 방향 | 두 끝을 잇는 축 위의 점 세 개 안팎 | 스펙트럼 |
| 레퍼런스 | 외부 사례를 갈래로 묶어 서너 개씩. "따라 해 달라는 뜻이 아니라 결을 보여 드리는 예" | 그림 격자 |
| 규격 | 쓰이는 자리에서 나오는 제약(정사각, 최소 크기, 원형 잘림, 단색) | 도식, 문단 |
| 결과물 상세 | 결과물마다 부탁 문단, 목업, 규격 예시 | 문단, 목업 그림, 예시 표 |
| 마치며 | 조율이 필요하면 편하게 말해 달라는 말과 감사 한두 문장 | 문단 |

넣지 않는 절이 있다.

- **진행 방식**: 계약하면 시작하고 시안을 받으면 의견을 모아 회신한다는 것은 받는 사람이 이미 안다. 계약서에 없는 날짜나 조건만 적는다.
- **우리가 드리는 것**: 이 문서 자체가 드리는 것이다. 기다릴 필요 없는 항목(가상 정보로 작업할 수 있는 명함 정보 등)은 그 결과물 안에 한 줄로 둔다.
- **최종 결정자, 내부 결재 구조, 팀 내부의 상징과 문화**: 작업자의 일을 바꾸지 않는다.
- **업계 경쟁사 현황**: 원하는 인상과 레퍼런스가 같은 일을 더 짧게 한다. 사용자가 원할 때만.

## 절별 작성 포인트

### 제목과 맥락
- 첫 쪽이 비어 보이면 요약 상자로 채우지 말고 다음 절(회사 소개)을 당긴다. 요약은 뒤와 같은 말을 반복한다.
- 공고를 냈다면 공고의 말과 맞춘다(결과물 이름, 일정, "의견 환영" 같은 태도).

### 의뢰 범위
- 계약서의 결과물 번호와 이름을 그대로 쓴다. 의뢰서에서 결과물을 합치거나 빼면 계약서와 어긋난다. 범위를 바꾸려면 계약을 먼저 바꾼다.
- 범위 표에는 요약만 둔다. 시안 개수, 폰트 조건 같은 상세는 결과물 상세에 한 번만 쓴다.

### 회사 소개
- 업종 용어(서치펌, 인하우스 등)는 풀어 쓰거나 뺀다. 작업자는 업계 사람이 아니다.
- 바뀔 수 있는 사실(팀 인원, 등록 기간 같은 운영 숫자)은 정체성처럼 쓰지 않는다.

### 원하는 인상과 스타일 방향
- 제약은 단정한다. "어렵다면 \~만이라도"처럼 흐리지 않는다.
- 작업자가 정해도 되는 것(워드마크 대소문자, 글자를 쓸지 말지)은 열어 둔다고 쓴다.
- 스펙트럼 축은 사용자가 확신하는 것만 남긴다. 많을수록 흐려진다.

### 결과물 상세
- 결과물마다 로고가 들어갈 자리를 점선으로 비운 목업을 붙인다. 우리 시안이 아니라 결과물의 모양(정사각, 가로형, 세로형, 앞뒤 면)을 보여 준다.
- 규격 예시는 요구와 정확히 맞춘다. 형태 넷에 색 셋을 요구했으면 열두 조합을 표로 모두 적는다. 일부만 적으면 나머지가 필요한지 모호해진다.
- 빈칸은 밑줄(`______`)이 아니라 이름을 붙인 옅은 회색 칸으로 그린다. 밑줄은 잘 안 보이고 자리 수를 세게 만든다.
- 업계 관행을 조사해 넣고 싶어도(사용 비율, 명도 대비, 별색 번호, 안전 영역) 이번 대가와 독자에게 필요한 것만 넣는다. 용어를 풀어야 읽히면 뺀다.
- 규격 예시 표의 "더 좋은 방식이 있다면 제안해 달라"는 말은 결과물 상세 맨 위에 한 번만 쓴다.

### 마치며
- 후속 계약이나 추가 작업 이야기를 꺼내지 않는다. 조율 환영과 감사로 닫는다.

## 어조

받는 사람은 대등한 사업자다. 의무("\~해야 합니다"), 허락("\~해도 됩니다"), 결재("확인받기")가 아니라 부탁("부탁드립니다"), 바람("\~면 좋겠습니다"), 함께 정하기("알려 주시면 함께 보고 정하겠습니다")로 쓴다. 계약상 의무도 내용은 그대로 두고 어투만 바꾼다.
