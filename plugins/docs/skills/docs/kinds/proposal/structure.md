# proposal: 내용 구조 가이드

## 설득 흐름

제안서는 한 줄의 논증이다. 각 절이 앞 절의 질문에 답하고 다음 절의 질문을 연다.

1. **문제**: 지금 무엇이 안 되고, 그대로 두면 무엇을 잃는가
2. **제안**: 무엇을 하자는 것인가
3. **근거**: 왜 이 방식이 맞고, 왜 제안하는 쪽이 할 수 있는가
4. **실행 계획**: 어떤 단계로, 누가 무엇을 맡는가
5. **비용과 일정**: 얼마가 들고, 언제 무엇이 나오는가
6. **다음 단계**: 읽는 사람이 언제까지 무엇을 결정하면 되는가

문제와 제안이 이어지지 않으면 근거가 아무리 많아도 설득되지 않는다. 쓰기 전에 draft.md 에 위 여섯 줄을 한 문장씩 적고, 이어지는지 먼저 확인한다.

## 2단 독자 구조

제안서는 한 문서로 두 독자를 잡는다.

- **1절 요약**: 의사결정자용. 첫 1\~2쪽에 결론, 금액, 기간, 기대효과, 결정 요청을 둔다. 여기만 읽고도 "받을지 말지"를 판단할 수 있어야 한다.
- **2절 이후**: 실무 검토자용. 현황, 방식, 책임 범위, 일정, 리스크를 근거 데이터와 함께 구체적으로 쓴다.

독자가 제안하는 쪽의 맥락을 모를수록 요약 뒤에 현황과 문제 정의를 길게 둔다.

## 결정 공란

이 종류는 독자와 제안의 성격을 고정하지 않는다. 작성 전에 아래 공란을 사용자와 해소한다(문법: [conventions.md](../../conventions.md#결정-공란ask)).

@ASK(target-audience): 이 제안서를 주로 누가 읽고 결정하나요? [의사결정자(임원, 대표) | 실무 검토자(엔지니어, 담당자) | 둘 다]
> 독자에 따라 1절 요약의 길이와 2절 이후의 깊이가 달라집니다. 인터뷰에서 이미 답이 나왔으면 그 답을 씁니다.

@ASK(proposal-kind): 어떤 제안인가요? [외부 사업, 서비스 제안 | 기술 방식 제안 | 조직 내부 기획, 예산 제안]
> 근거 절의 무게가 달라집니다. 외부 제안은 "왜 우리인가", 기술 제안은 "왜 이 방식인가", 내부 제안은 "왜 지금 이 비용인가"가 중심입니다.

@ASK(pricing-placement): 비용을 어디에 둘까요? [본문에 상세까지 | 본문은 요약만, 상세는 별도 견적서 | 비용 없음]
> 별도 견적서로 가르면 본문 비용 절은 총액과 지급 조건만 남기고 quotation 문서를 참조합니다.

@ASK(confidentiality): 표지에 기밀 조항을 넣을까요? 넣는다면 문구는 무엇인가요? [넣지 않는다 | 넣는다(문구 지정)]
> 넣으면 `COVER_CONFIDENTIAL` 로 문구를 주입합니다. 브랜드 기본값이 있으면 그것을 씁니다.

## 표준 절 구성

권장 순서다. 문서 성격에 따라 절을 더하거나 빼거나 순서를 바꿔도 되지만 **1절 요약은 항상 첫 번째**다. 절 제목은 `h1` 에 `1.` 형식으로 번호를 붙인다.

| 절 | 내용 | 비고 | 쓰는 컴포넌트 |
|---|---|---|---|
| 1. 요약 | 결론, 제안 범위, 금액, 기간, 기대효과, 결정 요청 | 필수. 1\~2쪽 | `summary`(라벨 "제안 요약"), `metrics` |
| 2. 현황과 문제 | 지금 상황, 문제 정의, 방치 비용 | 독자가 맥락을 모르면 길게 | `prose`, 표 |
| 3. 제안 | 무엇을 어떻게 하는가, 대안 비교 | 필수 | `prose`, 대안 비교 표 |
| 4. 근거 | 왜 이 방식인가, 실적, 수치, 사례 | 필수 | `prose`, `metrics`, `note` |
| 5. 실행 계획 | 단계, 단계별 산출물, 책임 범위와 제외 범위 | 필수. 단계 도식 권장 | `phases` 나 단계 표, 책임 범위 표 |
| 6. 일정과 비용 | 마일스톤, 비용 구조, 지급 조건 | 필수(비용은 `pricing-placement` 에 따름) | 마일스톤 표, 비용 표, `note` |
| 7. 리스크와 대응 | 일어날 수 있는 문제와 완화 방안 | 권장 | 표 |
| 8. 다음 단계 | 결정 요청, 기한, 결정 후 첫 일정 | 필수. 문서 끝 | `next`(라벨 "결정 요청") |
| 부록 | 상세 데이터, 참고 자료, 용어 | 선택 | 표 |

- `summary` 는 1절에 하나, `next` 는 8절에 하나만 둔다.
- 서사가 이어지는 절(2\~4절)은 문단을 `prose` 로 감싸 줄 길이 상한을 켠다. 표와 상자는 전폭 그대로다.
- 본문 안의 조건과 면책은 `note` 로 쓴다. 표지 기밀 조항은 `COVER_CONFIDENTIAL` 로만 넣고 본문에서 반복하지 않는다.

## 절별 작성 포인트

### 1. 요약
- 첫 문단에 "무엇을 제안하는가"를 1\~2문장으로 쓴다.
- 범위, 금액(또는 범위), 기간, 기대효과를 `metrics` 카드(한 줄에 2\~4개)나 표로 보인다. 값에는 단위를 붙이고, 추정 수치는 `note` 로 근거를 단다.
- "왜 지금, 왜 이 방식인가"의 논거 2\~3개를 사실로 적는다.
- 마지막 줄에 결정 요청을 한 문장으로 적고 8절을 가리킨다.

### 2. 현황과 문제
- 문제를 읽는 사람의 언어와 수치로 쓴다. "비효율이 크다" 대신 "주간 재고 대조에 담당자 2명이 하루씩 쓴다"로 쓴다.
- 그대로 두었을 때의 비용(시간, 돈, 기회)을 적는다. 추정이면 추정이라고 쓴다.

### 3. 제안
- 무엇을 하는지 먼저, 어떻게 하는지 다음에 쓴다.
- 검토한 대안이 있으면 표로 비교하고 이 안을 고른 이유를 적는다. 대안을 숨기면 검토자가 스스로 찾는다.

### 4. 근거
- "잘한다"는 주장 대신 검증할 수 있는 사실을 쓴다: 유사 사례 수, 기간, 성과 수치, 레퍼런스.
- 고유 방법론이 있으면 이름을 붙이고 단계로 구조화한다.

### 5. 실행 계획
- 단계, 산출물, 기간을 `phases` 흐름(3\~5단계)이나 단계 표로 한눈에 보인다. 단계가 6개 이상이거나 단계마다 설명이 길면 단계 표로 쓴다.
- 각 단계에서 받는 쪽이 할 일(자료 제공, 검수, 의사결정)을 적는다. 책임 범위 표와 이어진다.
- 책임 범위는 "제안하는 쪽 / 받는 쪽 / 제외"로 나눈다. 제외 범위를 흐리게 쓰지 않는다. 나중 분쟁의 대부분이 여기서 난다.

### 6. 일정과 비용
- 착수일 기준 주차나 단계로 마일스톤을 적고, 마일스톤마다 산출물을 붙인다.
- 받는 쪽의 의사결정 소요 시간(검수, 승인)은 별도 버퍼로 표시한다.
- 비용은 계산 기준, 총액, 지급 시점과 조건을 적는다. "별도 협의"로 비워 두지 않는다. 정말 미정이면 무엇이 정해지면 확정되는지 적는다.

### 7. 리스크와 대응
- 일어날 수 있는 문제를 현실적으로 적고 각각 대응을 붙인다.
- 불리한 사실도 적는다. 검토자가 먼저 찾아내면 나머지 주장까지 의심받는다.

### 8. 다음 단계
- `next` 상자에 결정 요청, 회신 기한, 결정 후 첫 일정(킥오프 날짜 등)을 적는다.
- 요청은 한두 개로 좁힌다. "검토 부탁드립니다"는 요청이 아니다.

## 표 패턴

### 단계 표

`phases` 대신 쓸 때의 열 구성이다.

| 단계 | 업무 | 산출물 | 받는 쪽 할 일 | 기간 |
|---|---|---|---|---|
| 1. 착수 | 킥오프, 현황 조사 | 현황 보고서 | 매장 데이터 제공 | 1\~2주차 |

### 책임 범위 표

항목, 제안하는 쪽, 받는 쪽의 3열이다. 셀에는 기호(체크, 대시) 대신 말을 쓴다(`담당`, `지원`, `제외`, 또는 구체적인 일). 제외 범위는 표 아래 목록으로 따로 나열한다.

| 항목 | 제안하는 쪽 | 받는 쪽 |
|---|---|---|
| 재고 데이터 이전 | 이전 스크립트 작성, 검증 | 원본 데이터 제공 |
| 매장 교육 | 교육 자료, 2회 교육 | 참석자 지정 |

### 마일스톤 표

간트 차트 대신 텍스트 타임라인 표를 쓴다. 받는 쪽 의사결정 소요 시간은 "비고" 열이나 표 아래 `note` 로 적는다.

| 마일스톤 | 시점 | 산출물 | 비고 |
|---|---|---|---|
| 킥오프 | 착수 1주차 | 도입 계획서 | |
| 시범 매장 가동 | 착수 6주차 | 시범 운영 보고서 | 받는 쪽 검수 1주 |

### 비용 표

항목, 산출 기준, 금액 순으로 두고 마지막 행에 합계를 둔다. `table.amounts` 를 달아 금액 열 정렬과 합계 강조를 켠다. 금액은 천 단위 구분자와 통화 단위, VAT 포함 여부를 적는다.

| 항목 | 산출 기준 | 금액(원, VAT 별도) |
|---|---|---|
| 설계, 개발 | 3인 x 10주 | 42,000,000 |
| 교육, 안정화 | 1인 x 2주 | 6,000,000 |
| **합계** | | **48,000,000** |

## 독자별 조정

| 독자 | 조정 |
|---|---|
| 의사결정자만 | 1절을 2\~3쪽으로 늘리고 5\~7절은 요약 수준으로 줄인다 |
| 실무 검토자만 | 1절을 1쪽으로 줄이고 3\~7절을 근거 데이터와 함께 상세히 쓴다 |
| 둘 다 | 표준 2단 구조 그대로 쓴다. 1절에 "상세는 5절" 같은 안내를 둔다 |
| 제안하는 쪽을 처음 접하는 독자 | 2절 앞에 제안 주체 소개를 1쪽 이내로 둔다 |

## 표지 변수

```bash
KIND=proposal [LAYOUT=a4] [BRAND=<brand>] <변수...> bash scripts/build.sh scaffold <문서 폴더>
```

표지 메타 라벨은 [kind.md](kind.md) 의 `labels` 가 정한다. 변수와 라벨의 짝은 이렇다.

| 변수 | 표지 라벨 | 예시 |
|---|---|---|
| `CATEGORY` | 카테고리 | 비우면 `PROPOSAL`. `PROPOSAL / 제안서`, `TECHNICAL PROPOSAL / 기술 제안서` |
| `DOC_TITLE` | 탭 제목 | `매장 재고 관리 시스템 도입 제안서` |
| `DOC_HEADER` | 러닝 헤더 | `재고 관리 시스템 도입 제안` |
| `SUBTITLE` | 부제 | `재고 대조 자동화와 12주 도입 계획` |
| `COVER_TITLE` | 메인 제목(`<br>` 가능) | `매장 재고 관리<br>시스템 도입 제안` |
| `COVER_FROM` | 발신 | 제안 주체. 비우면 브랜드 기본값 |
| `COVER_TO` | 수신 | 받는 조직과 부서 |
| `COVER_TARGET` | 대상 | `직영 매장 12곳` |
| `COVER_PERIOD` | 기간 | `2026-11 ~ 2027-01 (12주)` |
| `COVER_OWNER` | 담당 | 제안 담당자. 비우면 표지에서 생략 |
| `COVER_CONFIDENTIAL` | 기밀 조항 | `confidentiality` 결정에 따름. 비우면 브랜드 기본값, 브랜드도 비면 상자가 사라진다 |

## 호출 예시

```bash
DOC_TITLE="매장 재고 관리 시스템 도입 제안서" \
SUBTITLE="재고 대조 자동화와 12주 도입 계획" \
DOC_HEADER="재고 관리 시스템 도입 제안" \
COVER_TITLE="매장 재고 관리<br>시스템 도입 제안" \
COVER_TO="OO유통 운영본부" \
COVER_TARGET="직영 매장 12곳" \
COVER_PERIOD="2026-11 ~ 2027-01 (12주)" \
KIND=proposal bash <skill-dir>/scripts/build.sh scaffold "/path/to/제안서"

# <제안서>.html 의 본문 자리에 본문 HTML 을 작성한 뒤
bash <skill-dir>/scripts/build.sh pdf "/path/to/제안서"
```

회사 양식이 필요하면 `BRAND=<id>`, 발표용이면 `LAYOUT=deck` 을 붙인다. 컴포넌트 마크업은 [a4 layout.md](../../layouts/a4/layout.md#컴포넌트-카탈로그) 에 있다.
