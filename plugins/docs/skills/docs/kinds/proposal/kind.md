# proposal: 제안서

읽는 사람이 "이 제안을 받아들일지"를 결정하도록 만드는 문서다. 표지, 러닝 헤더, 기밀 조항을 갖춘 정식 문서로 낸다.

## 쓰는 자리

- 외부 고객이나 협력사에 서비스, 사업, 협업을 제안할 때
- 기술 방식(아키텍처, 도입 방식, 전환 계획)을 제안하고 승인을 받을 때
- 조직 안에서 예산, 인력, 일정을 요청하는 기획 제안을 올릴 때
- 예: 매장 재고 관리 시스템 도입 제안, 사내 데이터 플랫폼 전환 제안, 연간 유지보수 계약 제안

## 다른 종류와의 차이

| 종류 | 핵심 질문 | 목적 |
|---|---|---|
| **proposal** | "왜 이것을, 왜 이 방식으로 해야 하나?" | 설득. 서사와 근거 중심 |
| quotation | "무엇을, 얼마에?" | 금액과 조건 합의. 서사 없음 |
| analysis | "무엇을 확인했나?" | 사실과 근거 기록. 제안이 아님 |
| spec | "무엇을 어떤 형식으로 주고받나?" | 구현 규격 합의 |

금액만 전달하면 quotation 이고, 제안 없이 조사 결과만 공유하면 analysis 다. 제안서 안의 비용 절은 요약만 두고 상세 내역을 quotation 으로 분리해도 된다.

## 레이아웃별 차이

| 레이아웃 | 언제 | 달라지는 점 |
|---|---|---|
| `a4`(기본) | 보내서 읽히고 결재에 붙는 제안서 | [structure.md](structure.md) 의 표준 절 구성 그대로. 서사가 긴 절(문제, 제안, 근거)은 `prose` 로 감싼다 |
| `deck` | 대면 발표로 설득하는 제안 | 1절 요약이 한두 장(결론과 핵심 수치), 2\~4절이 절마다 2\~3장, 실행 계획은 단계 흐름 한 장과 책임 범위 한 장, 일정과 비용이 한두 장, 다음 단계가 마지막 한 장이 된다. 근거 데이터 상세와 비용 내역은 a4 부록이나 quotation 으로 따로 뽑는다 |

deck 의 슬라이드 규칙(한 장 한 메시지, 캔버스, 컴포넌트)은 `layouts/deck/layout.md` 에 있다.
