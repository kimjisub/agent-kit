# proposal: 작성 전 선행 재료

아래가 갖춰지지 않으면 제안서를 완성할 수 없다. 작성 전에 확인하고, 빠진 것은 받는 쪽이나 내부에 먼저 묻는다. 채울 수 없는 항목은 본문에서 "미정"으로 드러내고 무엇이 정해지면 확정되는지 적는다.

## 결정 공란

- [ ] [structure.md](structure.md#결정-공란) 의 결정 공란(target-audience, proposal-kind, pricing-placement, confidentiality)을 사용자와 모두 정했다

## 받는 쪽의 현황과 요구

- [ ] 받는 쪽 조직의 업무, 규모, 의사결정 구조를 안다
- [ ] 지금의 문제와 "왜 지금인가"를 받는 쪽 언어로 한 문장에 적을 수 있다
- [ ] 문제를 방치했을 때의 비용(시간, 돈, 기회)을 수치로 댈 수 있거나, 추정 근거가 있다
- [ ] 이전에 비슷한 시도가 있었다면 그 결과와 실패 원인을 안다

## 제안 범위와 조건

- [ ] 무엇을 하고 무엇을 하지 않는지(제외 범위)가 정해졌다
- [ ] 기간(착수 예정일, 종료 기준)이 정해졌다
- [ ] 비용의 산출 기준과 내부 근거가 있다(`pricing-placement` 가 "비용 없음"이 아닐 때)
- [ ] 지급 조건, 보증, 유지보수 같은 계약 조건의 기본값이 있다

## 근거

- [ ] 제안 방식이 맞다는 근거(유사 사례, 실적 수치, 레퍼런스, 벤치마크)가 있다
- [ ] 검토한 대안과 이 안을 고른 이유를 설명할 수 있다
- [ ] 수치마다 출처와 기준 시점이 있다

## 실행 계획과 일정

- [ ] 단계별 업무, 산출물, 기간을 나눌 수 있다
- [ ] 단계마다 받는 쪽이 할 일(자료 제공, 검수, 승인)을 안다
- [ ] 받는 쪽 의사결정 소요 시간을 가정했다
- [ ] 받는 쪽 지연이 일정에 미치는 영향을 어떻게 다룰지 기준이 있다

## 리스크

- [ ] 일어날 수 있는 문제 2\~3개와 각각의 대응을 적을 수 있다
- [ ] 제안에 불리한 사실(제약, 의존성, 미검증 가정)을 파악했다

## 다음 단계

- [ ] 받는 쪽에 요청할 결정 한두 개와 회신 기한이 있다
- [ ] 결정 후 첫 일정(킥오프 등)을 제시할 수 있다

## 표지

- [ ] 발신, 수신, 대상, 기간, 담당 값이 정해졌다. 정하지 않은 것은 비워 두면 표지에서 사라진다
