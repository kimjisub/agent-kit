# docs

**로드 시점: 남에게 건넬 문서를 만들 때.** 제안서, 견적서, 분석 보고서, 발표 자료, 매뉴얼, 기술 명세, 장 단위 참조 문서(인수인계서, 운영 핸드북)가 여기 듭니다. 회사 이름이 박힌 양식은 그 회사의 문서 스킬이 맡고, 이 스킬은 회사와 무관한 공통 틀입니다.

## 목적

**문서를 목적과 독자 인터뷰 -> 명세 로드 -> HTML 작성 -> PDF -> 체크리스트 검증의 차례로 만드는 스킬입니다.** 잘 되면 누가 만들어도 같은 구조와 같은 문체의 문서가 나오고, 독자에게 맞는 깊이로 쓰여 검토나 결재나 보관 어느 자리에서든 읽힙니다.

문서에는 따로 움직이는 세 가지가 있습니다.

| 축 | 정하는 것 | 폴더 | 있는 것 |
|---|---|---|---|
| 내용 종류(kind) | 무엇을 어떤 순서로, 어느 깊이로 쓰나. 내용 검증 | `kinds/<id>/` | analysis, proposal, quotation, brief, briefing, manual, spec, handbook |
| 레이아웃(layout) | 어떤 매체에 어떻게 보이나. 표지, 컴포넌트, 쪽 나눔, 표현 검증 | `layouts/<id>/` | a4, deck, web |
| 브랜드(brand) | 누구 이름으로 나가나. 색, 폰트, 로고, 문체 | `brands/<id>/` | default |

셋을 가르면 같은 제안서를 A4 로도 슬라이드로도 뽑고, 요약 상자의 모양을 한 곳에서 고치면 모든 종류가 같이 바뀝니다. 종류마다 기본 레이아웃이 있어 보통은 종류만 고릅니다.

이 스킬은 두 회사의 문서 스킬에서 회사 고유 내용을 걷어내 공통 부분만 옮긴 것입니다. handbook 종류와 web 레이아웃은 한 인수인계서의 장 구성과 화면 레이아웃을 틀로 만든 것입니다.

## 핵심 원칙

1. **독자가 문서를 정합니다.** 누가 어떤 맥락에서 읽는지가 정보의 양, 깊이, 결론의 위치, 어조를 정합니다. 적용 -> Step 2
2. **결정은 묻고, 추천은 추천까지만.** 어느 단계도 사용자 확인 없이 확정하지 않습니다. 맥락에서 후보를 골라 제시하는 것은 괜찮습니다. 적용 -> Step 1, 2, 4
3. **내용과 표현을 섞지 않습니다.** 내용 종류 문서는 컴포넌트를 이름으로만 부르고, 모양은 레이아웃이 정합니다. 문서 하나에만 필요한 스타일은 그 문서의 `<style>` 끝에 둡니다. 적용 -> Step 3, 4
4. **HTML 이 처음부터 끝까지 정본입니다.** PDF 는 HTML 을 굳힌 결과이고 직접 고치지 않습니다. 적용 -> Step 4, 6
5. **결정 공란(`@ASK`)을 다 풀기 전에는 본문을 쓰지 않습니다.** 적용 -> Step 3
6. **PDF 를 만들었다고 끝이 아닙니다.** 쪽 이미지를 눈으로 보고 두 체크리스트(내용, 표현)로 점검한 뒤 전달합니다. 적용 -> Step 5

## 정책

| 정책 | 언제 걸리나 | 내용 |
|---|---|---|
| 회사 고유 내용을 넣지 않는다 | 종류, 레이아웃, 브랜드를 더하거나 고칠 때 | 이 스킬은 여러 조직과 기기에서 같은 사본을 쓴다. 회사명, 고객사명, 회사 용어집, 회사 양식은 그 회사의 문서 스킬이나 `brands/<id>/` 를 담은 그 회사 저장소에 둔다 |
| 비밀 값을 문서에 넣지 않는다 | Step 4 | 비밀번호, 토큰, 개인 키는 "어디서 받나"만 쓴다. PDF 사본이 남는다 |
| 파일을 스스로 열지 않는다 | Step 6 | 경로를 알려 주고, 열어 달라고 할 때만 그 환경이 정한 방법으로 연다 |
| 도메인 사실은 추측하지 않는다 | Step 4 | 금액, 날짜, 수치, 법인 표기가 불확실하면 채우지 않고 묻는다 |

## 전제

| 전제 | 확인 | 없으면 |
|---|---|---|
| Chrome, Chromium, Edge 중 하나 | `scripts/build.sh pdf` 가 찾는다 | 설치하거나 `DOCS_CHROME` 에 실행 파일 경로를 준다 |
| `pdftoppm`(쪽 이미지 확인용) | `which pdftoppm` | `brew install poppler`. 없으면 PDF 를 파일 읽기로 직접 연다 |
| 인터넷(웹폰트) | 레이아웃 CSS 가 Pretendard 를 CDN 에서 불러온다 | 로컬에 Pretendard 가 설치돼 있으면 그것으로 렌더된다 |

## 절차

```
1. 목적      bash scripts/build.sh --list 로 종류와 레이아웃을 보여 주고 고른다
2. 독자      누가 어떤 맥락에서 읽나
3. 명세      READ <- kinds/<kind>/kind.md: 정체성, 다른 종류와의 차이, 레이아웃별로 달라지는 점
             READ <- kinds/<kind>/structure.md: 구조, 깊이, 표지 변수
             READ <- kinds/<kind>/inputs.md: 쓰기 전에 모을 재료
             READ <- layouts/<layout>/layout.md: 표지, 컴포넌트, 쪽 나눔
             READ <- brands/<brand>/voice.md: 문체
             READ <- conventions.md: @ASK 와 문서 폴더 규약
4. 빌드      scaffold -> draft.md -> 본문 HTML -> pdf
5. 검증      READ <- kinds/<kind>/review.md, layouts/<layout>/review.md, brands/<brand>/design-principles.md
6. 전달
```

### Step 1. 목적: 무슨 문서를, 왜

```bash
bash <skill-dir>/scripts/build.sh --list    # 종류(허용 레이아웃), 레이아웃, 브랜드
```

1. 목록을 보여 주고 무슨 문서인지 묻는다. 요청에서 이미 드러났으면 확인만 한다.
2. 왜 만드는지(결정을 받으려고, 기록하려고, 넘겨주려고, 발표하려고)를 묻는다.
3. 레이아웃은 종류의 기본값을 추천하고, 매체가 다르면(슬라이드로 띄운다, 화면에서 찾아 읽는다) 그 레이아웃을 고른다. 종류마다 허용 레이아웃이 `kind.md` 의 `layouts` 에 있다.
4. 브랜드는 기본 `default`(회사 이름 없는 중립 양식)다.

판단 기준은 읽는 방식이다. 계약한 외부 작업자가 받아 작업을 시작하면 brief, 한 번 읽고 판단하면 analysis 나 proposal, 따라 하며 읽으면 manual, 필요한 장만 찾아 다시 열면 handbook, 말로 전하며 띄우면 briefing 이다. 각 `kind.md` 의 "다른 종류와의 차이" 표가 경계를 정한다.

끝나면 종류, 레이아웃, 브랜드, 목적 한 줄이 정해져 있다.

### Step 2. 독자: 누가 어떤 맥락에서

1. 누가 읽나(결정권자, 실무자, 외부, 이어받는 사람)를 묻는다.
2. 그 사람이 이 주제를 얼마나 아나, 이 문서를 읽고 무엇을 하게 되나를 묻는다.
3. 독자가 여럿이면 누구를 기준으로 쓸지 정한다. handbook 은 장마다 독자를 따로 적는다.

주의는 자동 확정이다. 맥락에서 독자가 짐작돼도 추천으로 제시하고 확인받는다.

끝나면 독자와 깊이가 정해져 있다. 깊이의 단계는 종류의 `structure.md` 가 정한다.

### Step 3. 명세 로드와 결정 공란 해소

1. 위 READ 목록을 연다. 종류 문서가 브랜드의 문체를 덮어쓰는 부분이 있으면 종류 쪽을 따른다.
2. 결정 공란을 뽑는다.

   ```bash
   LAYOUT=<layout> bash <skill-dir>/scripts/build.sh ask <kind>
   ```

3. 나온 `@ASK(slot-id)` 마다 선택지를 주는 질문으로 묻는다(Claude Code 는 `AskUserQuestion`). Step 1, 2 에서 이미 답이 나온 슬롯은 그 값으로 정하고 다시 묻지 않는다.

끝나면 모든 `@ASK` 가 풀려 있다. 풀리기 전에는 Step 4 의 본문 작성으로 가지 않는다.

### Step 4. 빌드: scaffold -> 초안 -> 본문 -> PDF

1. **위치를 정한다.** 작업 맥락에 관련 폴더가 있으면 그 안을 1순위 후보로 제시하고, 없으면 어디에 둘지 묻는다. 폴더 이름이 문서 이름과 파일 이름이 된다(`conventions.md`).
2. **scaffold 를 만든다.** 표지 변수는 Step 1\~3 의 결정에서 뽑는다. 변수의 뜻과 표지 라벨은 종류의 `structure.md` 에 있다.

   ```bash
   KIND=<kind> [LAYOUT=<layout>] [BRAND=<brand>] \
   DOC_TITLE="..." DOC_HEADER="..." COVER_TITLE="..." SUBTITLE="..." \
   COVER_FROM="..." COVER_TO="..." COVER_TARGET="..." COVER_PERIOD="..." \
   bash <skill-dir>/scripts/build.sh scaffold "/path/to/<문서명>"
   ```

   비운 표지 변수는 표지에서 자리째 사라진다. 브랜드에 `logo.svg` 가 없으면 `BRAND_NAME` 으로 글자 로고를 만들고, 이름도 없으면 로고 자리를 비운다.
3. **`draft.md` 에 초안을 잡는다.** 핵심 메시지와 흐름을 먼저 정한다. 내용 방향이 크면 여기서 사용자와 맞춘다.
4. **본문을 HTML 로 쓴다.** `<문서명>.html` 을 열고 본문 자리 주석에 쓴다. 순서와 절은 종류의 `structure.md`, 상자와 표는 레이아웃의 `layout.md` 카탈로그를 따른다. 그림은 `assets/` 에 두고 상대 경로로 건다. 표지 영역은 건드리지 않는다.
5. **PDF 로 굳힌다.**

   ```bash
   bash <skill-dir>/scripts/build.sh pdf "/path/to/<문서명>"
   ```

주의는 문체다. 본문은 `brands/<brand>/voice.md` 를 따르고, 키보드로 칠 수 없는 문자(엠대시, 가운뎃점, 화살표 기호, 곡선 따옴표, 이모지)를 쓰지 않는다.

같은 내용을 다른 레이아웃으로도 뽑으려면 새 문서 폴더에 `LAYOUT` 만 바꿔 scaffold 하고, 본문은 그 레이아웃의 `layout.md` 에 있는 "다른 종류를 <레이아웃> 으로 뽑을 때" 절대로 다시 짠다. 슬라이드는 A4 본문을 그대로 붙이면 넘친다.

### Step 5. 검증

1. 쪽을 이미지로 뽑아 눈으로 본다.

   ```bash
   pdftoppm -r 60 -png "/path/to/<문서명>/<문서명>.pdf" /tmp/<문서명>-p
   ```

   표지와 본문 두세 쪽의 이미지를 연다. 겹친 글자, 빈 차트, 시스템 폰트로 떨어진 글꼴, 쪽 경계에서 잘린 표와 상자, 빈 표지 줄을 찾는다. web 레이아웃은 화면 모드도 캡처해 본다(`layouts/web/review.md`).
2. 내용은 `kinds/<kind>/review.md`, 표현은 `layouts/<layout>/review.md` 로 점검한다. 표현은 브랜드의 검증 베이스(기본은 [design-principles](brands/default/design-principles.md#검증-베이스))부터 적용한다.
3. 자판 밖 문자를 찾는다. `grep -nP '[^\x00-\x7F\p{Hangul}]' "<문서명>.html"` 에서 코드와 인용이 아닌 것을 고친다.
4. 걸린 것은 `.html` 만 고쳐 다시 `pdf` 하고 다시 본다.

끝나면 두 체크리스트에 걸리는 항목이 없고, 쪽 이미지를 한 번 이상 봤다.

### Step 6. 전달

1. PDF 경로와 HTML 경로를 알려 준다. 열어 달라고 하면 그 환경이 정한 방법으로 연다. 받는 사람이 다른 기기에 있으면 그 사람이 열 수 있는 자리(메신저 첨부, 공유 폴더)로 건넨다.
2. 고쳐 달라고 하면 내용 방향은 `draft.md` 부터, 표현과 배치는 `.html` 만 고쳐 다시 `pdf` 한다. PDF 는 직접 고치지 않는다.
3. 문서의 톤, 구조, 문구에 대한 지적은 `professionalify` 를 거친다.

## 공통 메커니즘

### 폴더

```
docs/
  SKILL.md
  conventions.md          @ASK 문법, 문서 폴더 규약
  scripts/build.sh        --list, ask, scaffold, pdf
  kinds/<id>/             내용 종류
    kind.md               frontmatter(description, layouts, category, labels) + 정체성, 차이, 레이아웃별 차이
    structure.md          구조, 깊이, 절마다 쓰는 컴포넌트 이름, 표의 열 구성, 표지 변수, 호출 예시
    inputs.md             쓰기 전에 모을 재료
    review.md             내용과 문체 검증
  layouts/<id>/           레이아웃
    layout.md             frontmatter(description) + 매체, 표지, 컴포넌트 카탈로그, 다른 종류를 뽑을 때
    style.css             모든 스타일. 브랜드 토큰(var(--brand-*))만 참조
    cover.html            <head> 와 표지. __STYLE__, __BRAND_CSS__ 자리에 CSS 가 들어간다
    footer.html           닫는 태그(web 은 목차 조립 스크립트 포함)
    review.md             표현 검증
    charts.md             (a4) 데이터 차트를 PDF 에 찍히게 그리는 법. deck 도 같이 쓴다
  brands/<id>/
    brand.env, brand.css, voice.md, design-principles.md, (logo.svg, logo-white.svg)
```

### kind.md frontmatter

```
---
name: proposal
description: 한 줄 (--list 에 뜬다)
layouts: a4 deck                        허용 레이아웃. 첫 값이 기본
category: 제안서                        표지 카테고리 기본값
labels: 발신 | 수신 | 대상 | 기간 | 담당   표지 메타 라벨. COVER_FROM | TO | TARGET | PERIOD | OWNER 순서
---
```

허용 목록 밖의 레이아웃을 주면 스크립트는 막지 않고 참고 한 줄만 찍는다.

### 새로 더하기

- **새 종류:** `kinds/<id>/` 에 네 파일을 쓴다. 컴포넌트는 기존 레이아웃 카탈로그에서 이름으로 고르고, 필요한 컴포넌트가 없으면 레이아웃 쪽에 더한다.
- **새 레이아웃:** `layouts/<id>/` 에 다섯 파일을 쓴다. 표지에는 `__LABEL_*__` 와 `__COVER_*__` 를 쓰고(치환 자리 목록은 `scripts/build.sh` 머리 주석), 쓸 만한 종류의 `kind.md` 의 `layouts` 에 이름을 더한다.
- **새 브랜드:** `brands/<id>/` 에 `default` 와 같은 키와 토큰 이름으로 값을 채운다. 회사 양식은 여기가 아니라 그 회사 저장소에 둔다(정책).

## 산출

문서 폴더 하나: `draft.md`, `<문서명>.html`, `<문서명>.pdf`, `assets/`.

## 스킬 생태계에서의 위치

- **pdf**: 이미 있는 PDF 의 병합, 분할, 텍스트 추출 같은 처리. 이 스킬은 PDF 를 만드는 쪽이다.
- **professionalify**: 이미 쓴 문서의 톤, 구조, 표, 도식을 진단하고 다듬는다. 이 스킬로 만든 문서에 대한 지적은 그쪽으로 간다.
- **show**: 글로는 이해가 막히는 결과를 그림으로 푸는 HTML 한 장. 지금 읽고 넘길 설명이면 show, 남겨 두고 결재하거나 보낼 정식 파일이면 이 스킬이다.
- **회사 문서 스킬**: 회사 양식과 회사 전용 종류(예: 채용 추천서)를 가진 스킬이 그 회사 저장소에 있으면, 회사 이름으로 나가는 문서는 그쪽을 쓴다.
