# 병목과 그림

**로드 시점 - Step 0 에서 병목을 고를 때, Step 3 에서 고른 그림을 지을 때.** 골라 쓰는 목록이다. 병목에 실린 정보의 성격(수치, 시간, 구조, 과정, 개념, 판단)마다 맞는 그림은 [forms](forms.md), 페이지 전체의 모양은 [pages](pages.md), 부품 마크업은 [kit](kit.md), 그리는 규칙은 [draw](../steps/50-draw.md).

출처: 그림 원칙과 「내용에 맞는 그림」 표는 visual-explainer v0.14.0 의 `SKILL.md`(MIT, `kit/LICENSE`)에서 옮겼다. 병목 표와 실제 화면, 도면, diff, 근거 칸은 show 의 것이다.

## 병목 표

왼쪽 열에서 읽는 사람이 막히는 자리를 고르고, 오른쪽 열의 그림을 후보로 삼는다. 한 페이지에 병목이 여럿이면 그림도 여럿이다.

| 막히는 자리 | 글로 쓰면 이렇게 된다 | 푸는 그림 |
|---|---|---|
| 어디 얘기인지 모른다 | "설정 화면 두 번째 표의 셋째 열" | 실제 화면에 테두리와 번호, 화면 지도, 그 부분만 크게 그린 확대 |
| 무엇이 바뀌었는지 안 보인다 | "A 를 B 로 바꾸고 C 를 뺐습니다" 열 줄, 진행 표, 판정 수 | 전후 사진 겹쳐 보기, 같은 좌표의 전후 그림, diff, 파일 지도. 화면이 바뀐 일이면 전후 화면이 반드시 들어간다(SKILL Step 0 의 4) |
| 관계와 구조가 안 그려진다 | "X 가 Y 를 부르고 Y 는 Z 에 쓴다" | 직접 그린 구조도, `<ve-flow>`, 순서도, 스키마 |
| 순서와 시간을 못 따라간다 | 단계 나열, 시각이 섞인 로그 | 단계 재생, 사건 재생, 타임라인 |
| 조건이 바뀌면 어떻게 되는지 상상이 안 된다 | "켜지면 이렇고 꺼지면 저렇고, 둘 다면..." | 값을 바꿔 보는 그림, 작은 그림 여럿, 상태 대조 표 |
| 크기와 비율이 안 느껴진다 | "1,819건 중 73%" | 치수선, 와플, 막대, 쌓기, 스파크라인 |
| 너무 많아 갈피를 못 잡는다 | 글머리표 40줄 | 묶은 요약과 펼치기, 상태 꼬리표 표, 수치 띠 |
| 무엇을 고르고 고르면 어떻게 되는지 모른다 | "A 안과 B 안이 있습니다" | 선택지마다 그림, 맞바꿈 표, `<ve-ask>` |
| 왜 이렇게 했는지 안 보인다 | "여러 가지를 고려해" | 의도 대조 |
| 믿어도 되는지 모른다 | "확인했습니다" | 근거 칸, 근거 절, (코드 근거) 표시 |

병목을 골랐으면 그 자리에 실린 정보를 [forms §성격 표](forms.md#성격-표) 에서 찾아 부품을 정한다. 병목이 표에 없으면 같은 질문을 한다. 읽는 사람이 머릿속에서 무엇을 다시 그리고 있나, 그것을 대신 그려 주면 무엇인가. 답이 그림이다.

## 그림 원칙

1. **그림 하나에 주장 하나.** 그림마다 `<figure>` 에 넣고, `<figcaption>` 이 그 주장을 한 문장으로 말한다. 렌더 검사가 캡션 없는 그림을 센다
2. **그림이 앞, 글은 라벨.** 절 대부분이 그림으로 열린다. 이유와 맞바꿈은 글로 열어도 된다. 그림을 설명하는 문장은 그림 안의 라벨이 된다
3. **첫 화면이 답이다.** 핵심이 그림 하나와 문장 하나로 첫 화면에 있다. 개념 설명이면 질문과 그 질문을 세우는 그림이다. 꾸밈용 대문 그림은 두지 않는다
4. **이름이 아니라 동작을 그린다.** "캐시" 상자가 아니라 캐시를 지나는 요청 경로다. 화살표마다 동사를 단다
5. **차이를 그린다.** 선택지마다 더하거나 빼는 상자와 선을 보인다
6. **상태는 모양으로도 말한다.** 모양, 자리, 무늬에 색을 더한다. 색만으로 말하지 않는다
7. **숫자마다 그림.** 그림 속 구간(지연, 크기, 기간)에는 치수선, 다른 숫자에는 옆에 와플, 막대, 스파크라인, 추세에는 선 그래프
8. **경우는 작은 그림 여럿.** 같은 작은 그림을 경우마다 한 번씩. 문장으로 된 표가 아니다
9. **사실마다 그림 안에 자리를 먼저 준다.** 라벨, 화살표 동사, 치수, 번호 표시, 캡션에 넣고, 그래도 남으면 문장이 된다

## 내용에 맞는 그림

정보의 성격마다 맞는 그림과 부품은 [forms](forms.md) 가 정본이다. 실제 화면은 [screen](../variants/screen.md), 도면과 렌더는 [drawing](../variants/drawing.md), 바뀐 코드는 [change](../variants/change.md) 와 아래 [diff](#diff).

mermaid 는 사용자가 원하거나 원본을 주었을 때만 쓴다. `<pre class="mermaid" aria-label="...">` 로 두면 렌더러가 SVG 로 그려 넣는다.

## 그림별 메모

### 실제 화면에 테두리와 번호

떠 있는 화면이면 찍기 직전에 요소를 글자나 셀렉터로 찾아 테두리와 번호를 그 자리에 그린다(`shot.mjs`, `mark.js`). 이미지 위에는 번호만 두고 설명은 캡션으로 뺀다. 브라우저 밖 이미지는 `grid_overlay.py` 로 좌표를 읽어 `annotate.py` 로 그린다. 쓰는 법은 [screen §화면 안에서 그리는 표시](../variants/screen.md#화면-안에서-그리는-표시) 와 [drawing](../variants/drawing.md).

### 화면 지도

화면이 넷을 넘으면 그림마다 어디서 온 것인지 말해 주는 지도 한 장을 앞에 둔다. 왼쪽에서 오른쪽이 깊이, 위아래가 같은 깊이의 다른 기능이다. `<ve-flow>` 로 그리면 된다. 담을 내용은 [document §화면의 자리와 깊이](../steps/20-document.md#화면의-자리와-깊이).

### 전후 사진 겹쳐 보기

같은 대상을 같은 범위와 축척으로 뽑은 두 장이면 `.pair[data-compare]` 로 나란히, 슬라이더, 차이를 오간다. 픽셀 크기가 다르면 겹쳐 보기가 꺼지니 같은 범위로 다시 자른다. 쓰는 법은 [output §겹쳐 보기](../steps/60-output.md#겹쳐-보기---나란히-슬라이더-차이).

### diff

바뀐 코드, 문서, 설정을 보일 때. 받는 사람이 코드를 읽는 사람이거나 바뀐 것이 화면에 드러나지 않을 때 맞는다. 코드를 안 읽는 사람에게는 화면 전후나 동작 전후 그림이 먼저이고, diff 는 근거로 접어 둔다.

```bash
git diff <기준>..HEAD -- <경로들> > data/change.diff
python3 scripts/diff-html.py --diff data/change.diff --side --into report.src.html --id change   # 원본의 <!--diff:change--><!--/diff:change--> 사이에 넣는다
python3 scripts/diff-html.py old.md new.md > data/doc-diff.html                                 # 두 파일을 바로 견준다
```

- 전부 싣지 않는다. 병목에 걸린 파일과 구간만 싣고, 나머지는 파일 지도 하나와 파일별 줄 수 `<ve-bars>` 로 둔다. 범위를 고르는 법은 [change](../variants/change.md)
- 구간마다 위에 왜 바꿨는지 한 줄(`<p class="why">`)을 단다. diff 는 무엇을 바꿨는지만 말한다
- 동작이 바뀌었으면 diff 위에 그 동작의 전후 그림을 둔다. 같은 좌표로 그리고 더해진 상자와 화살표는 `new`, 빠진 것은 `gone`
- 좌우 대조(`--side`)는 줄이 짝지어 바뀐 경우에, 한 줄 diff 는 줄이 더해지거나 빠진 경우와 좁은 화면에 맞는다

### 값을 바꿔 보는 그림, 상태 대조 표

"이 값이 바뀌면 어떻게 되나"가 논점이면 값을 바꿔 보는 그림을 만든다([draw §값을 바꿔 보는 그림](../steps/50-draw.md#값을-바꿔-보는-그림)). 상태가 몇 개로 끊기면 표 한 장이 낫다. 행이 상태, 열이 그 상태를 정하는 값과 그때 보이는 것이고, 칸마다 그 상태의 실제 화면 썸네일을 넣으면 더 빨리 읽힌다. 상태를 만드는 법은 [axes §상태축](../variants/axes.md#상태축---조건-a---조건-b).

### 숫자 차트

값은 재료 파일에서 만든다([data](../variants/data.md)). 크기는 `<ve-bars>`, 몫은 `<ve-waffle>` 과 `<ve-stack>`, 전후는 `<ve-shift>`, 추세는 `<ve-line>` 이다([forms §수치](forms.md#수치)). 막대는 0 에서 시작하고, 단위와 기준 시각을 라벨이나 캡션에 적는다. 막대 옆에 숫자를 함께 둬 인쇄에서도 읽히게 한다. 태그에 안 맞는 차트(산점도, 분포, 계열이 여럿인 추세, 작은 그림 여럿, 히트맵)와 행이 많은 재료 파일은 Vega-Lite 스펙으로 쓴다([vega-lite](vega-lite.md)).

### 수치 추이

지표가 시간에 따라 어떻게 움직였나가 논점일 때. 운영 지표, 사용량, 평점, 매출, 배포 전후가 흔하다. 같은 규칙이 링크와 이미지 모두에 걸린다.

- **지표를 먼저 정의한다.** 무엇을 셌나, 어느 플랫폼이나 집단인가, 집계 시간대, 그리고 값이 기간 단위(그 주의 새 가입)인지 누적(지금까지 전체)인지 이동 평균인지를 그림 위 `.meta` 나 부제에 쓴다. 한 플랫폼의 값을 전체처럼 쓰지 않는다
- **기간 단위 값을 그린다.** 누적값은 늘 오르니 변화가 안 보인다. 출처가 누적이나 가중 평균만 주면 그렇다고 쓰고, 기간 단위 값을 왜 못 구하나, 어디서 받으면 되나를 적는다. 누적, 이동 평균, 일 단위 값을 한 그림에 섞지 않는다
- **비교 기간을 맞춘다.** 요청한 시작점부터 마지막으로 들어온 기간까지, 견주는 두 구간은 같은 길이로. 기준선(앞 구간 평균, 목표)을 점선으로 긋고 라벨에 그 값을 쓴다. 기준, 지금 구간 평균, 바뀐 비율은 스크립트로 계산한다
- **기준 시각과 늦음을 보인다.** 출처의 마지막 날짜를 캡션이나 각주에 쓴다. 덜 찬 마지막 기간은 그렇다고 적는다. 실시간처럼 그리지 않는다
- **출처 캡션.** 어느 표나 화면에서, 언제, 어느 시간대로 뽑았나를 그림 아래에 둔다. 그린 값은 모두 그 출처에서 다시 만들 수 있어야 한다
- **함께 움직였다는 것과 원인을 가른다.** 배포나 작업과 같은 때 움직였어도 나눠 본 비교가 없으면 원인이라고 쓰지 않는다. 캡션이나 각주에 「같은 시기, 인과는 확인 못 함」 을 단다

### 묶은 요약과 펼치기

항목이 많으면 원인이나 성격으로 묶어 묶음마다 한 줄 요약을 세우고, 세부는 `<details>` 로 접는다. 항목이 수십 개면 상태 꼬리표 표 한 장으로 접고, 받는 사람이 자기 것만 찾으면 표 위에 검색칸을 단다.

### 의도 대조

"왜 이렇게 했나"가 논점이면 고른 안을 혼자 두지 않는다. 버린 안과 같은 좌표로 나란히 그리고, 가른 기준(제약, 요청 원문, 측정값)을 행으로 한 맞바꿈 표를 둔다. 요청 원문을 인용하고 그 옆에 대응한 결과를 두면 의도가 결과로 이어지는 것이 보인다.

### 근거 칸, 근거 절

어느 그림이든 옆에 근거를 둔다. 저장된 값과 화면 값, 파일과 줄, 명령과 출력을 `.evidence` 에 나란히 적고, 페이지 끝 근거 절(`section.sources`)에 출처를 모은다. 확인 못 한 것은 "(코드 근거)", "(확인 못 함)" 으로 단다.
