# 페이지 모양과 레시피

**로드 시점 - Step 2 에서 페이지 전체의 순서를 정할 때.** 모양은 내용에 맞춘다. 절을 합치고, 순서를 바꾸고, 빼거나 더한다. 그림 하나하나는 [figures](figures.md), 남에게 건네는 보고의 구조는 [document](../steps/20-document.md).

출처: 페이지 모양 표와 리뷰, 비교, 사실 확인, 프로젝트 요약 레시피는 visual-explainer v0.14.0 의 `SKILL.md` 와 `commands/*.md`(MIT, `kit/LICENSE`)에서 옮겨 고쳤다.

## 모양

| 페이지 | 흔한 순서 |
|---|---|
| 개념 설명 | 받는 사람이 할 일 -> 한 번 따라가기(단계 재생) -> 누가 무엇을 쥐나 -> 경계 사례 -> 용어([개념 풀어 주기](#개념-풀어-주기)) |
| 리뷰, 감사 | 판정 -> 근거 그림 -> 위험 -> 다음 할 일 |
| 비교 | 차이를 나란히 그린 것 -> 맞바꿈 -> 추천 -> 고르기 |
| 글 | 글 단에 그림. 글이 많아도 된다 |
| 그림 하나 | 큰 그림 하나, 제목, 캡션 |
| 남에게 건네는 보고 | 질문, 센 판정, 찍은 조건 -> 항목 목록 -> 묶음 절과 발견 카드 -> 잘 된 곳 -> 다음 할 것([document](../steps/20-document.md), [output §골격](../steps/60-output.md#골격)) |

## 레시피

자주 오는 요청의 모은 것과 절이다. 레시피의 절은 흔한 모양일 뿐이고 내용에 맞춰 바꾼다. 모든 주장에 `파일:줄` 이나 명령 출력을 단다. 이유를 지어내지 않는다.

### 작업 결과 알리기

"뭐가 바뀌었는지 show 해줘", "적용한 거 보여줘", 큰 작업을 마친 뒤의 보고. 받는 사람이 코드를 리뷰할 사람이 아니면 이 레시피다. 아래 「바뀐 코드 리뷰」 를 쓰면 diff 와 커밋 해시가 본문을 차지해 "그래서 무엇이 달라졌나"가 안 보인다.

| 절 | 그림 |
|---|---|
| 제목과 리드 | 무엇이 달라졌는지 한 문장. 배포 단계나 결정 대기 같은 상태는 넣지 않는다(다음 배포에서 틀린다) |
| 무엇이 문제였나 | 누가 무엇을 하다 어디서 막혔는지 흐름 하나. 막힌 자리를 강조 |
| 무엇이 달라졌나 | 같은 흐름의 바뀐 뒤. 새로 생긴 단계에 `new`. 화면이 바뀌었으면 전후 화면, 화면은 그대로이고 동작이 바뀌었으면 같은 상황의 전후 순서도 |
| 영향 | 기존 것에 무엇이 바뀌고 무엇이 그대로인지. 경우가 여럿이면 `<ve-matrix>` 전후 |
| 어디까지 반영됐나 | 환경마다 `<ve-matrix>`. 상태는 여기에만 둔다 |
| 정할 것 | 남은 결정. 없으면 절을 만들지 않는다 |
| 개발자용 세부 | `<details>` 안에 커밋, 오류 코드, 검증 명령, 논점 구간 diff |

작업 중에 붙인 이름(단계 번호, 줄임말)과 코드 식별자는 처음 나오는 자리에서 풀어 쓴다(SKILL 핵심 원칙 9).

- **대화가 아니라 출처를 다시 읽고 쓴다.** 실제 상태가 대화의 전제와 다르면 그 정정이 제목이다
- **제목의 개수는 스크립트로 센 것만 쓴다.** 세지 않았으면 개수 없이 쓴다
- **담당이 갈린 일은 격자로 보인다.** 행은 일의 조각, 열은 담당, 칸은 상태다
- **여러 갈래를 묶은 보고는 갈래마다 「문제였던 것」과 「달라진 것」 한 쌍이다.** 갈래의 무게가 다르면 그림도 다르다. 동작이 바뀐 갈래는 전후 순서도, 작은 정리 여럿은 상태 꼬리표 표, 문서 맞추기는 센 숫자 한 줄이다. 맨 위에는 갈래마다 한 줄 결론과 반영 상태를 격자로 둔다

### 바뀐 코드 리뷰

"diff 보기 좋게", "이 PR 정리해줘", "리뷰용으로 보여줘". 받는 사람이 그 코드를 리뷰하거나 고칠 사람일 때다.

범위는 가지, 커밋, 범위, PR, `HEAD` 다. 없으면 워킹트리를 기본 가지와 견준다. 모을 것은 diff 통계와 이름 상태, 바뀐 파일 전체와 그 주변 코드 경로, 공개 API 와 타입 변화, 테스트, 의존성과 설정 변화, 커밋 메시지다([change](../variants/change.md)).

| 절 | 그림 |
|---|---|
| 판정 | 한 문장 + 합쳐도 됨, 막힘 꼬리표 + 더한 줄과 뺀 줄 `<ve-stack>` |
| 무엇이 바뀌었나 | `new`, `gone` 을 단 파일 지도 `<ve-tree mono>`. 파일별 줄 수 `<ve-bars>` |
| 동작 | 같은 SVG 의 전후, 더해지거나 빠진 화살표 강조. 상태 기계나 큐가 바뀌었으면 사건 하나씩 재생 |
| 화면 | 화면에 드러나면 전후 사진 겹쳐 보기([screen](../variants/screen.md)) |
| 위험 | 정확성, 테스트, API, 보안, 성능의 상태 꼬리표 표 |
| 묶인 곳 | 바뀐 코드에 기대는 것의 작은 SVG |
| 코드 | 논점인 구간만 `diff-html.py`, 구간마다 이유 한 줄 |
| 고칠 것 | 손댈 만한 위험마다 `<ve-ask id="r1" q="parse() 의 null 검사를 고칠까요">` 에 `<ve-opt value="fix" default note="고치는 법 한 줄">고친다</ve-opt>`, `<ve-opt value="leave">그대로 둔다</ve-opt>` |

색은 빨강이 빠진 것과 전, 초록이 더한 것과 후, 주황이 위험, 파랑이 맥락이다. 답이 오면 사용자의 가지에서는 받아들인 고침을 반영하고, 남의 PR 이면 리뷰 의견 초안만 만들고 올리지 않는다.

### 계획 리뷰

"이 계획 봐줘", "구현 계획 검토".

계획 전체, 계획이 가리키는 파일 전부, 그것에 기대는 코드를 읽는다. 바꾸려는 것마다 파일, 함수, 타입이 있는지, 지금 동작이 계획과 맞는지, 놓친 파급이 무엇인지, 테스트가 저장소 방식에 맞는지 본다. 계획의 절과 `파일:줄` 을 인용한다.

| 절 | 그림 |
|---|---|
| 판정 | 승인, 고침, 반려와 이유 |
| 계획된 설계 | `<ve-flow>`. 발견이 닿는 부분을 `gone`, `new` 로 |
| 발견 | 틀릴 수 있는 문장 하나씩("3단계는 이제 없는 함수를 고친다"). 무거운 순서로 다섯까지. 각각 코드나 계획 원문으로 증명하고, 확인 못 한 것은 「(추정)」 |
| 결정 | 발견마다 `<ve-ask>`: 고친 계획(`default`), 계획 그대로, 실제 대안 |
| 잘 된 것 | 계획이 맞게 짚은 것 |

답이 오면 계획 파일에 받아들인 고침만 반영한다.

### 비교

"A 랑 B 중에 뭐가 나아", "선택지 비교해줘".

선택지가 이름 없이 오면 코드나 대화에서 실제 선택지를 찾는다. 선택지를 가르는 사실을 먼저 모으고 각각에 출처를 단다. 숫자는 모두 출처에서 온다.

| 절 | 그림 |
|---|---|
| 차이 | 선택지마다 그림 하나를 나란히, 각자 더하고 빼는 상자와 선 표시 |
| 경우 | 중요한 시나리오마다 같은 작은 그림을 선택지별로 |
| 맞바꿈 | 기준 하나가 행 하나인 상태 꼬리표 표 |
| 추천 | 고를 선택지와 이유 |
| 고르기 | `<ve-ask id="pick" q="어느 쪽으로 할까요">`, 선택지마다 `<ve-opt>`, 추천에 `default` |

`<ve-ask>` 는 진짜 하위 결정이 있을 때만 더한다. 답이 오면 원래 요청의 범위 안에서 그 선택으로 움직인다. 만들어 달라는 말이 없었으면 만들지 않는다.

### 사실 확인

"이 문서 맞는지 확인해줘", 만든 페이지를 내기 전 점검.

1. 확인할 수 있는 주장을 모두 뽑는다. 경로, 이름, 동작, 데이터 흐름, API, 명령, 의존성, 테스트, 숫자, git 이력. 의견은 뺀다
2. 주장마다 원본이나 `git show` 와 대조하고 확인됨, 고침, 근거 없음, 확인 불가로 단다
3. 틀린 것은 원본(`*.src.html`)을 작게 고쳐 다시 렌더한다. 구조와 모양은 그대로 둔다. 틀린 화살표나 라벨도 틀린 주장이다
4. 맨 위에 확인 띠를 둔다. 상태별 수를 꼬리표로, 바뀐 것을 `<details>` 목록으로

### 프로젝트 요약

"이 프로젝트 어디까지 왔어", "다시 들어가는데 정리해줘".

README, 변경 기록, 패키지와 빌드 파일, 최상위 구조, `git status`, 최근 커밋, 열린 가지, 최근 바뀐 파일의 TODO, 진행 메모, 주요 진입점을 읽는다. 명령 출력이나 `파일:줄` 을 인용한다. 없는 진척을 지어내지 않는다.

| 절 | 그림 |
|---|---|
| 이것이 무엇인가 | 한 문장 + 스택 꼬리표 + 진입점 |
| 구조 | 주요 모듈과 그 사이 데이터 흐름의 SVG |
| 최근 활동 | 날 로그가 아니라 주제로 묶은 `<ve-timeline>`, 갈래가 여럿이면 `lane` |
| 바뀐 화면 | 바뀐 화면마다 전후 짝. 이 절이 있으면 「지금 상태」 보다 앞에 둔다. 상태 표로 대신하지 않는다 |
| 지금 상태 | 커밋 안 된 작업, 가지, 막힌 것을 상태 꼬리표로 |
| 뜨거운 곳 | 모듈별 커밋이나 바뀐 줄 `<ve-bars>`, 가장 위험한 것에 `hot` |
| 명령과 파일 | 짧은 참조 표 |
| 다음 | `<ve-ask id="next" q="어디서 시작할까요">`, 근거 있는 다음 걸음마다 `<ve-opt>`, 가장 나은 것에 `default` |

### 개념 풀어 주기

"이게 정확히 뭔지 설명해줘", "등록 과정 시각화해서 설명해줘". 처음 보는 방식(인증, 데이터 모델, 알고리즘, 운영 절차)을 이해시키는 요청이다. 받는 사람은 대개 정의가 아니라 「그래서 나는 무엇을 하면 되나」를 묻고 있다. 정의와 배경부터 쌓으면 고쳐 쓸 때마다 설명이 늘고 「아직 이해가 안 된다」로 돌아온다.

| 절 | 그림 |
|---|---|
| 제목과 리드 | 받는 사람이 하는 일 기준의 한 문장. "출고대에서 비밀번호를 바꾸면 장비가 스스로 인증서를 받는다" |
| 한 번 따라가기 | 실제 값 하나(장비 하나, 요청 하나, 주문 하나)가 처음부터 끝까지 지나가는 단계 재생이나 `<ve-seq>`. 단계마다 누가 무엇을 하고 무엇이 오가나 |
| 누가 무엇을 쥐나 | 비밀, 권한, 데이터가 어디에 있고 어디로 옮겨 가나. 사람과 기계를 열로 둔 그림. 보안 개념이면 그것을 빼앗기면 무엇이 열리나까지 |
| 왜 이 방식인가 | 버린 대안을 나란히 두고 맞바꿈을 한 줄씩 |
| 경계 사례 | 실패하거나 예외가 되는 경우. 키를 잃었을 때, 끊겼을 때, 두 번 했을 때 |
| 용어 | 페이지에 나온 낱말의 풀이 표. 처음 나오는 자리에서도 푼다 |

정의(무슨 암호 방식인가, 어느 표준인가)는 「한 번 따라가기」의 그 단계 안에서 푼다. 따로 절을 세우면 그 절이 첫 화면을 차지한다. 받는 사람이 더 깊이 물으면 정의를 키우지 말고 따라가는 단계를 잘게 나눈다.

### 결정 근거 보고

"해도 되는지 분석해서 PDF 로", "구체적이고 논리적으로". 투자, 가격, 계약처럼 결정 하나를 근거로 받치는 보고다. 받는 사람은 결론과 그 결론이 뒤집히는 조건을 찾는다. `--pdf` 로 함께 낸다([output §PDF 로 건네기](../steps/60-output.md#pdf-로-건네기)).

| 절 | 그림 |
|---|---|
| 결론 | 큰 숫자 카드와 결론 한 문장. 할지 말지, 얼마나 |
| 판단 기준 | 무엇을 넘으면 하고 무엇에 못 미치면 안 하나. 기준값을 숫자로 |
| 사실 | 재료 파일에서 만든 차트와 표. 출처와 뽑은 시각 |
| 시나리오 | 가정마다 결과를 나란히. 가정에 따라 결론이 갈리면 가정 조합별 표를 반드시 둔다 |
| 종합 | 시나리오를 기준에 대 본 판정 |
| 실행과 중단 기준 | 시작하면 무엇을 보고, 어떤 숫자가 나오면 멈추나 |
| 가정과 한계 | 추정한 값, 표본 크기, 확인 못 한 것. 쓴 파일과 스크립트 이름 |

메신저로 건넬 때는 결론 몇 줄과 PDF 하나만 붙인다. 본문을 메신저 글로 다시 풀지 않는다.

### 사진 묶음 한 장

"행사 어땠는지 한 장으로". 스레드나 폴더의 사진 수십 장을 이미지 한 장으로 요약한다.

1. 사진을 한 장씩 열지 않는다. 촬영 시각 순으로 줄 세워 회전을 바로잡고(`ImageOps.exif_transpose`), 번호와 시각을 단 썸네일 시트로 훑는다
2. 사진만으로는 장소 이름, 인원, 논의 내용을 모른다. 일정, 일지, 준비 기록을 찾아 대조한다
3. 장면이 바뀌는 자리마다 한 장씩, 아홉 장(3x3)을 고른다. 긴 변 900px 로 줄여 넣는다(render 가 base64 로 넣어 원본이면 PNG 가 무겁다)
4. `data-image="mid"`, 결론 제목, 사진에서 센 숫자 셋, 3x3 격자(`aspect-ratio: 4/3; object-fit: cover`, 캡션은 시각과 장면 한 줄), 소감 두 칸, 각주

- 셀카로 찍은 사진은 글자가 좌우로 뒤집혀 있다. 뒤집어 싣고 각주에 적는다
- 사진에 없는 사실(인원, 장소 이름)은 확인되지 않으면 빼거나 「확인 못 함」으로 둔다
- 「어떤 것 같냐」는 의견 요청이다. 사진 나열로 끝내지 말고 제목에 판단을 쓴다

### 글이 주인공인 한 장

브리프, 미팅 질문지, 조사 요약처럼 차트가 아니라 사실 몇 줄과 판단과 물을 것을 메신저에 건넬 때. 위에서 멈춰도 답이 되게 쌓는다.

| 순서 | 내용 |
|---|---|
| 제목 | 판단이 든 결론 한 문장 |
| 리드와 메타 | 근거 두 문장, 작성일과 상태 |
| 확인 필요 상자 | 다음 행동 전에 사람이 확인할 것. 맨 위에 |
| 사실 격자 | 라벨 열과 내용 열. 칸 끝에 회색 출처 꼬리표(확인한 기사, 회사 주장, 추정, 누구 전언) |
| 판단 상자 | 점선으로 사실과 떼어 둔 가설과 판단 |
| 질문 격자 | 순서, 질문, 답으로 정하는 것의 세 열. 우선순위는 기호 대신 「1 우선」 같은 글자 |

글 칸에는 `data-prose` 를 단다. 칸이 여러 절이면 숫자 카드 아래부터 각주 앞까지를 `<section data-prose>` 하나로 감싼다. 질문을 `<ol>` 로 쓰면 일곱 줄부터 검사에 걸리니 처음부터 격자로 쓴다.

### 목록이 주인공인 한 장

도구, 북마크, 확장처럼 그림 없이 목록이 답인 경우. `data-image="dense"` 에서 숫자 카드와 그림을 지우고, 대상별 `h2` 절마다 표(이름, 주소나 정책, 이유, 상태) 하나를 둔다. 첫 줄 제목에 결론(몇 개, 어떤 원칙)을 쓰고, 근거 출처와 확인 못 한 것은 각주에 둔다. 받는 사람이 눌러 쓸 주소는 그림 아래 글에도 쓴다.

### 일정표 한 장

시간, 장소, 설명이 줄지어 오는 일정과 코스. `data-image="mid"` 에 표 하나를 두고, 날짜나 차량이 바뀌는 자리는 검은 띠 행으로, 이동 구간은 회색 행에 거리와 분을 적는다. 이동 표시는 그림 문자 대신 「차로」 같은 글자로 쓴다. 같은 주제를 다시 고칠 때는 새 작업 폴더에서 원본을 새로 쓴다.

### 답을 그림으로

"지금 설명한 거 그림으로 보여줘", 답이 길고 구조가 얽혀 글로 안 읽힐 때.

대화에서 이미 낸 답이 재료다. 답의 결론을 제목과 첫 그림으로 세우고, 답을 문장 단위로 놓고 [forms §글을 그림으로 바꾸는 순서](forms.md#글을-그림으로-바꾸는-순서) 대로 문장마다 정보의 성격을 찾아 그림으로 바꾼다. 렌더의 `✗ text:` 줄이 0 이 될 때까지 옮긴다. 답 안의 숫자와 관계는 원래 출처를 다시 열어 맞는지 보고 싣는다. 대화에는 페이지 경로와 한 줄만 쓴다. 터미널 표가 네 줄을 넘거나 세 열을 넘으면 이 레시피로 페이지 하나와 한 줄 답이 된다.
