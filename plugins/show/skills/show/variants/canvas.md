# 화면 캔버스

여러 화면이 어떤 순서로 이어지는지가 병목일 때 쓴다. 가입부터 첫 주문까지, 초대 메일을 받은 사람이 어디를 거쳐 들어오는지처럼 **단계마다 화면이 어떻게 생겼고 어느 버튼이 다음 화면으로 보내는지**를 한 캔버스에 펼친다. 흐름도(`<ve-flow>`)는 상자와 화살표만 보여 주고, 전후 짝(`.pair`)은 한 화면의 변화만 보여 준다. 캔버스는 그 둘 사이를 메운다.

각 화면은 그림이 아니라 **그 순간 그려진 HTML 자체**다. 화면을 뜰 때 HTML 과 자산을 저장해 캔버스에서 iframe 으로 띄우므로, 노드 안에서 스크롤이 되고 폭을 바꾸면 반응형이 실제로 따라온다. 화살표는 카드 머리가 아니라 **그 화면을 다음으로 보내는 링크나 버튼 자리**에서 나간다. 그 요소에는 테두리가 둘린다.

## 이 출구가 다른 점

| | 보통 페이지 | 화면 캔버스 |
|---|---|---|
| 결과 | HTML 한 장 | 폴더 하나(`index.html`, `screens/`) |
| 바깥 요청 | 없음 | 캔버스 라이브러리(React Flow)를 esm.sh 에서 받는다. 화면과 자산은 폴더 안에 있다 |
| 올리기 | `show.mjs publish <파일>` | `show.mjs publish <폴더>`, 문서에 끼웠으면 그 문서를 올릴 때 함께 |
| 렌더러 화면 검사 | 돈다 | 돌지 않는다. 직접 열어 본다 |

React Flow 는 끌기, 확대, 미니맵, 노드 사이 선을 맡는다. 손으로 짜면 그 셋이 기기마다 어긋나 이 출구만 예외로 바깥 스크립트를 받는다. 받는 사람이 인터넷에 닿지 않으면 캔버스가 뜨지 않는다. 그런 자리에 건넬 때는 화면 한 장씩을 보통 페이지의 그림으로 넣는다.

## 쓰는 자리

- 여러 갈래로 시작하는 흐름. 직접 가입한 사람과 초대 메일로 온 사람처럼 **시작점이 둘 이상**이면 시작점마다 맨 왼쪽 열에 세운다
- 상태나 자격에 따라 같은 주소가 다른 화면을 띄울 때. 같은 `path` 에 `id` 만 달리 두 화면으로 담는다
- 받는 사람이 기획자나 디자이너라 상자 이름보다 화면이 빨리 읽힐 때

**화면이 있는 흐름은 이 방식으로 보인다.** 사용자가 화면을 거쳐 가는 흐름을 `<ve-flow>` 상자나 그림 여러 장의 나열로 대신하지 않는다. 상자는 화면이 어떻게 생겼는지를, 나열은 어느 버튼이 다음으로 보내는지를 빠뜨린다. 흐름의 뼈대를 먼저 보이고 싶으면 `<ve-flow>` 를 위에 두고 바로 아래 캔버스를 끼운다.

한 화면의 전후만 보이면 되면 `.pair[data-compare]` 가 낫다. 화면이 하나도 없는 흐름(서버 사이 호출, 상태 전이)은 `<ve-flow>` 다.

## 왜 이런 모양인가

**왼쪽에서 오른쪽이 깊이다.** 위아래는 같은 깊이의 다른 갈래다. 이 규칙 하나로 지도를 대각선으로 읽지 않아도 되고, 어떤 화면이 몇 걸음 안에 있는지가 자리만 봐도 드러난다. 깊이는 사람이 정한다. 자동 배치에 맡기면 먼 길 하나 때문에 화면이 한 단 밀려난다.

**돌아가는 길은 그리지 않는다.** 들어온 길의 역이라 그으면 화살표가 양쪽으로 붙어 어느 쪽이 흐름인지 읽히지 않는다. 탭끼리 오가는 선도 같다.

**화면을 기기 안에 넣는다.** 폭이 700 이상이면 창 모양, 아래면 폰 모양으로 그린다. 반응형 제품은 폭마다 다른 화면을 띄우므로 어느 폭으로 본 것인지가 함께 보여야 한다.

## 쓰는 법

### 1. 설정

**화면을 채우기 전에 단계와 갈래를 코드에서 센다.** 라우트(페이지 파일, 라우터 표)와 화면이 갈리는 조건(로그인, 상태, 권한, 오류 응답)을 읽어 시작점, 화면, 그 화면에서 나가는 문, 실패하면 가는 곳의 목록을 먼저 만든다. 실패 갈래(잘못된 입력, 만료된 링크, 권한 없음, 결제 실패)는 기본으로 넣는다. 기억으로 깊이를 채우면 단계가 실제보다 줄고 실패 갈래가 빠진다. 다 그린 뒤 캔버스의 화면 수를 목록과 견주고, 뺀 것이 있으면 무엇을 왜 뺐는지 캔버스 옆 글에 적는다.

- **왜 목록이 먼저인가** - 가입 흐름을 네 단계로 그렸다가 「가입 절차가 원래 더 많지 않아?」, 「사용자가 보는 모든 화면을 순서대로 보여 준 거 맞아?」, 「실패 갈래까지 넣어서 다시 찍어 줘」가 차례로 돌아왔다. 세 번 다 그림이 코드보다 적었다.

[`../assets/canvas.config.example.mjs`](../assets/canvas.config.example.mjs) 를 작업 폴더에 `canvas.config.mjs` 로 복사하고 화면을 깊이별로 채운다. 필드는 [canvas-config](canvas-config.md) 에 있다.

```js
depths: [
  { title: "들어오는 길", screens: [
    { id: "signup", label: "가입", path: "/", click: "회원가입", exits: [{ to: "verify", by: "가입" }] },
    { id: "invite", label: "초대 메일의 링크", path: "/invitations/T/accept", exits: [{ to: "invite-signup", by: "가입하고 참여하기" }] },
  ] },
  ...
]
```

**`exits` 의 `by` 가 캔버스의 알맹이다.** 그 글자가 든 링크나 버튼을 찾아 테두리를 두르고 거기서 화살표를 낸다.

클릭 하나로 안 만들어지는 상태(창이 열린 상태, 칸을 채운 상태)는 화면의 `run` 에 브라우저에서 돌릴 JS 를 적는다. `await` 를 쓸 수 있고, 저장하는 것은 그 뒤의 DOM 이라 열린 창도 그대로 담긴다. 기다릴 초는 `wait`(기본 2)다.

### 2. 볼 만한 상태 만들기와 화면 뜨기

빈 DB 에서 뜨면 절반이 빈 화면이 된다. 단계마다 그 상태에 있는 계정을 시드로 만들어 두고(가입 직후, 조직 없음, 미인증 조직, 인증 마친 조직처럼), 화면의 `as` 로 그 계정을 고른다. 시드는 **로컬 DB 에서만** 돌린다. 데이터와 설정은 읽기만 한다는 정책(SKILL.md)이 여기도 그대로다.

```bash
node <스킬 폴더>/scripts/canvas/canvas.mjs snap     # 개발 서버가 떠 있어야 한다
node <스킬 폴더>/scripts/canvas/canvas.mjs build    # 브라우저 없이 몇 초. 설정을 고치고 다시 돌리기 가볍다
node <스킬 폴더>/scripts/canvas/canvas.mjs snap --only a,b   # 그 화면만 다시 뜬다. 앞에서 끊긴 snap 을 이을 때
```

브라우저는 있는 것을 고른다(`agent-browser`, 없으면 Playwright). `--browser playwright` 로 못 박는다.

### 3. 확인과 올리기

`.canvas/index.html` 을 열어 본다. 렌더러 검사가 없으므로 이것이 Step 4 다.

- 못 찾은 문이 있으면 `snap` 이 끝에 알린다. 그 화살표는 카드 머리에서 나간다
- 빈 화면이나 잘못된 상태는 시드 문제다
- 시작점이 둘 이상이면 맨 왼쪽 열에 다 서 있는지 본다

캔버스만 건넬 때는 폴더를 올린다. `raw/` 는 올리지 않는다.

```bash
node <스킬 폴더>/scripts/show.mjs publish .canvas --id <프로젝트>-<주제>
```

### 4. 문서에 끼우기

보고나 기획 문서 안에서 흐름을 보일 때는 그 페이지 원본에 `<ve-canvas>` 를 넣는다. 렌더러가 iframe 과 "새 창에서 크게 열기" 링크로 펼친다.

```html
<figure>
  <ve-canvas src="canvas" label="가입부터 첫 주문까지 단계별 실제 화면" height="720"></ve-canvas>
  <figcaption><span class="fig-n">그림 2</span>맨 왼쪽 열이 시작점이고, 화살표는 다음으로 보내는 버튼에서 나갑니다.</figcaption>
</figure>
```

- `src` 는 페이지 원본 옆의 캔버스 폴더다(`build` 가 쓴 `.canvas/` 를 `raw/` 없이 복사하거나 그 자리를 가리킨다). 페이지 밖(`..`)과 절대 경로는 렌더러가 거절한다. publish 가 이 경로를 보고 폴더를 페이지 아래에 함께 올리기 때문이다
- `label` 은 필수다. 프레임 제목이 된다. `height` 기본값은 680px 이고, 휴대폰 폭에서는 화면 높이의 70% 로 줄어든다
- 페이지는 더 이상 파일 하나로 닫히지 않는다. 받는 사람에게는 공용 공간 주소로 건넨다. 렌더한 HTML 파일만 보내면 캔버스가 비어 보인다
- 인쇄와 이미지 출구에서는 움직일 수 없으므로 프레임을 빼고 여는 링크만 남긴다(이미지 페이지에 넣으면 렌더러가 거절한다). 종이로 남길 문서면 대표 화면 몇 장을 그림으로 함께 둔다
- 렌더러의 화면 검사는 프레임 바깥까지만 본다. 캔버스는 올린 뒤 받는 사람 주소로 열어 노드가 뜨는지 직접 본다

## 캔버스에서 할 수 있는 것

- 노드 이름줄을 잡고 옮긴다. 옮긴 자리는 보기별로 남는다
- 화면 안에서 스크롤된다. 스크롤하면 화살표가 문을 따라 움직인다
- 폰과 데스크탑을 오간다
- 화면 만지기를 끄면 화면이 잠겨 캔버스를 휠로 훑을 수 있다
- 핀치는 캔버스를 당긴다. 화면 창이 확대되지 않는다

## 캔버스를 연 뒤 읽을 것

캔버스는 만드는 것이 목적이 아니라 보고 고치기 위한 것이다. 펼치면 대개 이런 것이 바로 드러난다. 보고에 쓸 때는 이것을 캡션이나 판정으로 옮긴다.

- 진입점이 없는 화면. 어느 버튼도 그리로 가지 않는데 존재한다
- 너무 깊은 화면. 자주 쓰는 것이 세 걸음 밖에 있다
- 같은 곳으로 가는 버튼이 한 화면에 여럿. 하나로 줄일 자리다
- 자격이나 상태에 따라 갈리는 화면. 막힌 사람이 보는 화면까지 함께 담으면 그 사람의 여정이 보인다

캔버스에 담은 화면 목록(`canvas.config.mjs`)은 그 자체로 문서다. 저장소에 남기고, 사람이 읽는 사이트맵 문서와 어긋나면 사람이 읽는 쪽을 정본으로 삼는다.

막히는 곳은 [canvas-troubleshooting](canvas-troubleshooting.md) 에 있다.
