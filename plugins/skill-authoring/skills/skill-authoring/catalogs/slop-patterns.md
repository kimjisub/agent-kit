# 스킬 slop 패턴 카탈로그 — 감사에서 반복 발견된 것

**로드 시점 — Step 2(진단)의 노이즈 축과 Step 4(작성)의 자기 점검에서.** 무엇을 남길지는 [house-style](../steps/40-house-style.md)이 정하고, 이 문서는 **뺄 것의 카탈로그**다 — 스킬 감사에서 반복 관측된 노이즈와 그 수정. 각 패턴: **증상 → 왜 slop인가 → 고침**.

## 1. undertrigger description
**증상**: description이 "무엇"만 있고 인용 트리거·형제 구분이 없다.
**왜**: description은 트리거의 전부인데, 발화 예시가 없으면 라우터가 안 부른다.
**고침**: `(<접두>) <무엇> — <상세>. "<발화1>", "<발화2>"류 요청에 발동합니다. (<겹치는 스킬>은 X.)`
- before: `클라이언트 미팅 전 브리핑 자동 생성. 회사 정보 + 내부 문서 + 최근 뉴스를 종합하여…`
- after: `클라이언트(고객사) 미팅 전 브리핑을 만든다 — … "이 회사 미팅 준비해줘", "고객사 브리핑"류 요청에 발동합니다. (포지션 등록·미팅 준비는 등록 스킬, 맥락 보강은 보강 스킬.)`

## 2. 헤더 drift + meta-noise 괄호
**증상**: 같은 개념을 스킬마다 다르게 표기(`진짜 일의 본질` vs `일의 본질` vs `목적`; 핵심 원칙의 괄호가 스킬마다 다른 것).
**왜**: 스위트 전체의 일관성이 깨지고, `진짜` 같은 hype는 filler.
**고침**: [house-style](../steps/40-house-style.md#정규-섹션명과-drift-함정)의 정규형으로 통일. 괄호 provenance 를 다는 스위트는 표기를 하나로.
- grep: `grep -rn "^## 목적\|^## 일의 본질\|핵심 원칙" --include=SKILL.md`

## 3. 북극성 규칙 N중 반복
**증상**: 한 규칙("가설까지만"·"단일 출처"·"물리 폴더 아님")을 3~6회 재진술.
**왜**: rule-of-three를 넘는 반복은 지시 예산을 먹고 신호를 흐린다.
**고침**: 규칙을 한 곳(가장 명확한 자리)에 강하게 두고 나머지 echo 삭제 → 1~2회로. 단, 서로 다른 맥락에서 다른 측면을 말하면 중복 아님(구분).

## 4. 마커와 사고 기록
**증상**: `⛔ ⚠️ 🔴 ❌ ✅ 📖 💰` 같은 경고·장식 이모지와 `**bold**` 를 강조로 쓰고, 규칙마다 「실측 2026-..: 무엇이 났다」 경위를 붙인다.
**왜**: 전부 강조하면 아무것도 강조 안 된 것과 같다. 경위는 규칙보다 길어져 지시가 묻히고, 문서가 사고 일지가 된다.
**고침**: 이모지 마커는 쓰지 않는다. 되돌릴 수 없는 게이트는 제목과 문장으로 드러낸다(「정책 — 위반 금지」). 경위는 지우고, 알면서 어기기 쉬운 규칙의 이유는 날짜 없이 한 문장으로 남긴다. 예문·판정 예는 경위가 아니므로 지우지 않는다. 값으로 쓰는 기호(★4+, 보드에 찍히는 ⚠ 표시)는 해당 없다.
- 검사: `scripts/check-links.py` 가 `마커`·`사고기록` 으로 센다(코드 블록과 `SKILL.intent.md` 는 제외).

## 5. frontmatter description 안 bold
**증상**: `description: … **재해석 JD** …` 처럼 description에 `**`.
**왜**: frontmatter는 마크다운 렌더가 안 돼 `**`가 리터럴 노이즈로 읽힌다.
**고침**: description에서 `**` 제거.
- grep: `grep -rnE "^description:.*\*\*" --include=SKILL.md`

## 6. dangling 크로스-스킬 라우팅
**증상**: 살아있는 스킬이 deprecated/이동된 스킬로 사용자를 계속 보낸다(예: `_legacy/`로 옮긴 스킬을 4곳이 여전히 참조).
**왜**: 플러그인이 로드하지 않는 스킬로 안내 = 실제 라우팅 버그.
**고침**: 스킬을 rename·deprecate·이동하면 `grep`으로 **모든** 참조를 찾아 재지정한다. 흡수한 스킬로 포인터를 옮기거나 문구를 정합화.
**⚠️ 앵커까지 본다 — grep 으로는 못 찾는다.** 파일이 살아 있어도 **헤딩을 개칭하면 그것을 가리키던 링크가 죽는데**, 옛 앵커 문자열을 모르니 검색어를 만들 수 없다. `scripts/check-links.py` 로 전수 검사한다(실측 2026-09-04: 한 스킬에서 29건이 죽어 있었고 10건이 「단일 출처」라 선언한 게이트를 가리켰다).
- grep: 대상 스킬명을 word-boundary로. `grep -rnE "(^|[^a-z-])<스킬명>([^a-z-]|$)" --include=SKILL.md`

## 7. rot하는 하드코딩 카운트
**증상**: "SKILL.md 12개를 카운트, 12개면 PASS", "7개 컨설팅 스킬" 같은 매직넘버가 서로 안 맞음. **넓게는** 회고 분석 %·벤치마크 수치 같은 **도메인 상수**가 근거·확인일 없이 박힌 것, "완결 예시"라면서 `[수치]`·`{}` 플레이스홀더가 남은 예시도 같은 rot이다.
**왜**: 스킬·버전이 늘면 전부 stale. 여러 곳에 박히면 상호 모순. 도메인 수치는 코퍼스(회고 등)가 커지면 조용히 틀려지고, 플레이스홀더가 남은 "완결 예시"는 신뢰를 깎는다(instruction-shaping §2 "하나의 탁월한 예시").
**고침**: 동적 카운트("개수를 센다, 0이면 sync 안 됨") 또는 정성 표현으로. 도메인 수치는 **출처·확인일을 달거나 런타임 조회로 뺀다**(세제 같은 상수를 하드코딩 않고 런타임에 확인하는 방식). 예시는 실제값으로 완결하거나 "골격"이라 명시한다. 예시 출력의 숫자도 권위적으로 읽히면 소프트하게. **헤딩에는 어떤 카운트도 넣지 않는다** — 축·슬롯 수가 헤딩에 있으면 하나 늘 때마다 앵커가 바뀌어 그것을 가리키던 링크가 죽는다(실측 2026-09-04: 이 스킬의 rubric 헤딩 「9축」과 house-style 헤딩 셋이 그랬다).

## 8. DRY 위반 — 허브 규칙 재정의
**증상**: (스위트에 속한 스킬) 소비 스킬이 허브 스킬의 저장 프로토콜·프리뷰 템플릿을 다시 정의.
**왜**: 허브가 "스킬마다 다시 정의하지 말고 여기 단일 출처를 따르라"고 명시한 것과 충돌.
**고침**: 재정의 대신 허브 체크포인트를 **참조**. ([house-style](../steps/40-house-style.md#허브-스킬--단일-출처와-dry-스위트에-속한-스킬만))

## 9. 형제 스킬 간 데이터소스 drift
**증상**: 같은 자산을 형제 스킬이 다른 소스로 본다(예: 미팅록을 한 스킬은 문서 저장소에서, 다른 스킬은 DB 에서).
**왜**: 어느 게 canonical인지 모호 → 한 스킬이 구세대 데이터모델에 고착.
**고침**: canonical 소스를 확정하고 정합. **소스 진실이 불확실하면 추측하지 말고 사용자에게 확인**(도메인 진실).

## 10. 병합 헤더·번호 버그
**증상**: `## Step 5: 확인 → Step 6: 반영` 처럼 두 스텝을 한 헤더에 묶음, 번호 체계 깨짐.
**왜**: 탐색성·번호 참조가 무너진다.
**고침**: 스텝당 헤더 하나로 분리, 번호 정합.

## 11. 워크플로우를 요약한 description
**증상**: description이 "언제 쓰나"를 넘어 스킬의 **절차·단계·워크플로우를 요약**한다(예: "…등록 → 조사 → 브리핑 생성까지 잇는다"를 트리거 예시 없이 절차로).
**왜**: description은 트리거 판단용이고 본문은 트리거 후 로드된다. description이 워크플로우를 요약하면 에이전트가 **본문을 안 읽고 description 요약만 따르는 지름길**이 생겨, 본문의 스텝·게이트가 스킵된다(관측된 실패 — "2회 리뷰" 지시가 desc에 "리뷰"로 뭉개져 1회만 수행).
**고침**: description은 `무엇을 하는가(한 줄) + 언제(인용 발화) + 형제 구분`까지만. 절차·순서·단계는 본문으로 내린다. (undertrigger[#1]과 짝 — desc가 얇아도(트리거 부재) 두꺼워도(워크플로우 요약) 문제다. 가운데: 트리거는 풍부하게, 워크플로우는 본문에.)
**⚠️ 예외 — 형제구분·산출물 식별용 절차 서술은 제거하지 않는다.** desc 의 절차 서술은 종종 **트리거 재료**다: 소싱 스킬의 "전략 → 발굴 → 채점 → 마무리"는 포지션 재정의 스킬과 갈라주는 형제 구분이고, 재정의 스킬의 "산출 셋"은 이 스킬이 *무엇을 내놓나* = 트리거 판단 재료다. **판단 기준: 이 절차가 (a) 본문 스텝을 desc가 대체해 지름길을 만드나 → 제거, (b) 형제 스킬과의 구분·산출물 식별 신호인가 → 유지.** 무턱대고 절차를 지우면 트리거·형제구분이 약해진다(house-style의 description 공식 "무엇을 하는가 한두 절"과 정합).
- grep: description 라인에 `→`·`Step`·"…까지 잇는다/수행한다" 류 절차 서술이 있나 눈으로. 있으면 (a)/(b) 판정.

## 12. 정합성 drift — peer·산출물 계약·허브 다중기재
**증상**: dangling(#6)·허브-DRY(#8)가 잡는 "허브↔스킬" 세로축 말고, **가로·문서 내부** 정합이 어긋난 것 — (a) 형제 스킬이 소유한 도메인 개념(수집 스키마·BACKOUT 신호 세트 등)을 참조 않고 **재정의**, (b) A 스킬이 쓴 산출물 슬롯을 B 스킬이 **다른 스키마로 소비**(계약 불일치 — 예: `cycle_N/전략.md`의 a/b/c 슬롯을 소싱이 다르게 읽음), (c) 허브 문서가 **같은 사실(경로·소유 매핑)을 트리·표·명명규칙에 다중 기재**해 한 곳만 고치면 나머지가 stale(예: 문서 라우팅이 허브 세 자리에 각각).
**왜**: (스위트에 속한 스킬) 파이프라인 스킬 스위트는 스킬끼리 산출물을 주고받는다 — 계약이 어긋나면 다운스트림이 조용히 깨진다. #6/#8과 한 가족(정합성)이나 축이 다르다(세로 vs 가로·내부).
**고침**: (a) 개념 소유 스킬을 정하고 나머지는 참조(peer-SSOT). (b) 산출물 스키마는 그 문서 type의 소유 스킬(허브 레지스트리)에 두고 소비 스킬은 그 슬롯을 그대로 읽는다. (c) 허브의 같은 사실은 한 자리(정본)에 두고 나머지는 포인터. **소스 진실이 불확실하면 추측 말고 사용자 확인**(#9와 동일).
- grep: 같은 경로·enum·개념명이 여러 파일·여러 표에 독립적으로 박혔나(한 곳 수정 시 나머지가 stale 되는 구조인가).

## 13. 앵커를 깨는 헤딩 마커
**증상**: `## ⚠️ 회사는 따로 훑는다` 같은 헤딩을 `#회사는-따로-훑는다` 로 가리키는 링크.
**왜**: GitHub 슬러그는 이모지를 지우고 **그 자리 공백을 하이픈으로 남긴다** — 실제 앵커는 `#️-회사는-…` 라 그 링크는 안 걸린다. 눈으로는 멀쩡해 보이고 grep 으로도 안 잡힌다. #4(마커 인플레이션)가 신호를 죽인다면 이쪽은 **라우팅을 죽인다.**
**고침**: 링크를 이모지 슬러그에 맞추지 말고 **헤딩에서 마커를 뗀다**(맞추는 쪽은 눈으로 검증이 안 된다). 검사는 `scripts/check-links.py`.
- 실측 2026-09-04: 한 문서의 `##` 헤딩 여섯에서 경고 이모지를 떼자 죽어 있던 링크 여섯이 함께 살아났다.

## 14. 문서 안 목차와 blockquote
**증상**: 문서 머리의 `## 목차`, 근거·주의를 `>` 로 접은 문단.
**왜·고침**: → [house-style 목차와 blockquote 금지](../steps/40-house-style.md#문서-안-목차와-blockquote-금지).

## 15. 문장으로 쓴 헤딩

**증상**: `## 절차와 사고는 다른 층이다`, `### 왜 X 가 중요한가` 처럼 헤딩이 주장이나 의문문이다. `check-links.py` 의 `문장헤딩` 이 잡는다. **왜·고침**: → [house-style 헤딩의 형식](../steps/40-house-style.md#헤딩의-형식--명사구).

## 16. 면제 조항과 선택 표현

**증상**: 「안 되면 넘어간다」·「어려우면 나중에」·「미응답 시 미결로 남긴다」 같은 면제 조항, 「가능하면」·「권장」·「~해도 된다」 같은 선택 표현, hook·스크립트가 검사하게 된 항목을 여전히 설명하는 산문(실측 사례 나열 포함). **왜 slop인가**: 면제 조항이 곧 기본 행동이 되고, 선택 표현은 안 하는 쪽으로 읽히며, 검사가 정본이 된 뒤의 산문은 사본이라 낡는다. **고침**: 지키게 하고 싶은 규칙 옆의 면제 조항을 지운다(한 번 더 강조하는 것보다 확실하다). 필수면 조건문을 지우고 정말 선택이면 조항을 없앤다. 기계가 세게 됐으면 그 산문을 지운다. 실측: 한 세션이 반복 위반 지점 여덟을 고치며 707단어를 더하고 한 줄도 빼지 않았다.

## 과잉 교정 — 남겨야 할 것

anti-slop을 기계적으로 밀면 목소리를 죽인다. 다음은 **고치지 않는다** (→ [house-style](../steps/40-house-style.md)):
- **em-dash(—)·가운뎃점(·)** — 한국어 하우스 구분자. 일괄 제거 금지.
- **provenance 괄호**("…에서 반복된 것") — meta처럼 보여도 신뢰 신호. 표기만 통일.
- **작은 스킬을 refs로 강제 분할** — load-bearing이면 본문 유지가 옳다.
