# 파일과 폴더 — 가르는 이유·자리·라우팅

**로드 시점 — Step 3(설계)에서 문서를 여럿으로 가르거나, 가른 것을 폴더에 두고 READ 목록으로 이을 때.** 문서 하나의 뼈대는 [30-structure](30-structure.md)이고, 이 문서는 파일 사이의 규칙이다. 절차의 정본은 [SKILL.md](../SKILL.md#절차)다.

## 파일을 가르는 축 — 그리고 상한

한 파일에서 갈라져 나갈 **이유**는 이것뿐이다. 길이는 가르는 이유가 아니다.

| 축 | 질문 | 갈라진 예 | 안 갈라야 할 예 |
|---|---|---|---|
| **시점** | 언제 읽나가 다른가 | 10(전략) / 20(발굴) / 40(종료) | 발굴 안의 하위 스텝 — 한 시점 안의 순서 |
| **조건** | 어느 갈래를 택했느냐로 갈리나 | 채널 21·22·23 | 위생·5축 — 채널 무관이라 20 에 |
| **독자** | 읽는 주체가 다른가 — **그리고 그 주체에게 파일이 실제로 가는 경로가 있는가** | 브리프에 실려 나가는 rubric / 그것을 거는 메인의 실행 모델 | 둘 다 메인이 읽으면 한 파일. 「서브에이전트가 읽는다」고 선언만 하고 싣는 코드·절차가 없으면 독자 축이 아니다 |
| **성격** | 읽고 따르는 것인가, 찾아보는 것인가 | 31(필드 사전) | 스텝 안 판정 기준 — 따르는 것 |
| **매체** | 문서인가 코드인가 | `linkedin-scraper/*.js` | 명령 한 줄 호출 예시 — 문서에 |

이유 없이 가르면 **읽을 때마다 파일이 하나 늘고, 그것이 한 번이라도 안 열리면 그 절차가 통째로 빠진다.** 실측: `references/README` 가 「매 사이클 셋을 반드시 연다」고 적어 뒀는데도 메인이 한 사이클 동안 하나도 안 열었고, 결과가 임시 스크립트 151개와 평소의 몇 배인 모델 비용이었다.

**그러나 상한은 있다.** 본문 500줄·reference 300줄은 skill-creator 가 컨텍스트 비용에서 세운 실용 규칙이고, **큰 파일은 안 열린 것과 같은 결과를 낸다** — `Read` 가 토큰 cap 에 걸려 앞부분만 오면 뒷부분 규칙은 없는 것이다(실측 2026-09-04: 398줄짜리 `30-scoring` 을 두 번에 나눠 읽어야 했다). 매번 필요하고 독자가 같아도 상한을 넘으면 **시점 축으로** 가른다 — 한 시점 안에서도 「먼저 할 것 / 나중에 할 것」은 갈린다.

- **깊이는 2단까지.** SKILL → 자식은 되고 자식 → 손자는 안 된다(부분 읽기로 유실). 자식이 형제를 가리키는 것은 같은 층이라 된다. 다른 스킬의 정본을 가리키는 것은 예외.
- **실행 순서 번호는 `steps/` 에만.** 조건 축(채널)이 같은 번호대에 끼면 「번호가 순서」라는 약속이 절반만 참이 된다. 변주는 `variants/` 로 가고, 그 앞 번호는 순서가 아니라 부모 스텝 표시다(→ [폴더](#폴더--가른-이유에-따른-자리)).
- **독자 축은 전달 경로가 있어야 선다.** 선언만으로는 그 독자가 파일을 받은 적이 없다. 실측 2026-09-04: 채점 문서를 「채점 서브에이전트에 전문을 넘기는 단위」라 세 곳에 선언했는데, 워크플로의 rubric 인자는 실행 환경의 평가기준·전략을 싣고 그 문서를 싣는 코드는 없었다 — 그 분할이 실제로 서 있는 근거는 성격(무엇으로 / 어떻게)과 상한이었다.

**실제로 내린 판단.**

| 스킬 | 상황 | 판단 |
|---|---|---|
| 리서치 스킬 | 536줄, 하위 문서 0개, 8단계 템플릿·예시가 선택적 심화 | 분할 → 157줄 + refs 3개 |
| 등록 런북 | 175줄 선형 런북, 표가 매 실행 필요 | 분할 안 함. 경계 반복·description 배관만 정리 |
| 허브 스킬 | 375줄 단일 출처 허브, 트리·라우팅이 로드 시점 필수 | 분할 안 함. description 노이즈만 |
| 소싱 스킬의 채점 문서 | 398줄, 앞뒤 둘 다 매 사이클 필요. 앞은 「무엇으로 평가하나」(rubric), 뒤는 「어떻게 거나」(실행 모델) | 분할 → rubric 155 + 실행 모델 252. 가를 때는 독자 축이라 봤는데 점검에서 서브에이전트에 그 문서를 싣는 경로가 없었다. 실제로 선 근거는 성격 축과 상한이다 |

## 폴더 — 가른 이유에 따른 자리

파일을 가르는 이유가 다섯이면 폴더도 그 다섯에서 나온다. `references/` 하나에 전부 떨구면 여는 쪽은 열어 보기 전까지 그 파일이 따라야 하는 절차인지, 골라 쓰는 목록인지, 자기가 읽을 것이 아니라 넘길 것인지 모른다. 실측 2026-09-17: references 안에 여섯 종류(절차의 연장·조건 변주·카탈로그·서브에이전트 프롬프트·필드 맵·실행 코드)가 섞여 있었고, 한 스킬은 references 없이 문서 종류별로, 다른 스킬은 `agents/` 를 따로 만들어 스킬마다 구조가 달랐다.

```
<skill>/
  SKILL.md          목적·배경, 핵심 원칙, 정책, 절차, 산출, 생태계
  SKILL.intent.md
  steps/            시점 축. 절차의 연장. 번호 접두사. SKILL.md Step N 이 READ 로 지정하고 순서대로 따른다
  variants/         조건 축. 채널·엔티티·트랙·시나리오별 절차 변주. 스텝이 조건에 맞는 하나만 연다
  catalogs/         성격 축(찾아보는 것). 핵심 원칙 N 이 가리키는 기법·예시·어휘·실패 모드
  prompts/          독자 축. 서브에이전트에게 통째로 넘기는 텍스트. 페르소나 포함
  schemas/          매체 축(기계 계약). JSON 스키마·필드 맵·enum·산출 보드 형식·env 이름
  assets/           매체 축(산출물 양식). 템플릿·HTML
  scripts/          매체 축(실행 코드). 앱 크기면 scripts/<이름>/ 하위 폴더
```

**판정 순서** — 여섯 질문을 이 순서로 묻고 앞에서 예가 나오면 거기서 끝난다. 축이 서로 직교하지 않아 한 파일이 두 축에 걸리므로(페르소나 파일은 조건이면서 독자, 채널 문서는 시점이면서 조건), 순서가 자리를 하나로 정한다.

1. 실행되는가 → `scripts/`
2. 값 이름과 형식의 정본인가(필드 맵·enum·JSON 스키마·산출 보드 형식·env 이름) → `schemas/`
3. 산출물에 그대로 들어가는 양식인가 → `assets/`
4. 서브에이전트에게 통째로 넘기는가(페르소나 포함) → `prompts/`. 메인도 같이 읽는 공유 문서(진단 rubric 처럼 전달도 되지만 메인이 따르는 것)는 prompts 가 아니라 steps 다
5. 메인이 읽는 문서인데 골라 쓰는가 → `catalogs/`
6. 읽고 따르는 문서인데 조건에 따라 하나만 여는가 → `variants/`, 언제나 여는가 → `steps/`

5 와 6 에 같이 걸리는 파일(원칙 뒤에 목록이 붙은 채널 문서)은 자리 문제가 아니라 가르라는 신호다. 조건이 붙은 카탈로그는 `variants/` 가 아니라 `catalogs/` 에 두고 파일명에 조건을 쓴다(`catalogs/<채널>-recall-killers.md`). `variants/` 는 조건에 따라 하나만 여는 **절차** 문서만 받는다.

규칙 넷.

- **빈 폴더는 만들지 않는다.** 파일이 하나 생길 때 폴더가 생긴다. 원칙-에세이는 SKILL.md 하나로 끝나고 보통 스킬은 폴더 하나나 둘이다. 일곱을 다 갖추려는 것이 곧 흉내다.
- **폴더명과 파일명은 영문 kebab-case 다.** 한글 경로는 git 이 quotepath 로 escape 해 status·diff 가 안 읽히고(실측 2026-09-17: 한 스킬의 한글 폴더), macOS NFD 정규화로 grep 이 놓친다.
- **실행 순서 번호는 `steps/` 에만 단다(10·20·30).** `variants/` 는 조건 값으로 이름 짓고 어느 스텝의 변주인지를 그 번호로 앞에 붙인다(`variants/20-linkedin.md`). 루트 갈래 표에서 갈리는 갈래 전체의 변주는 번호 없이 이름만(`variants/<갈래>.md`). 조건이 두 차원이면(목적 x 시나리오, doctype x brand) `variants/<차원>/` 로 한 단 내린다.
- **폴더 안 README 는 두지 않는다.** 대응표의 정본은 SKILL.md 의 READ 목록이고 폴더 이름이 종류를 말한다.

스킬 폴더에 안 들어가는 것 셋.

- **플랫폼이 자리를 정한 것.** `agents/`·`hooks/`·`commands/` 는 Claude Code 가 그 경로에서 읽는다. 그대로 둔다.
- **실행에 안 쓰이는 이력과 미결.** 어느 스텝도 열지 않는 마이그레이션 기록·결정 대기 목록은 `SKILL.intent.md` 나 `planning/` 으로 간다. references 가 그동안 이런 것의 서랍 노릇을 했다.
- **다른 스킬이 소유한 정본.** 포인터만 둔다(→ [house-style 허브](40-house-style.md#허브-스킬--단일-출처와-dry-스위트에-속한-스킬만)).

라우팅은 경로만 바뀐다. 로더는 SKILL.md 만 파싱하고 나머지는 포인터로 열므로 폴더 이름에 의미를 두는 곳이 없고, CI 의 문법 검사가 글로브면 `scripts/` 로 옮겨도 잡힌다. 옮길 때는 `check-links.py` 로 `파일없음` 과 `고아`(어디서도 안 가리키는 md)를 0 으로 만들고, md 밖의 경로(hook·스크립트 헤더)는 grep 으로 따로 잡는다. 실측 2026-09-17: md 밖에서 스킬 경로를 박아 둔 곳이 셋 있었고 전부 한 스크립트 폴더를 가리켰다.

## 실행 코드의 자리 — 문서가 아니라 파일

코드블록에 스크립트를 박아 두면 붙여넣다 따옴표가 깨지고, CI 문법 검사를 못 받고, 고칠 때마다 문서 편집이라 실수가 난다. 판별 질문은 하나다. 이걸 검증하려면 코드블록에서 꺼내 파일로 만들어야 하나. 그렇다면 처음부터 파일이다.

| 성격 | 어디에 | 예 |
|---|---|---|
| 그대로 실행되는 한 덩어리. 매번 같은 코드가 통째로 돈다 | 파일(`.sh`·`.js`·`.py`) + 문서엔 호출 한 줄 | 환경 수집 스크립트 · 크롤러 · 이 스킬의 `scripts/` |
| 사람이 골라 쓰는 개별 명령. 맥/윈도우로 갈리고 승인받아 하나씩 | 문서 코드블록 | 진단 스킬의 항목별 설치 명령 |
| 한두 줄 호출 예시 | 문서 코드블록 | 스크립트 호출법 · MCP 호출 예 |

파일로 뺄 때는 헤더 주석에 계약(호출법·출력 값 이름·주의)을 적고, 문서에는 호출 한 줄과 무엇이 나오는지만 남긴다. 스크립트가 뱉는 값 이름을 바꾸면 그것을 소비하는 문서를 같은 커밋에서 고친다. 셸 스크립트는 CI 의 문법 검사(`sh -n`)를 받게 둔다.

- **worked example** — 한 진단 스킬의 환경 수집은 문서 코드블록 90여 줄이었다. 파일로 빼고 문서엔 호출 한 줄 + 수집되는 값 표만 남기니 241줄 → 138줄이 되고 판정 전용 문서가 됐다. 반대로 같은 스킬의 복구 명령들은 그대로 뒀다. 맥/윈도우가 갈리고 사용자 승인 후 골라 실행하는 것이라 실행 단위가 아니다.

## 라우팅 — 정본은 READ 목록

쪼개는 순간 「언제 무엇을 여나」를 누군가 알아야 한다. 그 앎은 세 곳에 있고 역할이 다르다.

| 층 | 무엇 | 누구를 위한 것 | 역할 |
|---|---|---|---|
| **순서 개요의 READ 목록** | `1. 전략  READ ← 10-strategy — 검색 가능한 페르소나 인터뷰` | 이 스킬을 실행하는 에이전트 | **정본.** 「이 사이클에 무엇을 읽나」가 한눈에 보인다 |
| 스텝 슬롯의 포인터 | `**쓴다** — search.js (→ 채널 문서 §검색)` | 지금 그 스텝을 실행하는 에이전트 | 보조 — 그 순간에 다시 가리킨다 |
| 문서 머리의 로드 시점 | `**로드 시점 — 실행 루프가 채널 A 를 열 때.**` | 지금 이 파일을 연 에이전트 | 역방향 확인 — 「내가 이걸 지금 읽는 게 맞나」 |
| 폴더 이름 | `steps/`·`variants/`·`catalogs/`… | 처음 오는 사람 | 열기 전에 종류를 안다 |

**왜 READ 목록이 정본인가** — 모아둔 목록만이 「전체를 읽었나」를 검사하게 해 준다. 슬롯에 흩으면 그 검사가 불가능하다. 목록이 잊힌 실측(2026-08-29)은 있지만, 그 원인이 「목록이라서」인지 「목록에 이유가 없어서」인지는 갈린다 — 그래서 **각 줄에 「무엇을 위해」를 단다.** `READ ← 20-retrieval` 이 아니라 `READ ← 20-retrieval — R1~R5 없이 발굴하면 즉흥이 된다`.

포인터 규칙 둘.

- **링크는 절(#앵커)까지 가리킨다.** 파일 통째로 가리키면 어디를 읽을지 모른다. 예외는 전문을 읽게 하는 자리(READ 목록·로드 시점 문단)의 파일 링크다. **요약을 링크에 덧붙이지는 않는다** — 같은 사실을 여러 곳에 요약으로 두면 한 곳 고칠 때 나머지가 낡는다([slop-patterns #12](../catalogs/slop-patterns.md#12-정합성-drift--peer산출물-계약허브-다중기재)). 앵커가 요약을 대신한다.
- **규칙은 한 곳, 포인터는 여러 곳 — 단 안전장치는 한 줄로 반복한다.** 같은 규칙이 네 파일에 통문장으로 있으면 한 곳을 고칠 때 셋이 낡는다. 그러나 **그 파일을 열었을 때 그 규칙 없이는 실행이 틀어지는 것**(「컷이어도 행을 남긴다」 — 안 남기면 dedup 이 깨진다)은 한 줄로 반복한다. 그것은 반복이 아니라 안전장치다. 반복하는 줄은 정본을 가리킨다. **정본은 그 규칙이 적용되는 스텝을 가진 파일이다** — 「세 풀을 다 판다」는 R1 이 있는 20 이 정본이고, 채널 문서와 SKILL.md 는 규칙 한 줄과 R1 앵커만 둔다. 근거는 정본에만 — 반복 줄에 근거까지 따라가면 다시 통문장이 된다.

- **왜 READ 목록에 이유를 다나** — 실측 2026-08-29: `references/README` 가 "매 사이클 셋을 반드시 연다"고 적어 뒀는데도 메인이 한 사이클 동안 셋 중 하나도 안 열었다(임시 스크립트 151개, 평소의 몇 배인 모델 비용). 목록이라서 잊혔는지 이유가 없어서 잊혔는지는 갈리므로, 목록은 두고 이유를 단다.
- **왜 규칙은 한 곳인가** — "한쪽을 돌았다고 다른 쪽을 줄이지 않는다"가 네 파일에 통문장으로 있었다. 한 곳을 고치면 셋이 낡는다.

## 자식 문서 — 머리의 부모 스텝 대응표

조건 구체화 문서(`variants/` 의 채널·플랫폼·모드별 문서)는 헤딩을 **그 갈래의 고유 구조대로** 두되, 로드 시점 바로 아래에 **부모 스텝과의 대응표**를 둔다. 갈래 전체의 변주도 같다. 그때 부모는 루트의 갈래 표와 스텝이다.

```markdown
**로드 시점 — 실행 루프가 채널 A 를 열 때.** 공통은 발굴 절차 문서, 여기는 채널 A 에서만 다른 것.

| 부모(발굴 절차) | 이 문서 |
|---|---|
| 1 넓게 검색 | §검색 — 이 채널은 직무코드·다축 OR·역방향·빈 태그·본문 다섯 축을 다 돈다 |
| 2 값싼 훑기 | §대량 훑기 실행 모델 — 요약 일괄 덤프 |
| 4 저장 | `ingest.js <채널>` |
| 3 · 5 | 부모 그대로 |
```

**왜 헤딩을 물려받지 않나** — 채널마다 부모 스텝 안의 모양이 다르다. 한 채널의 검색은 축 다섯이고 다른 채널의 검색은 검색식 하나의 루프다. 헤딩을 부모 스텝 이름으로 통일하면 그 하위 구조가 H4 로 내려가 깊이 규약과 부딪히고, 부모 스텝 번호를 고칠 때 자식 전부의 헤딩이 바뀐다. 대응표는 **「2 에서 이 채널은 뭐가 다른가」를 한 표에서 찾게** 하면서 결합도를 안 올린다.
