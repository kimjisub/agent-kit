# 스킬 진단 루브릭 + 병렬 감사 레시피

**로드 시점 — Step 2(진단)에서, 기존 스킬을 다듬기 전에.** 형식의 정본은 [house-style](40-house-style.md), 뺄 것의 목록은 [slop-patterns](../catalogs/slop-patterns.md)이고, 이 문서는 그 둘을 **축으로 묶어 grade 를 내는 법**과 스킬이 많을 때의 병렬 감사 레시피다.

## 루브릭 — 축별 평가

축 수를 헤딩에 넣지 않는다. 축이 늘 때마다 앵커가 깨져 그것을 가리키던 링크가 죽는다(#7 rot 하는 하드코딩 카운트 — 이 문서가 실제로 두 번 겪었다).

각 스킬을 아래 축으로 보고 **`파일:라인` 근거**를 붙인다. 축별로 grade(good / minor / needs-work).

1. **description** — 무엇을 + 언제(구체 발화)가 명확한가? "언제 쓰는지"가 description에 다 있나, 본문에 흩어졌나? 인용 트리거·형제 구분이 있나? 모호(undertrigger)하거나 과한가? **워크플로우를 요약하나?**(형제 구분·산출물 식별용 절차 서술은 예외 → [slop #11](../catalogs/slop-patterns.md#11-워크플로우를-요약한-description)) — description이 스킬의 절차·단계를 요약하면 에이전트가 본문을 안 읽고 description만 따르는 지름길이 생긴다(관측된 실패). "하는 일 한 줄 + 언제 쓰나"까지만, 워크플로우 요약은 본문 몫.
2. **progressive disclosure / 길이** — 본문이 &gt;500줄인가? SKILL.md 밖으로 뺄 선택적 심화가 본문에 있나, 반대로 load-bearing을 억지로 뺐나? 본문→ref 포인터가 명확한가? 참조가 1단계 깊이인가(중첩 참조는 부분 읽기로 정보 유실)? (반대로 너무 얇아 부실하지 않은가?)
3. **노이즈 / slop** — [slop-patterns](../catalogs/slop-patterns.md)의 패턴(반복·마커·filler·rule-of-three·bold-in-desc·meta 괄호·워크플로우 요약 desc). 구체 인용.
4. **지시 형식 (instruction shaping)** — 지시가 행동을 실제로 좁히는 형식인가? (→ [instruction-shaping](41-instruction-shaping.md)) 세부: (a) 대문자 MUST/NEVER/ALWAYS를 이유 없이 남발하나? reframe해 근거를 붙일 곳은? (b) **금지 지시가 긍정 레시피로 나을 곳** — "산출물 모양 틀림"을 금지 리스트로 잡고 있으면 긍정 레시피/템플릿으로 전환 후보. 거꾸로 "알면서 어기는" 규율 실패를 맹숭한 문장으로 두었으면 합리화 표·게이트가 필요. (c) **output**이 산문 서술이 아니라 템플릿·예시로 고정됐나? (d) **how**가 검증 게이트(주장 전 확인)로 명시됐나?
5. **명령형 / 명료성** — 수동태·애매한 지시("적절히 처리"), 초장문 run-on, 중첩 괄호. 모호 서술을 명시적 단계로 바꿀 곳은?
6. **구조 / 오버피팅** — 특정 예시에 과적합해 일반성이 떨어지나? 헤더가 탐색하기 쉬운가, 명사구인가(문장 헤딩은 `check-links.py` 의 `문장헤딩`)? 아키타입에 맞나?
7. **검증 가능성 / 합리화 빈틈** — 이 스킬 산출물의 성공을 무엇으로 확인하나(Capture Intent ④)? 규율·게이트가 걸린 스킬인데 "알면서 어기는" 빈틈(저장 스킵·confirm 우회)이 열려 있나? 되돌릴 수 없거나 대외로 나가는 산출인데 검증 절차가 없나? (→ instruction-shaping §4) **산출물이 반복 갱신되는 성격**(대화형·장기관계·파이프라인 재진입)이면, 새 정보가 왔을 때 이전 산출과 화해하는 규율(diff 제시·임의 덮어쓰기 금지·미결 잔류·전제 "얇음"의 관측 가능한 판정)이 있나?
8. **파일 경계 (스킬이 여러 파일일 때)** — 앞 일곱 축이 *한 파일 안*을 본다면 이 축은 *파일 사이*를 본다.
   - (a) **가른 이유** — 다섯 축(시점·조건·독자·성격·매체) 중 하나인가, 그냥 길어서인가. 거꾸로 상한(본문 500·그 밖 300)을 넘어 뒷부분이 안 읽히는 파일은 없나. 독자 축으로 갈랐으면 그 독자에게 파일이 실제로 가는 경로(코드 인자·브리프 절차·hook)가 있나, 선언뿐인가.
   - (b) **한 파일에 성격 다른 둘** — 독자가 다르거나 로드 시점이 다르면 갈릴 후보다(→ [31-files 분할](31-files.md#파일을-가르는-축--그리고-상한)).
   - (c) **로드 시점과 내용의 일치** — 「이 phase 는 이 파일을 안 읽는다」고 적어 두고 정작 그 phase 가 필요한 것을 담고 있는 경우가 실재한다.
   - (d) **배치와 읽는 순서** — 절 순서가 실행 순서와 같은가(검색법이 아웃리치 템플릿 뒤에 있으면 검색하려는 사람이 문서 뒤부터 읽는다). 전제가 그것을 쓰는 곳보다 앞에 오는가. 처음 여는 사람이 어디부터 읽을지 문서가 말하나(로드 시점 한 줄). 스텝 안이 그 스텝의 실행 순서대로 서 있나(기계가 앞단이면 도구가 먼저). 자리 이름(본다·가른다…)이 볼드 라벨로 박혀 있지 않나, 결정에 안 쓰이는 실측이 문장 안에 괄호로 끼어 있지 않나, 판단 기준인 근거를 뒤로 접어 버리지 않았나.
   - (e) **라우팅** — READ 목록의 각 줄에 「무엇을 위해」가 있나. 링크가 파일 통째가 아니라 절(#앵커)까지 가리키나. 같은 규칙이 여러 파일에 있으면 정본이 그 스텝을 가진 파일이고 나머지는 한 줄과 앵커뿐인가. `steps/` 로 가른 스킬의 루트 스텝이 규칙 본문을 되풀이하지 않고 가리키기만 하나. 자식 문서(채널·모드)가 머리에 부모 스텝 대응표를 두었나. `check-links.py` 가 `앵커없음`·`마커앵커`·`고아`·`문장헤딩` 을 0 으로 내나.
   - (f) **정책 절** — 정책 절 하나를 읽으면 게이트 전체가 보이나(본문이든 한 줄 포인터든). 각각 적용 시점이 달려 있나. 스텝에 붙어야 뜻이 서는 게이트를 정책 절로 옮겨 스텝 맥락을 끊지 않았나, 거꾸로 스텝에만 있어 「막는 것 전체」가 안 보이지 않나.
   - (g) **목적·방법·근거의 층** — 첫 문단만 읽고 이 스킬이 무엇을 위한 것인지 한 문장으로 말할 수 있나. 통찰(「읽는 쪽은 에이전트다」)이나 파일 안내로 시작하면 독자는 무엇을 위한 문서인지 모른 채 읽는다(실측 2026-09-04: 이 스킬 자신). `## 목적` 이 무엇을 위한 일인가 → 어느 단계에서 왜 → 얼마나 중요한가로 이어지는 문단이고(「중요한 이유」 H3 로 갈리지 않았나), 핵심 원칙이 그다음, 절차가 그다음인가. 내부 용어가 첫 등장에 풀려 있나. 도구 사용법이 목적보다 앞에 오지 않았나(실측 2026-09-04: 채널 문서 둘이 덤프 SQL 28줄로 시작했다). 실측 서술이 길어져 다음 방법을 밀어내면 접거나 절 끝으로 뺐나.
   - (h) **폴더** — 파일마다 [판정 순서](31-files.md#폴더--가른-이유에-따른-자리) 여섯 질문으로 자리가 하나로 나오나. `references/` 라는 이름이 남아 있나. 어느 스텝도 여는 곳이 없는 고아 파일, 실행에 안 쓰이는 이력·미결 문서, 한글 경로, 폴더 안 README 가 있나.
9. **가드와 레버의 균형** — 스텝에 붙은 것이 전부 「무엇이 잘못되나」(금지·상한·게이트)인가, 「무엇이 결과를 크게 가르나」(판단을 넓히는 지식)도 있나? **가드는 실패 실측에서 나오고 레버는 거기서 안 나오므로**, 실측으로만 키운 문서는 하지 말 것의 목록이 된다. 특히 (a) 「전문가 지식으로」·「판단해서」로 넘기면서 **잠정 안을 만들 근거는 안 주는** 자리, (b) 실측 사례가 전부 실패 사례인 절 — 둘 다 레버가 빠진 신호다(→ SKILL 핵심 원칙 4). 레버의 모양은 「검색어를 넓힐 때 다른 도메인이라도 같은 구조의 일이면 비슷한 구조의 산업군 회사를 기준으로 찾아보라」처럼 신호와 수가 한 문장에 붙은 것이고, 실패 로그가 아니라 성사 케이스에서만 나온다.
10. **절차와 사고의 자리** — 스텝을 넘어 걸리는 프레임·상황 레버·함정이 `## 핵심 원칙` 한 곳에 있나, 아니면 절차 앞에 H2 로 여럿 나열되거나(실측 2026-09-17: 한 스킬은 일곱) 스텝 사이에 끼어 있나(다른 스킬은 태도 절 둘이 Step 3 과 4 사이)? 항목이 신호·수·왜 한 문단인가, 격언 한 줄인가? 원칙에 `적용 → Step N`, 스텝 판단 기준에 `→ 핵심 원칙 N` 이 있나? 한 스텝에서만 쓰는 판정이 원칙에 올라가 있거나, 골라 쓰는 목록이 원칙 안에 펼쳐져 있지 않나(→ `catalogs/`)? `## 일의 본질` 이나 그 안의 `### 그래서 우리는 이렇게 생각한다` 가 남아 있으면 전환 전이다. 헤딩의 괄호 표기는 저장소 규약을 따르고 이 축이 재지 않는다(→ [structure 절차와 사고](30-structure.md#절차와-사고--두-층)).
11. **전제** — 시작 때 있어야 하는 입력·환경·상태가 `## 전제` 한 표에 있나(전제 · 확인 · 없으면)? 줄마다 확인 방법이 있나, 없을 때 어디로 가는지 적혀 있나? 시작 조건이 로드 시점 문단이나 Step 1 안에 섞여 있지 않나? 실측 2026-09-17: 이 방법론 자신이 소스/배포본 구분·남의 미커밋 확인·변경 근거를 절차 곳곳에 흩어 두고 있었다.

**grade 밴드(대략):**
- **good** — 손댈 것이 거의 없음(모범).
- **minor** — 일관성·노이즈 폴리시 정도.
- **needs-work** — 구조 재편·description 재작성·라우팅 정합 등 실질 작업.

## 아키타입별 축 적용 (오분류 주의)

**모든 축을 모든 스킬에 기계 적용하면 오판한다.** 진단 전에 [아키타입](10-archetypes.md)을 먼저 식별하고, 그 아키타입에 유효한 축만 needs-work 근거로 삼는다.

- **원칙-에세이**(판단·태도 스킬 — 협상·관계·클로징 등, Step 헤더·도구 호출 없이 대략 35\~110줄): **축4(c) output 템플릿·축7 검증 게이트를 요구하지 않는다 — 없는 게 정상이다.** 이걸로 needs-work 판정하면 아키타입 오분류다. 이들에겐 축4(a·b) 지시 형식·why·축6 구조가 핵심.
- **절차-런북**(생성·수집 스킬 — 브리핑·등록·첨삭 등, Step 1\~N·출력 템플릿): 축4(c) output·축7 검증이 **실제로 있어야** 한다 — 없으면 진짜 갭.
- **도구·참조 스킬**(CLI 사용법·운영 절차·필드 사전 — 판단보다 조작이 몸통): 축 9(레버)·축 10(사고의 자리)을 요구하지 않는다. 핵심 원칙 절이 짧거나 없어도 정상이다. 축 8(폴더)·축 11(전제)은 그대로 유효하고, 특히 전제(환경·자격·설치)가 이 아키타입의 몸통이다.
- **금지의 성격도 아키타입처럼 가른다**(축4b·축7): 같은 "금지"라도 안전·저장 게이트(anti-loss·쓰기 confirm·개인정보)는 **유지가 정답**이고, "산출물 모양" 금지만 긍정 레시피 전환 후보다(→ [instruction-shaping §1](41-instruction-shaping.md#1-금지에서-긍정으로--실패-유형에-맞춘-형식)). 게이트 금지를 "긍정으로 바꾸라"고 지적하면 오진이다.

## 병렬 감사 레시피 (스킬이 많을 때)

스킬 전부를 한 컨텍스트로 진단하면 decay한다. 4~5개 배치로 나눠 병렬 서브에이전트에 맡긴다.

1. **인벤토리** — `find … -name SKILL.md`로 목록 + 줄수. 클러스터(도메인)·이상치(큰 것) 파악.
2. **배치 분담** — 배치당 4~5개 스킬. 각 에이전트에 **위 루브릭 전체 + slop-patterns를 그대로** 주고: 축 1~7·9·10 은 SKILL.md 정독으로, 축 8·11 은 SKILL.md 밖 문서를 열어 대조해서(파일 사이를 재는 축은 목록만 봐서는 못 잰다), **파일:라인 근거 필수, 절대 편집 금지(진단만)**, 마지막에 배치 통틀어 **공통 패턴** 정리.
3. **종합** — 배치 결과를 모아 **횡단 패턴**(여러 스킬에 걸친 라우팅·헤더 drift·boilerplate)을 뽑는다. 이게 개별 스킬 이슈보다 레버리지가 크다.
4. **판단 결정** — 동작 변경·삭제·deprecated 거취 같은 되돌리기 어려운 건 사용자에게 확인.
5. **단계 실행** — 폴리시 → 구조, ≤5파일/단계, 각 단계 grep 검증. (→ SKILL 본문 워크플로우)

## grep 툴킷

감사·검증에 실제로 쓴 grep들:

```bash
# 인벤토리 + 줄수
find <스킬 루트> -name SKILL.md -not -path "*/node_modules/*" | while read f; do printf "%5d  %s\n" "$(wc -l <"$f")" "$f"; done | sort -rn

# 헤더 drift
grep -rn "^## 목적\|^## 일의 본질\|핵심 원칙" --include=SKILL.md .   # 일의 본질 = 전환 전 표기

# frontmatter description 안 bold (렌더 안 됨)
grep -rnE "^description:.*\*\*" --include=SKILL.md .

# 특정 스킬로의 크로스-참조(rename/deprecate 시 dangling 점검) — 스킬명을 word-boundary로
grep -rnE "(^|[^a-z-])<스킬명>([^a-z-]|$)" --include=SKILL.md . | grep -viE "무시할패턴"

# description에 인용 트리거가 있나(undertrigger 후보 스캔)
grep -rL '"' --include=SKILL.md */SKILL.md   # 대략적 신호 — 실제론 description 라인만 봐야 정확
```

grep은 AST가 아니다 — 이름을 바꾸면 직접 참조·문자열·재-export·주석·트리 주석까지 **따로** 검색한다. 한 번의 grep이 다 잡았다고 가정하지 않는다. 한글 파일명은 macOS NFD 정규화로 놓칠 수 있으니 `ls` 눈확인 병행.

## 진단 뒤의 리팩터 패스

진단이 끝나면 SKILL 본문의 [절차](../SKILL.md#절차) Step 3~5 로 넘어간다. 진단(이 문서)과 실행은 **다른 패스**로 분리한다 — 같은 컨텍스트에서 진단하며 편집하면 근거 없는 수정이 섞인다.
